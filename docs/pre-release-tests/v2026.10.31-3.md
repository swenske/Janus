# v2026.10.31-3 pre-release tests

Tested on 2026-10-31, the afternoon the pre-release came out. It is
[v2026.10.31-2](v2026.10.31-2.md), the previous pre-release, with
[#454](https://github.com/swenske/Janus/pull/454), which answers two of
its campaign's findings ([#453](https://github.com/swenske/Janus/pull/453)):

- `POST /api/fleet/renew` and `/api/fleet/rescue` answer once a pass of
  the trust loop is done (15 s at most), so the Fleet card's notice says
  where the nodes really stand;
- `-advertise-address`'s first entry is where nodes register: the
  flag's help says so, and the Controller logs it at start.

Only the Controller changed; janusd, the kernel, HAProxy and the
extensions are the same code as v2026.10.31-2, rebuilt. This campaign
is therefore short: the two fixes, a second renewal of the issuing CA
and the rescue, and the usual checks once each.

## Verdict

**Ready to promote**, in my opinion. On the lab's real nodes and its
Controller:

- **The Fleet card is right at the answer (#453's finding 3)**: renewed
  with one node switched off, the answer and the card - without a
  reload - named that node alone, and `GET /api/fleet` said the same at
  that moment. The running nodes had the bundle within the second.
  However, **with a node switched off, the answer takes the whole 15 s**
  (finding 1). With every node up, a pass takes less than a second (the
  rescue answered in 0.81 s).
- **Where nodes register (#453's finding 1)**: the start line names
  the address and where it comes from. It names the name too when the
  name is listed first, so the earlier campaign's trap now shows in the
  log.
- **A second renewal**: the bundle kept the current CA and the new one,
  dropped the first, and reached every node, the v2026.10.21 node
  included. The switch waited for the node switched off and followed
  it. A new janusctl certificate came from the new CA and reached all
  five nodes. Everything was still there after a Controller restart.
- **The baseline holds**: the Controller's update, the cluster updated
  in place under load with nothing lost, HAProxy's throughput at
  v2026.10.31-2's level, zero AVC denials and the CIS audit 33/33 on
  every node.

Three minor findings and one older one, none in the way of a promotion
([Findings](#findings)).

## What this pre-release changes

### The renewal's answer (#454)

Before the test, every node was on the bundle of this morning's renewal
(`GET /api/fleet`, `janusctl access trust`), which lists two issuing
CAs: the first one and "2026-10".

One Controller machine, the one with Let's Encrypt, was shut down.
Then, in headless Chromium, the Fleet card's *Renew the issuing CA…*:
its confirmation, then the kit's file and its passphrase typed in. The
passphrase was never printed or captured, and the screenshots show only
the empty form. The script timed the click to the `POST
/api/fleet/renew` answer, then read the card as it stood, with no
reload, and `GET /api/fleet` at the same moment:

- **the answer came 15.98 s after the click** - the 15 s wait spent in
  full (finding 1). The Controller logged the renewal and each running
  node's `fleet bundle version … applied` within the click's second;
  the answer only came when the wait ran out;
- **the card named only the node switched off**: *Renewing: bundle
  version … goes to every node - still on an older one:* followed by
  that one node. The answer's `nodes_behind` and `GET /api/fleet` said
  the same. With v2026.10.31-2, the card named every node until a
  reload;
- the new bundle on every running node (the v2026.10.21 node
  included): **two issuing CAs, the current one and the new one; the
  first CA is gone**. Both are named "Janus fleet issuing CA 2026-10"
  and end on 2028-10-30 (finding 2). The card reads *Renewed 10/31/2026
  - the CA before until 10/30/2028*;
- a `janusctl login` while the switch waited: a certificate from the
  current CA (correct);
- the node powered on through the Controller had its janusd up 5 s
  later. It took the bundle **5 min 4 s** after that, at the trust
  loop's next pass (finding 3), and in the same second the Controller
  logged `fleet: every node has the renewal's bundle - janusctl's
  certificates now come from the issuing CA "Janus fleet issuing CA
  2026-10"`;
- a new `janusctl login`: the certificate's chain is the new CA (by
  fingerprint), and it reaches all five nodes, including v2026.10.21.
  A context still holding a certificate of the CA before kept working;
- **the rescue** (`POST /api/fleet/rescue`, with every node up - the
  card offers it only while a node needs the kit, so it went through
  the API): **200 in 0.81 s**, with a whole pass in the answer. Every
  node was checked within that second, none was behind, and the switch
  was already made. The log reads `the recovery kit opened for an
  hour…`, and the card afterwards was as before;
- after that: a node rebooted through its page was back in 7.1 s. The
  Controller restarted with the CA, the bundle and the switch, and every
  node was trusted in the second it started;
- the pages of every node, the node list with the Fleet card, and
  Settings, light and dark: axe clean, no failed request apart from
  the older node (finding 4).

### Where nodes register (#454)

- The image's `dashboardd -help` for `-advertise-address` now ends with
  *the FIRST entry is also the address nodes are told to register at
  (the Provision panel, the machines a hypervisor without a controller
  address of its own creates): add a name for the certificate after
  it, not instead of it*.
- Without the setting (the lab's Compose file), the Controller logs
  `registration: nodes are told to register at <address>:8443 (this
  host's first address)` at start.
- With the address first and a name after (`JANUS_CONTROLLER_ADVERTISE_ADDRESS`),
  it logs `… at <address>:8443 (the first -advertise-address)`. In that
  case `controller-info`'s `address` and the Provision panel's
  *Controller address* (light and dark, axe clean) give the same
  address.
- With the name first, the log line names the name, and so does
  `controller-info`. That is the previous campaign's trap, now visible
  at start.
- Each of these restarts kept the certificate served: no new name, no
  renewal.

## Findings

1. **With a node switched off, a renewal answers only after its full
   15 s.** The trust loop's pass gives each node 30 s, so it can't end
   while a node doesn't answer, and the renewal waits for its 15 s
   limit. The answer is right, because the running nodes are counted as
   they finish, but the card's button is busy for 16 s. That is exactly
   the case where its notice matters: with every node up, the pass
   takes under a second. Minor. Possible fixes: answer once every node
   is done or known unreachable, or keep the wait but say on the button
   what it's waiting for.
2. **A second renewal in the same month gives two CAs one name.** Both
   are "Janus fleet issuing CA 2026-10", and here both end on 2028-10-30
   because they were made the same day. The card, the switch's log line
   and `janusctl access trust` then show two identical names; only the
   fingerprints tell them apart. Renewing twice in a month is unusual,
   except after a key is suspected, which is exactly when telling them
   apart matters. Minor: a day or a short fingerprint in the name would
   do.
3. **A node powered on through the Controller waits for the trust loop's
   next pass.** It got the bundle 5 min 4 s after it came up (3 min 9 s
   in the previous campaign). Starting the machine doesn't kick the
   loop, so the switch waits up to ten minutes. Minor.
4. **A node older than clusters makes its page log a 501** (already in
   the previous report). The page of the v2026.10.21 node asks for
   `/api/cluster` and gets 501, which shows in the console.

Also: `PATCH /api/machines/{id}` refuses `"prerelease": true` (an unknown
field, 400), which `POST /api/machines` accepts; the version alone is
enough there. The lab's log profile still has a Logstash target outside
the lab's reach (`failing`), as in the campaigns before.
