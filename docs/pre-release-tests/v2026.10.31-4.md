# v2026.10.31-4 pre-release tests

Tested on 2026-10-31, the afternoon the pre-release came out. It is
[v2026.10.31-3](v2026.10.31-3.md), the previous pre-release, with new
kernels:

- Linux 7.2.14 on the default track (was 7.2.13; no known vulnerability
  fixed), [#456](https://github.com/swenske/Janus/pull/456);
- Linux 6.18.60 on the longterm track (was 6.18.59; fixes
  CVE-2026-98853), [#455](https://github.com/swenske/Janus/pull/455);
- versitygw 1.10.0 for `qemu-dashboard-test`
  ([#244](https://github.com/swenske/Janus/pull/244)), a test only.

janusd, HAProxy, the extensions and the Controller are the same code as
v2026.10.31-3, rebuilt. The kernel changed, so this campaign is the
node side of the usual one: the update in place under load, the kernel's
boot stages through the firmware and kexec, the rollback, failovers,
a rebooting node seen from the router, and HAProxy's throughput as a
real A/B against v2026.10.31-3.

## Verdict

**Ready to promote**, in my opinion. On the lab's real nodes and its
Controller:

- **Both kernels run**: the cluster's two nodes on 7.2.14 and the
  Controller's longterm machine on 6.18.60, each from the slot the update
  wrote, with zero AVC denials, no OOM kill, no oops, SELinux enforcing
  and the CIS audit 33/33 - and the Let's Encrypt machine on 7.2.14 the
  same.
- **The boot is as fast**: the kernel hands over to init at the same
  moment as with the kernels before (1.5-1.7 s on the default track,
  1.2-1.3 s on longterm), through the firmware and through kexec.
- **kexec works on both new kernels**: four chained kexec reboots on
  each, no oops; the patch the kernels carry for kexec still applies.
- **HAProxy costs the same**: node 01 alternated between v2026.10.31-4
  and v2026.10.31-3 by rollbacks, three runs each, and spent the same CPU
  per request on either kernel (within 2 %).
- **The baseline holds**: the Controller's update, the cluster updated
  in place under load with nothing lost to the update, the rollback with
  a continuous event log, the failovers, and the node's `Cease` to the
  router at a reboot - all as in the campaigns before.

Two minor observations and an older finding, none in the way of a
promotion ([Findings](#findings)).

## What this pre-release changes: the kernels

### Boot stages

Each node's Janus exporter gives `janus_boot_stage_seconds`: when, after
the kernel started, init started (`kernel`), janusd started (`init`),
HAProxy served (`haproxy`) and the API listened (`api`). Read after each
reboot, with the time from the call to the exporter answering on the
new boot. v2026.10.31-3 was measured the same way just before the
update.

**Node 02, default track** (2 vCPU, keepalived and BIRD):

| | v2026.10.31-3 (7.2.13) | v2026.10.31-4 (7.2.14) |
|---|---|---|
| Firmware reboots | 10.8 / 10.9 s | 10.9 / 10.9 s |
| `kernel` / `api` | 1.55 / 1.97 s, 1.51 / 1.94 s | 1.64 / 2.18 s, 1.52 / 1.98 s |
| kexec reboots, chained | 8.9 / 8.9 / 8.9 s | 8.8 / 8.9 / 8.9 / 8.9 s |
| `kernel` / `api` | 1.69 / 2.24, 1.70 / 2.24, 1.52 / 2.04 s | 1.56 / 2.04, 1.71 / 2.28, 1.53 / 2.05, 1.54 / 1.98 s |
| Oops | none | none |

The other boots of the day agree: nodes 01 and 02 after the cluster's
update on v2026.10.31-4, `kernel` 1.57 and 1.60 s, `api` 1.94 and
2.08 s; on v2026.10.31-3 (its campaign), 1.58 and 1.61 s, 1.91 and
2.16 s.

**The Controller's longterm machine** (1 GiB, no extension services),
rebooted through its node page:

| | v2026.10.31-3 (6.18.59) | v2026.10.31-4 (6.18.60) |
|---|---|---|
| Firmware reboots | 5.4 / 5.4 / 7.4 s | 5.3 / 40.4 s (below) |
| `kernel` / `api` | 1.23-1.24 / 1.41-1.43 s | 1.24 / 1.46 s, 1.31 / 1.59 s |
| kexec reboots, chained | 4.4 s each (4) | 4.4 / 6.5 / 6.5 / 4.5 s |
| `kernel` / `api` | 1.20-1.27 / 1.39-1.52 s | 1.22-1.25 / 1.42-1.49 s |
| Oops | none | none |

The same, within a tenth of a second. The kexec'd boots come up as
fast as the firmware's once the kernel runs; the time saved is the
firmware's (about 2 s on node 02, 1 s on the small machine). One
firmware reboot of the longterm machine took 40.4 s, with the kernel's
stage at 1.31 s: the time went to the firmware (finding 1).

### HAProxy's throughput

`wrk` on the VIP from a runner, 30 s runs, twice, then from the three
runners at once (256 keep-alive connections each); v2026.10.31-3 just
before the update, v2026.10.31-4 after it:

| Run | v2026.10.31-3 | v2026.10.31-4 |
|---|---|---|
| Keep-alive, 8 connections | 14,305 / 14,215 req/s | 14,327 / 14,409 |
| Keep-alive, 64 connections | 46,594 / 46,569 | 46,273 / 44,690 |
| Keep-alive, 256 connections | 49,569 / 49,521 | 49,445 / 48,794 |
| A new connection per request, 32 connections | 4,830 / 4,878 | 4,697 / 4,669 |
| Three runners at once (sum) | 44,345 / 44,026 | 42,507 / 43,028 |

New connections and the three runners came out about 3.5 % lower,
within the spread these runs have shown between rounds, but the kernel
is on that path. So node 01 (the VRRP master, serving the VIP) was
measured alternating: v2026.10.31-4, rolled back to v2026.10.31-3, and
so on, three runs each, its CPU time by mode read off its exporter
around each `wrk` run:

| Run | v2026.10.31-3 (7.2.13) | v2026.10.31-4 (7.2.14) |
|---|---|---|
| A new connection per request: req/s | 4,656 / 4,588 / 4,693 (mean 4,646) | 4,701 / 4,680 / 4,636 (mean 4,672) |
| CPU per request (user + system + softirq + steal) | 174 / 178 / 171 µs (mean 174.3) | 181 / 168 / 181 µs (mean 176.7) |
| Keep-alive, 256 connections: req/s | 50,189 / 50,643 / 49,667 (mean 50,166) | 45,871 / 52,165 / 49,552 (mean 49,196) |
| CPU per request | 39.5 / 39.0 / 39.9 µs (mean 39.5) | 43.4 / 37.7 / 39.9 µs (mean 40.3) |

The two kernels cost the same: the means are within 1.4 % and 2 %, and
each version's runs spread wider than the gap (the keep-alive mean is
pulled by v2026.10.31-4's first run alone). New connections are
latency-bound here (the node about 60 % idle), as the earlier campaigns
found.

### The nodes' health

At the end:

- nodes 01 and 02 (v2026.10.31-4, Linux 7.2.14): SELinux enforcing, no
  OOM kill, no oops, the CIS audit 33/33, **zero AVC denials**,
  `Secure Boot: off`. Node 01 runs from slot A and node 02 from slot B,
  with v2026.10.31-3 on the other slot;
- the Controller's longterm machine (6.18.60) and its Let's Encrypt
  machine (7.2.14): SELinux enforcing, no OOM kill, no oops, zero AVC
  denials, CIS 33/33;
- the node pages of all five nodes, the Nodes and the Clusters pages,
  light and dark: axe clean, no failed request apart from the older
  node's (finding 3).

## Findings

1. **One firmware reboot of 40 s.** The longterm machine's second
   firmware reboot took 40.4 s against 5.3 s for the first; the kernel
   reached init 1.31 s after it started, so the time went before the
   kernel - the lab's firmware variable store, met before on these
   machines. Not the kernel; a kexec reboot skips the firmware.
2. **The update under load had a longer tail.** `wrk`'s p99 during the
   cluster's update was 30.1 ms (8.87 ms in v2026.10.31-3's campaign),
   the median the same (0.57 ms), the throughput 1.4 % lower and nothing
   lost. A tail across two reboots of one 3-minute run; not seen in the
   throughput runs or the A/B.
3. **A node older than clusters makes its page log a 501** (from
   v2026.10.31-2's campaign): the v2026.10.21 node's page asks
   `/api/cluster` and gets 501. Not this pre-release.

Also: the lab's log profile still has a Logstash target outside the
lab's reach (`failing`), as in the campaigns before.
