# v2026.10.29-4 pre-release tests

Tested on the afternoon of 2026-10-29: a short pass on what changed since
[v2026.10.29-3](v2026.10.29-3.md), on a configuration shaped like the
production one whose rollout found the defects this pre-release fixes.
It is v2026.10.29-3 with
[#412](https://github.com/swenske/Janus/pull/412) (a frontend that listens
only on a socket gets its URLs at the bind relaying to it; `scheme=` and
`proto=` tags; a frontend's check is HAProxy's own state of it, not a
connection) and [#411](https://github.com/swenske/Janus/pull/411) (a
cluster member's update is found before it is drained; a machine is
ready with the version it runs; an update error that's behind the
machine goes). What isn't run again here is in the reports of
[v2026.10.29-2](v2026.10.29-2.md) and [v2026.10.29-3](v2026.10.29-3.md).

## Verdict

**Ready to promote.** What it fixes works on the lab's nodes:

- **Every site behind the socket reaches Consul**: 10 URLs of 10 on
  each member, where v2026.10.29-3 registered 1 - with the relaying
  bind's port, `via`, and the new tags.
- **The frontend that refuses other sources stays passing**: 5.5
  minutes without a change, where v2026.10.29-3's check flipped 7 to 8
  times in 3 minutes.
- **A cluster's update builds the new image while the member serves**:
  96 s of the image factory's build, the member in service, its machine
  ready; drained only then.
- **Terraform's update of a machine ends cleanly**, and the next plan
  has no changes.

Two defects, neither from this pre-release ([findings 1 and
2](#findings)):

1. **A janusd restarted on a node whose boot came from an update never
   comes back**: init stops supervising it. Found here, present since
   the first releases - v2026.10.29-3, in production, too. HAProxy keeps
   serving; the extensions janusd ran stop with it.
2. **`filter: 'ServiceMeta.proto == "…"'` doesn't pick a service's
   instances in Prometheus**, as the release notes and the guide say:
   only `tags` does.

## Findings

1. **janusd isn't started again after it exits, on a node booted from
   an update.** `janusctl system restart` on B (16:43) and on C (16:49):
   janusd stopped its extensions - the Consul agent left, the node's
   services left the catalog -, exited (`init: /sbin/janusd (pid 86)
   exited (0)` on the console), and nothing started it again: its API
   refused connections for 10 minutes, the console stayed silent,
   HAProxy kept serving. Both boots came from an update with
   `wait_for_health`. The same machine C, rebooted through the
   firmware and restarted 70 s later: janusd back in a second. In
   `rootfs/init`: a boot that starts with a pending boot-commit marker
   gives the supervisor a deadline (`GiveUpAfter`, 60 s or the marker's
   health timeout) from boot; past it, janusd's first exit makes the
   supervisor call its give-up hook - a no-op, the marker having been
   confirmed and cleared - and return, so nothing restarts janusd until
   the next reboot. There since 2026-09-24: every release, the one in
   production too. A node with keepalived or BIRD would lose them with
   janusd. Until it's fixed, reboot an updated node rather than
   restarting its janusd (the node's page **Restart janusd**, `janusctl
   system restart`); a reboot also brings back one in this state.
2. **`filter` doesn't do what the notes say in Prometheus.** The
   release notes ("`tags: [url, proto=http]` or `filter:
   'ServiceMeta.proto == "http"'` in Prometheus") and the guide
   ("`filter: 'ServiceMeta.proto == "http"'` does what `tags:
   [proto=http]` does"): Prometheus's Consul discovery passes `filter`
   to the catalog's list of services only - `haproxy-url` has a TCP
   instance, so it is kept, then every instance of it is a target. On
   each service's instances (`/v1/health/service`), `ServiceMeta` isn't
   a selector: `Service.Meta.proto` there made Prometheus refuse the
   service list ("Selector "Service" is not valid", no target). The
   published example uses `tags`, which works; a relabel rule on
   `__meta_consul_service_metadata_proto` would too.
3. **The Controller's update needs its release list refreshed** for a
   pre-release published minutes earlier: the list is cached 10
   minutes, and the call answered 409 "isn't the pre-release on offer"
   until a refresh. As designed (the page's Refresh); noted for the
   campaigns' script.
4. **The cluster's journal is silent during the image factory's
   build**: 94 s between "updating kc to …" and the first drain, with
   nothing on the cluster's page saying why - the machine's history has
   it.
