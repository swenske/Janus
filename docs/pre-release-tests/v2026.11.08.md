# v2026.11.08 pre-release tests

Tested on 2026-11-08, the morning it came out, on the lab where
v2026.11.07 - the newest release, promoted the day before - was measured
again the same morning as the baseline
([v2026.11.07's report](v2026.11.07.md)). The rest of the 2026-11-05
security review:

- **A node's identity and its fleet's reset take a console certificate**
  ([JANUS-2026-033](https://github.com/swenske/Janus/blob/v2026.11.08/security/fixes/JANUS-2026-033.json)):
  a certificate of the node's own CA issued through its API no longer
  exports the identity nor passes `access trust-reset`; a rescue
  certificate or the fleet's recovery kit (`-kit`) still does;
- **the review's hardening items (#28)**: the connectivity test kept
  away from the node itself and link-local addresses for an operator of
  the network domain alone, an open pairing window renewing its
  certificate and code every hour, only the Controller's own certificate
  shown as the Controller in a node's clients, `/csp-report` bounded per
  source, single sign-on "trusted as is" keeping a linked account's own
  factor, a removed standby dropping its copy, init surviving a
  malformed volume, janusctl's dashboard drawing no control character.

Each item reachable from the lab was tried on v2026.11.07 first - where
the hole shows - then on the pre-release. The baseline went through as
usual: the Controller's update, the cluster updated in place under load,
the Controller's other machines updated, failovers, janusd restarted,
HAProxy reloaded under load, rollbacks, HAProxy's throughput against
v2026.11.07 with an A/B by rollbacks, the boot stages, the nodes' health,
the Controller's pages.

The load and the probes came from the build box and one CI runner, as
for v2026.11.07 (the production hypervisors hosting the two other
runners may be updated at any time); every throughput figure is
compared with v2026.11.07 measured this morning from the same client.

## Verdict

**JANUS-2026-033 and every #28 item the lab can reach work on the lab's
real Controller and enforcing nodes, and the baseline holds: the
cluster's in-place update lost nothing (VIP 0 of 3,323, anycast 0 of
3,320), the failovers are as before, zero AVC denials, every node CIS
33/33, the same CPU cost per request. My opinion: ready to promote.**
The decision is yours. No regression found.

- **#033**: on v2026.11.07, an `os:admin` certificate a node issued
  through its API (`pki generate-client-config`) exported the node's
  identity (`pki/ca.key` in the file) and reset its fleet; the node also
  issued certificates named `rescue:…` and `kit:…`. On v2026.11.08 the
  export is refused - "… goes only to a certificate the fleet's root
  itself signs or one the node issued at its console, and lab-74-api's
  is neither: add -kit KIT (the fleet's recovery kit) or use a rescue
  certificate (janusctl access rescue)" - and leaves no file; the fleet's
  reset is refused - "only a certificate the node's own CA issued at its
  console - a rescue certificate (janusctl access rescue) - may forget
  its fleet"; both names are refused. `-kit` still exports the
  identity, and a rescue certificate (it carries OID 2.999.1.2) both
  exports it and resets the fleet.
- **#28, the connectivity test**: on v2026.11.07 an operator of the
  network domain alone reached the node's own API and HAProxy on
  127.0.0.1 from the node page's Connectivity test. On v2026.11.08 the
  same account gets "the node itself and link-local addresses are for
  whoever may change its HAProxy configuration" towards 127.0.0.1 and
  169.254.169.254, while the admin and an operator of the HAProxy domain
  still reach 127.0.0.1; a backend is reached by all three.
- **#28, the clients**: on v2026.11.07 a certificate named
  `janus-controller` issued through the API, calling with
  `-as-user lab-74-ghost`, showed in `system clients` as
  "janus-controller (Controller) … for lab-74-ghost". On v2026.11.08 it
  is a plain `os:admin` client; the real Controller is still shown as
  the Controller, acting for its user.
- **#28, CSP reports**: 50 reports from one address, then 10 from
  another, within a minute: on v2026.11.07 the first address took all
  ten lines of the minute and the second got none; on v2026.11.08 each
  got three, the rest counted in "54 more reports in the last minute,
  not logged".
- **#28, the pairing window**: a bare pre-release node left with its
  window open showed a new code exactly an hour after the first, served
  from a new certificate; `janusctl fleet adopt` with the first code was
  refused - "… another code (an open window's is renewed every hour -
  read it again on the node's console) …" - and the new code paired it.

## The security fixes

### A console certificate for the identity and the fleet's reset (#033)

Two fresh Controller machines on the second KVM host, made by the lab's
Controller in 10 and 15 s: the first on v2026.11.07's default image, the
second on the pre-release's. Every call with the janusctl context of a
Controller sign-in (an admin certificate of the fleet's issuing CA),
each machine's own certificates issued with `janusctl pki
generate-client-config` - what any admin can have a node do.

| Step | v2026.11.07 | v2026.11.08 |
|---|---|---|
| `generate-client-config -role os:admin -name lab-74-api` | issued by the node's CA | the same |
| With it: `system state export -identity FILE` | **written, 15 files, `pki/ca.key` among them**; the node's log: "state: exported (14 files, identity true) - by lab-74-api (os:admin)" | **PermissionDenied**: "the node's identity - its CA's key - goes only to a certificate the fleet's root itself signs or one the node issued at its console, and lab-74-api's is neither: add -kit KIT (the fleet's recovery kit) or use a rescue certificate (janusctl access rescue) - docs/guide/replacing-a-node.md"; **no file** |
| `generate-client-config -name rescue:lab-74`, then `kit:lab-74` | both issued | **InvalidArgument**: "rescue:<name> is how the node names its rescue certificates", "kit:<name> is how the node names a recovery kit's certificates" |
| With the API certificate: `access trust-reset` | **"Fleet: none"** - the fleet's context refused afterwards ("certificate required") | **PermissionDenied**: "only a certificate the node's own CA issued at its console - a rescue certificate (janusctl access rescue) - may forget its fleet"; the fleet's context still works |

Then the ways that remain, on the pre-release's machine:

| Step | Result |
|---|---|
| `system state export -identity -kit KIT` (the Controller's recovery kit, its passphrase through `JANUS_KIT_PASSPHRASE`) | written, `pki/ca.key` in it; the node's log: "… by kit:admin (os:admin, fleet)" |
| A rescue volume (`janusctl image rescue-volume`) attached as a SATA CD-ROM, a cold boot read on the hypervisor's serial console, `janusctl access rescue` with its code | `O=os:admin, CN=rescue:lab-74-r33`, an hour, **carrying OID 2.999.1.2**; "the rescue window is closed" |
| With the rescue certificate: `system state export -identity` | written, `pki/ca.key` in it; "… by rescue:lab-74-r33 (os:admin)" |
| With the rescue certificate: `access trust-reset` | "Fleet: none - only the node's own CA lets in" |

The code stayed in the job's temporary directory and was never printed;
every certificate and export file was deleted at once, the volume
detached and its image removed, both machines destroyed.

### The connectivity test keeps to the network (#28)

Two throwaway Controller accounts with no role of their own: one with
an operator grant on the **network** domain alone, one with an operator
grant on HAProxy and the network. Each, and the admin, ran the node
page's Tools › Connectivity test (its own route, `POST
/nodes/<id>/api/system/probe`) on node 01:

| Target | v2026.11.07: admin / network only / HAProxy | v2026.11.08: admin / network only / HAProxy |
|---|---|---|
| `tcp 127.0.0.1:9505` (the node's API) | connected / connected / connected | connected / **refused** / connected |
| `http://127.0.0.1:8080/` (HAProxy's health frontend) | 200 / 200 / 200 | 200 / **refused** / 200 |
| `http://169.254.169.254/latest/meta-data/` | timeout ×3 (nothing there in the lab) | timeout / **refused** / timeout |
| `tcp <a backend>:80` | connected ×3 | connected ×3 |

"Refused" is the connect step failing with "dial tcp …: the node
itself and link-local addresses are for whoever may change its HAProxy
configuration" - the request reaches the node and is refused there, not
by the Controller.

### The pairing window renews its code (#28)

A node on the pre-release's image with nothing provided (no NoCloud,
one DHCP interface), made by hand on the second KVM host, its window
left open. Its serial log was read every minute: each new code stamped
with the time it was first seen and a hash of it - never the code.

| Time (UTC) | What happened |
|---|---|
| 08:08:00 | janusd: "pairing: the node trusts nothing yet - a pairing window on :9506, its code on the console"; the window's certificate dated 07:08:00 |
| 09:08:00 | janusd: "pairing: the window on :9506 has a new certificate and code, its code on the console - the previous one no longer opens it"; a second code on the console, the window serving another certificate (dated 08:08:00) |
| 09:08:40 | `janusctl fleet adopt -code` with the **first** code, into a throwaway fleet: refused at the TLS handshake - "the node's pairing certificate isn't the one its code names - another code (an open window's is renewed every hour - read it again on the node's console), or not that node" |
| 09:08:40 | the same with the **new** code: paired; janusd: "the window on :9506 is closed: paired" |

The node and the throwaway fleet were destroyed afterwards.

## The baseline

### The Controller's update

The lab's Controller updated itself from v2026.11.07 to v2026.11.08
through its updater: the pre-release offered apart (`update_available`
false); refused without `"prerelease": true` (409); the job "Updated to
v2026.11.08" in 25.5 s; **7.46 s** without an answer (73 probes of 616,
every 0.1 s, none slower than 0.5 s). The session, in memory, was lost
and signed in again; `docker compose up -d` gave the updater the
pre-release's image too (Compose v5.7.0 in both). The `ha/` directory as
before, no stale socket.

### The image factory

The node page's pre-release request for the lab's schematic answered
"building" at once this time, 2 minutes after the release (v2026.11.07's
first request had answered "unavailable" - #553), and the bundle was
**ready in 51 s**. The two other schematics the lab uses (the longterm
kernel, Let's Encrypt) were ready in 33 and 34 s.

### HAProxy's throughput

`wrk` on the VIP from the CI runner, 30 s each; v2026.11.07 measured
first, the same morning, from the same runner. HAProxy and the kernel
are the same bytes, so this is a sanity check:

| Run | v2026.11.07 | v2026.11.08 |
|---|---|---|
| Keep-alive, 64 connections | 47,614 / 47,351 / 47,745 req/s | 49,874 / 48,910 / 50,589 (mean +4.7 %) |
| A new connection per request, 32 | 3,301 / 3,315 / 3,780 | 3,253 / 2,932 / 3,495 (mean −6.9 %) |

New connections swing by a fifth between rounds, so an A/B decided it:
node 01 alternated between the two versions by rollbacks, its CPU time
per request read from its exporter around each run.

| Per request (node 01's busy CPU) | v2026.11.07 | v2026.11.08 |
|---|---|---|
| A new connection per request, 32 | 191.4 / 201.1 µs (3,387 / 3,111 req/s) | 202.9 / 188.7 µs (3,112 / 3,715 req/s) |
| Keep-alive, 256 connections | 36.8 / 37.0 µs (52,585 / 52,390 req/s) | 36.7 / 36.1 µs (53,045 / 53,413 req/s) |

The same cost per request.
