## CI: image-build

[Run 39206112558](https://github.com/swenske/Janus/actions/runs/39206112558),
from `main` at `f657cca`, with `release_version=v2026.10.19-2` and
`prerelease`, dispatched at 07:44 Paris. Published at 08:53 Paris.

A first build from `ab56f74` (#168 alone) was cancelled during its
tests, nothing published, to take #170 in.

The first attempt of this one failed on a test script's own check:
`haproxy-runtime-test`, with HAProxy 3.2, expected a stream it had just
shut down to be unknown the second time. A stream's ID is its address,
and HAProxy hands the address of a stream that ended to the next one -
often the runtime API connection of the very next command, which the
second shutdown then found and ended. It had passed every build before,
on the three branches. The job, run again on the same commit, passed;
[#171](https://github.com/swenske/Janus/pull/171) tests the unknown
stream with an address no stream can have.

The lab ran v2026.10.19, as its campaign left it. The load and the
probes came from the runners, once the image factory had built the
pre-release for the lab's schematics and none ran a CI job; the browser
ran on the fourth client machine.

| Step | v2026.10.19 | v2026.10.19-2 |
|---|---|---|
| The Controller's update by its updater | no answer for 0.41 s (the job: 13.8 s) | no answer for **0.51 s** (the job: 13.9 s) |

| Rolling update under load: VIP | 1 lost (0.05 s) / 2,344 | **0** lost / 2,336 |

| Same: `wrk` | 12,943 req/s, 99th percentile 11.52 ms | 12,699 req/s, 99th percentile 13.44 ms |
| The longterm machine, updated through the Controller | ready 74 s after the call | ready **73 s** after; 6.18.57, 0 AVC denials, CIS 33/33 |

- **The rolling update ran twice.** The first try stopped after node 02:
  the lab's script, once its wait had seen the node in service, checked
  it all again at once and took one transient answer for a failure,
  without saying which check. Node 02's own logs show nothing amiss: it
  was back on v2026.10.19-2 with HAProxy, keepalived and BIRD healthy.
  The script now trusts its wait and names the check that fails; node
  02 was rolled back to v2026.10.19 (8 s) and undrained, and the rolling
  update ran again from the start - the figures above.
- **`wrk`'s 16 read errors** are its 8 keep-alive connections, closed
  once by each node that reboots, as in every campaign.
- **The binaries moved again**: HAProxy, keepalived and BIRD took a new
  address on both nodes after the update.

### The Controller's pages

The same walk as [v2026.10.19's](v2026.10.19.md#the-controllers-new-pages),
nothing laid over the pages this time:

| Run | Pages | Result |
|---|---|---|
| v2026.10.19 | 216 | axe `color-contrast` on 7 (a status pill on a machine's strip); one console error |
| v2026.10.19-2 | 216 | **no axe finding**, no page error, no failed request; three console errors, below |

The three console errors are each `net::ERR_NETWORK_CHANGED`, and each
came within seconds of a container joining a Docker bridge on the
browser's machine (09:13:37, 09:30:16, 09:41:58 - another job there):
Chromium aborts a request in flight when the machine's network
interfaces change. Not the pages - and most likely v2026.10.19's one
too.
