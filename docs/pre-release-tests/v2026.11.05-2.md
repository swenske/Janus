# v2026.11.05-2 pre-release tests

Tested on 2026-11-05, the evening it came out, on the lab where
v2026.11.05 was measured the same afternoon
([v2026.11.05's report](v2026.11.05.md)) and which this campaign took as
its baseline. The release that closes the 2026-11-05 security review:
the twelve lower-severity findings left after v2026.11.05's two high and
nine medium, JANUS-2026-019 to -030, all fixed. What the lab can show of
them, each tried on the lab's real nodes and Controller - on the release
first, where the hole can be seen without exploiting it:

- **The pairing and rescue window, rate-limited per source**
  ([JANUS-2026-029](https://github.com/swenske/Janus/blob/v2026.11.05-2/security/fixes/JANUS-2026-029.json)):
  five wrong codes from one place pause only that place, the window stays
  open for everyone else, and the paused source stops filling the audit;
- **a rescue volume's `firewall: skip` ends with the window**
  ([JANUS-2026-030](https://github.com/swenske/Janus/blob/v2026.11.05-2/security/fixes/JANUS-2026-030.json));
- **a state import checked against the global policy**
  ([JANUS-2026-028](https://github.com/swenske/Janus/blob/v2026.11.05-2/security/fixes/JANUS-2026-028.json));
- **a write-only secret re-required when its URL or TLS trust changes**
  ([JANUS-2026-026](https://github.com/swenske/Janus/blob/v2026.11.05-2/security/fixes/JANUS-2026-026.json));
- **fewer ways for a reader to see secrets**
  ([JANUS-2026-023](https://github.com/swenske/Janus/blob/v2026.11.05-2/security/fixes/JANUS-2026-023.json));
- **the hypervisor SSH key sealed on disk**
  ([JANUS-2026-021](https://github.com/swenske/Janus/blob/v2026.11.05-2/security/fixes/JANUS-2026-021.json));
- **a deleted, disabled or demoted account's sessions and tokens end at
  once** ([JANUS-2026-020](https://github.com/swenske/Janus/blob/v2026.11.05-2/security/fixes/JANUS-2026-020.json));
- **a crafted ICMP packet can't crash a probe**
  ([JANUS-2026-019](https://github.com/swenske/Janus/blob/v2026.11.05-2/security/fixes/JANUS-2026-019.json));
- **an SSO sign-in flood can't block sign-in**
  ([JANUS-2026-024](https://github.com/swenske/Janus/blob/v2026.11.05-2/security/fixes/JANUS-2026-024.json)).

The baseline went through as usual: the Controller's update, the cluster
updated in place under load, failovers, janusd restarted, HAProxy
reloaded under load, rollbacks, HAProxy's throughput against v2026.11.05
(the same bytes, so a sanity check), the boot stages, the nodes' health.

## Verdict

**Every fix the lab can reach works on real enforcing nodes and on the
lab's Controller, and the baseline holds: the cluster's in-place update
lost one request of 3,293, the failovers are as before, zero AVC
denials, every node CIS 33/33. My opinion: ready to promote.** The
decision is yours. Two things to know, neither this release's doing:
the Controller still reads every release's `security.json` one after the
other to name the newest ([finding 1](#findings)) - tonight GitHub was
quick, so it didn't bite; and a single lab host can't fill the SSO
sign-in table that [JANUS-2026-024](#accounts-the-probe-single-sign-on-020-019-024) guards,
because the per-source limit stops it first - that fix stays proven by
its unit test.

- **#029**: on the release, five wrong codes from one source closed the
  pairing window until the node restarted, and the right code from
  another source was then refused ("no pairing window answers"). On the
  pre-release the five wrong ones pause only that source ("5 wrong
  pairing codes from your address: wait 1m0s"), the window stays open -
  `openssl s_client` still answers on :9506 - and the Controller, a
  different source, pairs the node. The paused source's further calls
  are `ResourceExhausted` and leave no audit line: janusd logged four
  counted refusals and nothing for the flood that followed.
- **#030**: a `-skip-firewall` rescue volume booted the node without its
  saved nftables ruleset ("the rescue volume says skip - the saved
  ruleset isn't applied this boot") - its marker rule gone -, and when
  the rescue window closed janusd put the ruleset back **in the same
  boot** ("the rescue window closed - the saved ruleset is applied
  now"), not at the next.
- **#028**: a state export whose `haproxy/haproxy.cfg` broke the global
  policy - no `chroot`/`uid`, or a second stats socket - was **refused
  before staging** ("the imported haproxy/haproxy.cfg: global: "chroot
  /var/empty" is required on a node", and "only janusd's socket ... is
  allowed"); the untampered export imported and staged.
- **#026**: a log target's API key, a Consul token and an SSO client
  secret - each set but not read back - were **kept** on the release when
  only the TLS trust or the issuer changed; on the pre-release each is
  re-required when the destination or the trust changes ("give the
  client secret again"), and kept when only a name changes.
- **#023**: a reader of a node saw, on the release, the probe's target
  with its credentials, a `tcp-check send` payload and the bearer/cookie/
  url-param ACL patterns, and an operator the previous boot's kernel log.
  On the pre-release the probe event hides the credentials, those lines
  read `<redacted>`, and the kernel log is admin-only.
- **#021**: the hypervisor SSH keys on the Controller's disk were PEM in
  the clear on the release; on the pre-release's first start they are
  sealed (the `JSK1` prefix, no `PRIVATE KEY`), and the Controller still
  drove libvirt to make a node.
- **#020, #019, #024**: an account's sessions and tokens end at once when
  it is disabled, demoted or deleted; a node under a flood of crafted
  ICMP kept janusd alive through ping and traceroute probes; single
  sign-on works end to end, and a sign-in flood from one host is turned
  away transiently without blocking sign-in.

## The security fixes

### The pairing and rescue window, per source (#029)

A throwaway node from the pre-release's image of the lab's schematic,
nothing provided - one DHCP interface, its pairing window open. Five
well-formed but wrong codes from the build box (a scratch fleet's
`janusctl fleet adopt -code`), then more, then the right code from the
lab's Controller - another source:

| | v2026.11.05 | v2026.11.05-2 |
|---|---|---|
| The five wrong codes | "4 … 1 tries left before the window closes", then "the window is closed until the node restarts" | "4 … 1 tries left **from your address** before a pause", then `ResourceExhausted`: "5 wrong pairing codes from your address: wait 1m0s" |
| More wrong codes from that source | the port is refused (the window shut) | `ResourceExhausted`, the window still answering |
| `openssl s_client` on :9506 | connection refused | the window's certificate (`CN=pairing janus-…`) |
| The right code, from the Controller | 502 "no pairing window answers" | **201 - the node paired** |
| janusd's audit of the flood | - | the four counted refusals only; the pause and the `ResourceExhausted` calls are **not** logged |

### A rescue volume's firewall skip (#030)

On a node that trusts the fleet, with nftables: a ruleset with a marker
rule (`tcp dport 4242 counter drop`) applied and confirmed, then a
`-skip-firewall` rescue volume attached as a CD-ROM (a SATA bus - SATA
doesn't hot-plug, so attached to the stopped domain and cold-booted) and
the node started:

| Step | What the node did |
|---|---|
| The rescue boot | `init: rescue: a rescue volume on /dev/sr0`; **`firewall: the rescue volume says skip - the saved ruleset isn't applied this boot`** - the marker rule absent, the window answering on :9506 |
| `access rescue -name …`, one call | an `os:admin` certificate of the node's CA; the call works; the window closes ("the window on :9506 is closed: rescued") |
| The window closed | **`firewall: the rescue window closed - the saved ruleset is applied now`** - the marker rule back, **in the same boot** |
| The volume detached, rebooted | no rescue line, the firewall applied at boot, :9506 shut |

### A state import against the global policy (#028)

The state of node 02 exported; two copies whose `haproxy/haproxy.cfg`
breaks the policy (one with no `uid`/`gid`/`chroot`, one with a second
`stats socket`; the manifest's SHA-256 updated so the refusal is the
policy, not a corruption check), each imported onto an unused node:

| The import | v2026.11.05-2 |
|---|---|
| No `uid`/`gid`/`chroot` | **refused**: "the imported haproxy/haproxy.cfg: global: "chroot /var/empty" is required on a node" |
| A second stats socket | **refused**: "only janusd's socket, /run/janus/haproxy-admin.sock, is allowed on a node" |
| The untampered export (`-no-reboot`) | **accepted**: "Staged: the state goes in place at janusd's next start" |

### A write-only secret follows its server (#026)

Three secrets an admin can set but not read back, set then re-saved with
the secret field empty and one non-secret field changed, on the lab's
Controller (the real log profile and Consul settings read first and put
back untouched):

| The secret | A changed destination/trust, empty secret | Only a name changed, empty secret |
|---|---|---|
| A log target's API key (its TLS CA changed) | the secret **re-required** - the target's `secrets` map is empty (kept on the release) | kept |
| The Consul token (its TLS CA changed) | the token **re-required** - `has_token` false (kept on the release) | - |
| The SSO client secret (its issuer changed) | **400** "the issuer, client ID or TLS trust changed: give the client secret again" | kept |

### Readers (#023)

An operator and a reader certificate of node 02:

| | The release | The pre-release |
|---|---|---|
| The `probe.run` event's target | `https://user:pass@host/` | `https://host/` - the credentials gone |
| A reader's `get-config`: `tcp-check send`/`send-binary`, the `http_auth_bearer`/`req.cook`/`url_param` ACLs | the payloads and patterns in the clear | `<redacted>` (the admin still sees them) |
| An operator reading a previous boot's kernel log | served | refused - "Dmesg requires role [os:admin]"; a reader refused too |

### The hypervisor SSH key sealed (#021)

The Controller's `hypervisors/<id>/ssh.key` on disk (read as a
fingerprint only, never the key's bytes):

| | v2026.11.05 | v2026.11.05-2 |
|---|---|---|
| The two hypervisors' keys | PEM in the clear (`----`, a `PRIVATE KEY` header) | **sealed** (`JSK1`, no `PRIVATE KEY`) on the first start |
| The hypervisor still usable | - | the Controller made a node on a hypervisor through libvirt, ready in 17 s |

### Accounts, the probe, single sign-on (#020, #019, #024)

- **#020**: an operator account's session and token were cut at once
  when it was disabled (401) and when it was deleted; a token followed a
  demotion to reader; a name reused after a delete did not bring an old
  session back. (All already so on v2026.11.05 - a regression check.)
- **#019**: 24,880 crafted ICMP packets - the unassigned types 64-79,
  20-59 bytes, that could panic the probe's raw socket - sent to node 02
  while `ping` and `traceroute` probes ran: janusd's PID and boot stage
  unchanged (no restart), the API up, every probe "done ok", **zero AVC
  denials**.
- **#024**: single sign-on works end to end against a Keycloak next to
  the Controller (a reader signed in, an admin asked to enrol a second
  factor, an ungrouped account refused, `acr` honoured, `sso.json`
  sealed). The per-source limit answers "too many sign-ins started -
  try again later" past ten starts from one host and clears in seconds -
  never the durable "too many sign-ins under way". Filling the global
  10,000-entry table needs many source addresses (an IPv6 /64), out of
  one lab host's reach; the eviction fix is proven by `TestLogins`.

## Findings

1. **The Controller still names the newest release by reading every
   `security.json` - not new, not fixed here.** v2026.11.05's
   [finding 1](v2026.11.05.md#findings) stands: the Controller reads
   each release's `security.json` one after the other within one fetch,
   and one slow or failing file holds the whole list. #027 caches the
   *site's* unknown versions and caps a cluster pull, but not the
   Controller's `nodeproxy` release reading. Tonight GitHub was quick and
   the update went through in 7.35 s; on a bad GitHub day a restart would
   still leave the update and the 🔒 badge unknown for a while. Worth a
   disk cache or reading them in parallel.
2. **The SSO sign-in table's eviction can't be shown from one lab host.**
   JANUS-2026-024's fix is the global 10,000-entry table evicting its
   oldest entry instead of refusing; filling it needs many source
   addresses. From one host the per-source limit (ten, then one every
   six seconds) answers first, so the lab shows the per-source behaviour
   and that sign-in stays possible, and leaves the eviction to
   `TestLogins`.
3. **The 43.7 s firmware reboot is OVMF_VARS compaction (#307).** Node
   02's stateful Secure-Boot-vars file compacts now and then at the
   firmware stage; it isn't the pre-release and the stages after the
   kernel are unchanged.
