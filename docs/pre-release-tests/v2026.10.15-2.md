# v2026.10.15-2 pre-release tests

Tested on the afternoon of 2026-10-15, right after it was cut: the CI
run that built it, then the lab. The figures to compare with are
[v2026.10.15's campaign](v2026.10.15.md), measured the same morning with
the same clients and the same scripts.
The scenarios: [Lab test scenarios](lab-scenarios.md).

## Verdict

**Ready to promote.** What it brings held, and nothing that worked
before moved.

- **HAProxy 3.4.7** on the lab's nodes, the branch's two high
  vulnerabilities fixed and a third in 3.4. 3.2.26 and 3.0.30 passed
  CI's per-branch tests. Throughput, failovers and reboots are the same
  as with 3.4.6.
- **The OOM order** ([#111](https://github.com/swenske/Janus/pull/111))
  on the lab's nodes:
  - janusd -900, HAProxy -500, bird and both keepalived processes -300,
    node_exporter and the guest agent 0, read back from `/proc`;
  - the configuration HAProxy can't fit in 1 GiB, applied four times:
    HAProxy killed - twice the serving one with the new one - and
    started again in 1 to 2 s; janusd never.

  The same morning, on v2026.10.14-6, the kernel had taken janusd on the
  same machine, in the same kind of test.

Everything else matched v2026.10.15:
- the Controller's update;
- the rolling update under load;
- failovers, reboots and rollbacks;
- throughput;
- SELinux enforcing with no denial, CIS 33/33.

Found on the way, not a regression: **the anycast address loses 0 to 3
requests when HAProxy stops and starts on a node** (the route
withdrawn, then back).
- The first runs here lost 3, 3 and 1, against 0 and 0 with the node
  rolled back to v2026.10.15.
- Four more runs of each:

  | Node on | Requests lost, run by run |
  |---|---|
  | v2026.10.15-2 | 3, 1, 3, 0 |
  | v2026.10.15 | 1, 1, 3, 2 |

- The lab's router dropped what it routes as the route switches. Every
  campaign before measured that one run at a time - 0 or 1.
- HAProxy itself was ruled out: 3.4.6 and 3.4.7 both answer HTTP within
  0.5 ms of their stats socket, over 20 starts each.

What the pre-release brings: v2026.10.15, plus HAProxy 3.4.7, 3.2.26 and
3.0.30 (🔒) and the OOM order -
[its notes](https://github.com/swenske/Janus/releases/tag/v2026.10.15-2).

### The OOM order

On both nodes, every process janusd's Processes lists:

| Process | `oom_score_adj` |
|---|---|
| janusd | -900 |
| HAProxy | -500 |
| bird | -300 |
| keepalived, both its processes | -300 |
| node_exporter, the guest agent | 0 |
| the kernel's threads | 0 (the OOM killer never picks them) |

On the auto-scaled machine (1 GiB, no auto-scaling policy, updated to
v2026.10.15-2 through the Controller in 12 s), the three-cache
configuration was applied four times:

| Try | What the kernel killed | Serving again |
|---|---|---|
| 1 | the new HAProxy, then the serving one - started again by janusd after 1 s | 1.8 s after the apply |
| 2 | the same - started again after 2 s | 2.8 s |
| 3 | the new HAProxy only - refused, the serving one went on | 0.6 s |
| 4 | the same | 0.7 s |

janusd was never killed. The same machine's event log shows the kernel
killing janusd at 08:51 that morning, on v2026.10.14-6, in the
auto-scaling put-back test - the case #111 fixes.
