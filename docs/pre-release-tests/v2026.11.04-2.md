Tested on 2026-11-04, the hour it came out, on the lab where
v2026.11.04 was measured the same afternoon
([v2026.11.04's report](v2026.11.04.md)). What this pre-release
changes:

  ([#531](https://github.com/swenske/Janus/pull/531)), browsers'

## Verdict

**Everything this pre-release brings works on the lab, and the
baseline holds. My opinion: ready to promote, once the release notes
say how the updater gets its fix** ([finding 1](#findings)). The
decision is yours.

- **The Content Security Policy** (#531) is the blocking header on the
  page, the API, every node's page and the node app, with
  `report-uri /csp-report`, no report-only header left. Sixteen pages
  walked in the pinned Chromium, light and dark - the Controller's

  Traffic flow, another's Overview and Update: **no console error, no

  Controller's log meanwhile. A script injected into the page and into
  a node page - inline, and from a public CDN - **ran nowhere**, and

  **v2026.11.04 as the latest**, the pre-release offered apart, **no

  (12.16 s yesterday: two set-asides to back up now, five then).
- **A new machine** (#523) was ready in **12 s**; `GET /api/fleet`
  said `waiting` - "joining the fleet…" - for 15.0 s, then `trusted`:

## CPU mitigations (#498)

The x86 kernels are built without `CONFIG_CPU_MITIGATIONS` (the
2026-10-07 security review's #1, open). To put figures on the choice:
the default track's kernel built with it, everything else the
pre-release's own bytes, measured against the pre-release on one node.

**The two kernels.** Linux 7.2.15 from the committed
`janus_stable_defconfig` with only `CONFIG_CPU_MITIGATIONS=y` (through
kbuild: `make kernel-build-stable`); kbuild turned on its default
`MITIGATION_*` options - page table isolation, retpolines, return
thunks, untrained returns, call depth tracking, IBPB and IBRS on entry,
SRSO, GDS, RFDS, Spectre-BHI, MDS, TAA, MMIO stale data, L1TF,
Retbleed, Spectre v1 and v2, SRBDS, SSB, ITS, TSA - all but straight
line speculation (off by default). The resolved configuration differs
from the committed one by those options and what they select (call
thunks and padding), nothing else. Its `bzImage` is 8.06 MB, 0.9 MB more
than the release's.

**The bundle.** The default schematic built by `image/schematic/build.sh`
from v2026.11.04-2's published inputs, the stable kernel replaced by
this one: **`rootfs.squashfs` and `rootfs.verity` the same bytes as the
release's**; only the two UKIs differ - the kernel, and unsigned.

**The node.** A machine the Controller made from the pre-release's
image: 2 vCPU (host-passthrough: the guest sees the host's Xeon
E3-1220 v3, Haswell, 4 cores without SMT; the host's microcode 0x28),
1 GiB, on the first host. The hypervisor runs Debian 13's kernel with
its own mitigations. HAProxy answering on the node itself - `:80` in
plain HTTP, `:443` the same over TLS (ECDSA P-256, a full handshake per
connection with `Connection: close`) - so the load measures the node,
not the backends. A = the pre-release (slot A); B = the mitigated
bundle, uploaded and installed with `-insecure-skip-signature-check`
(slot B); then rolled back to A, then to B: **two passes of each, two
rounds each**, from a runner and, for the multi-client run, the three
runners and the build box.

Read with the node's state: under keep-alive the node's two vCPUs are
saturated (about 2 s idle out of 60), so the extra CPU per request
becomes lost throughput one for one - about 10 %. A new connection per
request leaves the node half idle (latency-bound on the client's side):
the rate barely moves, but each connection costs **16 % more CPU** -
headroom a busier node would lose. A TLS handshake is mostly user-space
cryptography (two thirds of its CPU), which the mitigations don't touch:
4 to 5 %. The cost lands on every kernel entry and exit - system and
interrupt time +10 to 16 % - and on user time too (+16 % under
keep-alive, +30 % for a new connection), the cache and TLB lost at each
page-table switch and buffer clear. Each mitigation's share wasn't
isolated: the kernel's command line is in the signed UKI, so turning
them off one by one means a kernel image each.

The spread between two passes of the same kernel is up to 5 % (116 k
then 111 k without); under keep-alive every round of the mitigated
kernel stayed below every round of the release, while a new connection
per request overlaps within that spread.

### Who is exposed without them

- **The node's own kernel and processes, from code running on the
  node.** That's what the guest's mitigations stand for - its log says
  so: "attack vectors: user_kernel, user_user". A Janus node runs no
  one else's code, but HAProxy parses the internet's input, and
  janusd's extensions (BIRD, keepalived, Consul) talk to the network:
  code execution in one of them - in HAProxy's chroot as uid 1000,
  under SELinux - could, without PTI, read kernel memory (Meltdown),
  and without the MDS clears and retpolines leak data from the kernel
  or from other processes. On the node that means its TLS private keys,
  its CA key, the fleet credentials janusd holds. The mitigations
  turn a remote code execution in HAProxy from "everything on the
  node" back into what SELinux and the chroot leave it.
- **Neighbouring guests on the same host**: crossing between virtual
  machines is the hypervisor's job - flushing buffers and predictors
  when it switches from one guest to another - and the lab's hosts do
  it (Debian's kernel: MDS clears, conditional L1D flushes, IBPB). A
  guest's own mitigations don't protect it from a neighbour, and their
  absence doesn't expose a neighbour more, as long as the host is
  mitigated. On a CPU with SMT on and two guests' vCPUs on sibling
  threads at the same time, no guest kernel setting closes that: it
  takes SMT off or core scheduling on the host. The E3-1220 v3 has no
  SMT.
- **What a node's operator can't do**: the command line is signed, so
  `mitigations=auto` can't be added to today's kernel - with nothing
  compiled in it would turn nothing on anyway - and with the
  mitigations built in, `mitigations=off` couldn't be passed either:
  the build decides for every node.

### My reading

About **10 % of throughput when a node is CPU-bound on keep-alive
traffic, 16 % more CPU per new connection, 4 % on TLS handshakes,
nothing on the boot**, measured on 2013-era Haswell cores - the CPU
where PTI and the MDS clears cost the most; most newer cores aren't
affected by Meltdown or MDS in hardware and pay less. The gain is
defence in depth for the node's secrets against a compromised HAProxy;
the neighbours on a host depend on the hypervisor either way. My
opinion: turn them on - the review rated it high, and the cost is a
tenth of a saturated node's throughput - but the decision is yours. The longterm track wasn't measured; it would get the same
options.

## Findings

1. **The updater doesn't get its fix from an update.** The notes say,
   under 🔒 Security: "Update the Controller - its updater comes with
   it." It doesn't: the updater recreates only the Controller's service
   (`docker compose up --no-deps`), and its own container keeps the
   image it started with - on the lab, v2026.10.07-3 with Compose
   v5.6.0, the critical and high vulnerabilities this release fixes,
   after the update to v2026.11.04-2. The README says it ("the next
   `docker compose up -d` gives it the new one"); `docker compose up -d`
   did, Compose v5.7.0, the Controller untouched. The notes should say
   to run `docker compose up -d` in the Compose directory after the
   update, before the promotion - the updater has no network of its
   own, so the exposure is small, but the step is the only way to the
   fix.

Also noticed: a new machine now stays joining for 15 s after its
admission (yesterday 1.5 s or none): the fail-fast first try (#524)
waits for #517's 15 s retry. Ready and answering meanwhile, and what
the page says is right; only longer.
