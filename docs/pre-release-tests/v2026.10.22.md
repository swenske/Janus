# v2026.10.22 pre-release tests

Tested on 2026-10-22, late afternoon. It is
[v2026.10.21](v2026.10.21.md) with:

- 🔒 **Docker Compose v5.6.1** in the Controller's image, the updater's:
  five high and two medium vulnerabilities of the Go standard library
  its older build carried ([#212](https://github.com/swenske/Janus/pull/212));
- **Linux 7.2.12** for the default kernel track
  ([#211](https://github.com/swenske/Janus/pull/211)) and **6.18.58**
  for the longterm one, which fixes CVE-2026-46302
  ([#208](https://github.com/swenske/Janus/pull/208));
- a node's page loading the Controller's node app once for every node
  ([#216](https://github.com/swenske/Janus/pull/216)), 1x screenshots in
  the docs ([#217](https://github.com/swenske/Janus/pull/217)), the image
  build's `test-controller` job
  ([#215](https://github.com/swenske/Janus/pull/215)) and incremental
  images ([#218](https://github.com/swenske/Janus/pull/218));
- dependencies: go-jose 4.1.6, React 19.3.1, Playwright 1.64.1,
  Astro 7.4, markdown-it 15.0.3 and Node 24.22.1 for the docs' build,
  OpenTofu 1.13.2.

HAProxy and the extensions are v2026.10.21's. A short campaign, as
for [v2026.10.21](v2026.10.21.md): the update path, the throughput, the
failovers, the longterm machine, and the node pages' shared assets. The
scenarios: [Lab test scenarios](lab-scenarios.md).

## Verdict

**Ready to promote.** Compose v5.6.1 updates the Controller as before
(0.41 s without an answer), the new kernels pass every step - the
update path, the throughput, the failovers, health, CIS, SELinux -, and
the node pages share one cached copy of their code. One reboot of the
update took a minute on one node, before its kernel started, and didn't
happen again in seven more reboots and slot switches of the same node;
7.2.12's kernel stage is 0.6 s longer than 7.2.11's.

### The build's own changes

- **Ten jobs**: Secure Boot and bare metal took 4 min 48 s alone, the
  Controller's three tests 15 min 48 s in their own job - its libvirt
  test 10 min 17 s this time, against 5 min 34 s in v2026.10.21's run.
- **Incremental images**: in the log job, 7 of its 8 image-booting
  steps took the root filesystem and the disk image as they were ("up
  to date", "from the pristine copy"), the first one built them.
- **Not measurable on this run**: both kernel tracks changed, so every
  job built its kernel first (2 to 4.5 minutes on each runner, against
  20 s to 1.5 minutes from the cache in v2026.10.21's run), and the jobs
  landed on other machines; the 72 steps that ran in both builds
  without building a kernel took the same time (median change 0 s).
  The next build without a kernel change will show what the cache and
  the incremental images save.
