# v2026.11.09-2 pre-release tests

Tested on 2026-11-09, the afternoon it came out, on the lab where
v2026.11.09 - the newest release, promoted that morning - was measured
again first as the baseline ([v2026.11.09's report](v2026.11.09.md)).
What the pre-release brings:

- **CPU_FREQ's core back in the kernel, without a driver** (#607), on
  both tracks: v2026.11.09's virtual-machine kernel printed a CPUfreq
  warning at every boot;
- **update downloads asked again** when the server doesn't answer
  (#603): no answer, a timeout, 408, 429 or a 5xx gateway error, 5, 15,
  30 and 60 seconds later, each try shown; a 404 stays final;
- **the follow-ups of v2026.11.09's campaign** (#606): the hardware
  check reads an NVMe boot disk by its own name, a hardware refusal
  names janusctl's `-allow-unsupported-hardware`, a node too old for
  clusters is in none (no more 501 on its pages), node_exporter's
  `cpufreq` and `thermal_zone` collectors no longer offered.

The core campaign ran in full, v2026.11.09 measured the same way the
same afternoon: the Controller's update, the image factory, the cluster
updated in place under load, failovers, janusd restarted, HAProxy
reloaded under load, rollbacks, HAProxy's throughput and three A/B
series by rollbacks, the boot stages on both kernel tracks with each
boot's console read, every kind of machine's kernel log before and
after, the nodes' health, hot-plug through auto-scaling, every
extension, the Controller's pages. Then the pre-release's own changes on
real nodes: updates through a server answering 504, a 404, the hardware
refusal's new message.

The load and the probes came from the build box and one CI runner;
every throughput figure is compared with v2026.11.09 measured the same
afternoon from the same client.

## Verdict

**What the pre-release changes works on real nodes: the CPUfreq warning
is gone from every kind of machine on both tracks, with no new cpufreq
line and the same boot times; a node on the pre-release asks a file
again after a 504 and says so, a 404 still stops it at once; the
hardware refusal names janusctl's flag; the old node's page no longer
fails a request; node_exporter keeps a node's settings without the two
collectors. The core campaign is as before: zero AVC denials, no oops,
CIS 33/33 everywhere, the cluster's in-place update without a lost
request (VIP 0 of 3,301, anycast 0 of 3,298), the failovers, reboots
and rollbacks as before. My opinion: ready to promote** - with
finding 1 to weigh, a small CPU cost per keep-alive request that three
A/B series all show. The decision is yours.

- **The retries, on a real node** (#603): from a server that answers
  504 to the first request for each file, a node on the pre-release
  printed `GET …/uki-a.efi: unexpected status 504 Gateway Timeout -
  trying again in 5s (2/5)`, then the same for `rootfs.verity` and
  `rootfs.squashfs`, each asked again 5.0 s later and served, and
  updated; v2026.11.09 on the same server stopped at the first 504. A
  404: refused in 4 ms, one request.
- **The Controller's Update page doesn't show the retries** (finding
  2): it relays only the update's last message, so its "the node
  downloads it" mode waits in silence while the node retries (up to
  about two minutes a file). janusctl shows them, and janusd's log keeps
  them.
- **The CPUfreq warning is gone** (#607): six boots of node 02 printed
  it on v2026.11.09, none on the pre-release; the same on the longterm
  machine, the Let's Encrypt machine, a default Controller machine and a
  machine with Proxmox's default devices. No new cpufreq line, none at a
  CPU hot-add; `/sys/devices/system/cpu/cpufreq` is there and empty (no
  driver, no policy).
- **The hardware refusal's message** (#606) can't come from a vmxnet3
  machine any more (v2026.11.09's kernel has no driver for it, so its
  cards are never bound - the machine has no network); shown instead on
  a pre-release node given a lab-built bundle whose `image.json` leaves
  `virtio_net` out: refused, "Only if those devices change before the
  node boots it, janusctl's -allow-unsupported-hardware installs it all
  the same (allow_unsupported_hardware; the Controller's Update page
  doesn't offer it)". A vmxnet3 machine on v2026.11.08-3 still refuses
  the pre-release (with that release's older words).
- **HAProxy costs about 3 % more CPU per keep-alive request** (finding
  1): 38.4 against 37.3 µs over 24 runs by rollbacks, each of the three
  series in the same direction (+3.8, +3.2, +2.4 %); new connections the
  same (184.9 against 185.1 µs); the VIP benchmark, bound by its client,
  the same (−0.1 %).

### The hardware refusal's message (#606)

The brief asked to replay v2026.11.09's vmxnet3 refusal from a machine
made on v2026.11.09. Such a machine has no network: v2026.11.09's kernel
has no vmxnet3 driver, so the cards are never bound ("the stored network
configuration can't apply (… this node has no physical Ethernet
interface)", the `hardware:` line naming the disk alone, the
registration retrying "network is unreachable" forever). A janusd that
has the new message never runs with a vmxnet3 card bound, so that
refusal can't be seen from it. Two things instead:

- **A vmxnet3 machine made on v2026.11.08-3**, updated to the
  pre-release through its node page: **refused in 2.1 s** by
  v2026.11.08-3's janusd ("this release's kernel (virt) has no driver
  for vmxnet3 (backend), vmxnet3 (front), vmxnet3 (mgmt): the node would
  lose those network interfaces. Set allow_unsupported_hardware only
  if…"), no reboot, its other slot marked - the guard holds against the
  pre-release's `image.json`; the words are that release's.
- **The new words, on a pre-release node**: a bundle built in the lab
  from the pre-release's - its root filesystem rebuilt with an
  `image.json` whose `kernel.drivers` leaves `virtio_net` out, its hash
  tree and both UKIs' command lines redone, unsigned -, given with
  `-insecure-skip-signature-check` to the default Controller machine
  (virtio cards): signature skipped, hash tree checked, blocks written,
  then **refused**: "this release's kernel (virt) has no driver for
  virtio_net (backend), virtio_net (front), virtio_net (mgmt): the node
  would lose those network interfaces. Only if those devices change
  before the node boots it, janusctl's -allow-unsupported-hardware
  installs it all the same (allow_unsupported_hardware; the
  Controller's Update page doesn't offer it) - slot A now holds it, and
  Rollback won't switch to it". No reboot, the running slot unchanged,
  the other one marked. The node page's update gives the same message
  (502).

The NVMe fix can't be proven on a release that doesn't boot from NVMe:
its unit tests only.

## Findings

1. **About 3 % more CPU per keep-alive request** - not a blocker in my
   view: three A/B series by rollbacks on node 01, 24 runs, put the
   pre-release at 38.4 µs against 37.3 µs (+3.0 %, −2.7 % req/s),
   spread evenly over user, system and softirq, steal the same; new
   connections cost the same, and the VIP benchmark (bound by its
   client) doesn't see it. HAProxy is the same bytes and the kernel the
   same version; the kernel's change is CPU_FREQ's core. The ranges
   overlap, so it is a small, probable effect, not a proven one; a
   quieter host or more series would settle it.
2. **The Controller's Update page doesn't show the retries**: in "the
   node downloads it" mode, `upgrade-url` (`runUpgrade` in
   `nodeproxy/lifecycle.go`) keeps only the update's last message, and
   `Update.jsx` waits for that JSON - the "trying again" lines reach
   janusctl and janusd's log, not the page, which waits in silence up to
   the retries' 110 s a file. The notes' "each new try shown as the
   update goes" is janusctl's.
3. **One rollback took 43.8 s** instead of 11: the 33 extra seconds were
   between the reset and the kernel (the firmware or the host); not seen
   again in two rollbacks and twelve reboots after it.
4. The brief's vmxnet3 replay can't be done from v2026.11.09 (no
   network on such a machine): the new message shown with a lab-built
   bundle instead (above).
