# v2026.11.08-3 pre-release tests

Tested on 2026-11-08, the evening it came out, on the lab left by
[v2026.11.08-2's campaign](v2026.11.08-2.md). The pre-release replaces
v2026.11.08-2, which wasn't promoted; v2026.11.08 stays the newest
release. What changes since v2026.11.08-2 is the fix of that campaign's
first finding (#596) and its third:

- **a node says what its HAProxy services are named after**
  (`ConsulManagedGetResponse.scope`);
- **the Controller takes `janus-nodes-legacy` off a node's Consul token**
  as soon as the node names its services after its scope, and gives the
  node its layer again, **once**, when the layer lacks the scope;
- **`janusctl network consul managed` prints `Scope:`**, and the
  Controller's **Consul** tab shows each node's `writes haproxy-<scope>-…`
  and a badge on a node still on the older right.

The kernels, the absence of io_uring and the hardware guard are the
same as v2026.11.08-2's - the kernels are the same bytes - so the
throughput, the A/B and the full boot campaign weren't run again. The
campaign replayed the Consul transition in the order the notes give,
then a lighter core campaign. The load and the probes came from the
build box.

## Verdict

**The fix holds on the path that failed in v2026.11.08-2: every node
updated after the Controller lost `janus-nodes-legacy` at the first
Consul pass after its update, was given its layer again exactly once,
and from then on was refused another scope's `haproxy-<other>-x` (403)
and allowed its own (200). No node was pushed a layer pass after pass,
whatever its release. The core campaign is as v2026.11.08-2's: the
cluster updated in place without a lost request (VIP 0 of 3,306,
anycast 0 of 3,305), zero AVC denials, no oops, every node CIS 33/33,
32 pages without a problem. My opinion: ready to promote.** The
decision is yours.

Two observations, not blockers in my view (findings 1 and 2):

- the older right comes off at the **next** Consul pass after the
  node's update: right away for a cluster member and for a machine
  updated by the Controller (both run a pass when they finish), but up
  to ten minutes for a node updated through its own page or rolled
  back, which don't (8 min 32 s in the lab) - as the notes say ("the
  Controller's next Consul pass"), only longer than one may expect;
- a node **rolled back** to a release before scoped names can't
  register its HAProxy services under their old names until that next
  pass gives the older right back (35 s with **Run now**).

## The Consul transition

### The starting point

The brief asked for the lab's Controller on v2026.11.08 first. It ran
v2026.11.08-2, and **its updater can't go back**: asked for
v2026.11.08, the Controller answers 409 "this Controller already runs
v2026.11.08-2" (it installs the newest release only when it's newer,
or the pre-release on offer). So the campaign started from a
v2026.11.08-2 Controller - the exact state v2026.11.08-2's finding came
from: that Controller gives the nodes on v2026.11.08 a layer with the
scope, which they drop. From a v2026.11.08 Controller the nodes end up
the same once the Controller is updated: its first pass gives them the
scoped layer.

A throwaway Consul server set up as v2026.11.08-2's campaign did (the
extension's version pinned by digest, ACLs denying by default, gossip
encryption, RPC TLS verified both ways, `auto_encrypt`, the HTTP API on
HTTPS only), the Controller's token with the guide's policy (unchanged
since). Three Controller machines on **v2026.11.08** with Consul and
node_exporter: two of them the cluster `kc` (a hosts map, a Host ACL,
HAProxy's Prometheus exporter), the third alone; picked by a label.
Main's `examples/prometheus/consul.yml` in a Prometheus and a blackbox
exporter on the build box (adapted: the lab's Consul, its CA, a
read-only token, every 5 s). The catalog read every second; each
node's release, the Controller's view of it (`legacy`) and its token's
policies read every second too.

When its Consul settings were saved again, the Controller deleted the
tokens v2026.11.08-2's campaign had left behind (its finding 5) - by
itself, on its first pass.

## Findings

1. **The older right comes off at the next Consul pass, and a node
   updated through its page waits for the periodic one.** A cluster's
   update and a machine's update by the Controller run a Consul pass
   when they end; an update through the node's page
   (`/api/lifecycle/upgrade-url`) and a rollback with janusctl don't
   (nothing pokes the Consul loop on those paths), so the node keeps
   `janus-nodes-legacy` up to ten minutes (8 min 32 s in the lab).
   What the notes say - "the Controller's next Consul pass" - only
   longer than one may expect. Not a blocker in my view: nothing is
   worse than before the update; **Run now** clears it at once. A poke
   when the node's page sees the node back on a new release would make
   it immediate.
2. **A node rolled back to a release before scoped names can't register
   its HAProxy services until the next pass.** Its token no longer has
   the older right, the rolled-back node names its services the old
   way, the agent is refused until the Controller gives the right back
   (35 s with Run now, up to ten minutes otherwise). The other services
   (`janus`, the exporters) stay. Expected from the design (the right
   follows the release); worth a line in the guide, or the same poke as
   above.
