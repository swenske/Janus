# v2026.10.23-2 pre-release tests

Tested on 2026-10-23, in the evening. It is [v2026.10.23](v2026.10.23.md)
with:

- **Let's Encrypt for nodes without the internet**
  ([#249](https://github.com/swenske/Janus/pull/249)): each node chooses
  how it reaches the CA - directly, through an HTTP(S) proxy, through the
  Controller's relay, or not at all, the Controller ordering its
  certificates - and the Controller has a Let's Encrypt tab for the relay
  and the ordering;
- **a reboot's line shipped before the reboot**, and the sockets table
  reachable with the keyboard
  ([#248](https://github.com/swenske/Janus/pull/248)) - the two findings
  of [v2026.10.23's campaign](v2026.10.23.md).

The same kernel, HAProxy and extensions as v2026.10.23. The campaign of
[v2026.10.23](v2026.10.23.md) - the update path, the throughput, the
failovers, the reboots, the longterm machine - plus what this one adds:
a new machine with the Let's Encrypt extension taken through every way

[Lab test scenarios](lab-scenarios.md).

## Verdict

**Ready to promote.** The Controller and the nodes update as before -
both nodes back in service 16 s after their drain, the throughput level
with the release's. Every way to the CA worked on a real node that can't
reach the internet: through the proxy (asking for its password) and
through the Controller's relay, Let's Encrypt's own directory answered;
a private CA issued an HTTP-01 certificate and a wildcard over DNS-01
through the proxy, then through the relay, then ordered by the
Controller - zero AVC denials. Every reboot's timing line reached the log
server this time. Four findings, none blocking: a DNS provider's API
reached over plain `http://` can't go through the relay (it tunnels
HTTPS only - the docs say so now), the relay doesn't list such a refusal
in its journal, the Controller's list of ordered certificates shows a
renewal still asked for until its next pass, and one log line reads
oddly.

### Let's Encrypt without the internet

A machine the lab's Controller created for it, from the pre-release with
the Let's Encrypt extension - ready 76 s after the call, 62 s of which

page on the Controller, as an operator would: it has no credentials of

The setting:

- **its internet cut**: the lab's router rejects its new connections to
  anything outside the lab - directly, Let's Encrypt's directory gives
  `network is unreachable`;
- **a proxy**: Squid 6.13 on a lab machine, asking for a username and
  password, open to the lab's networks only;
- **a private CA**: Pebble on a machine outside the lab, reachable from
  inside only on the Controller's own host - through a tunnel - so that
  the node can never reach it directly, while the proxy and the
  Controller can; Pebble validates HTTP-01 on the node's port 80, and
  its DNS test server answers DNS-01 (an `httpreq` DNS provider in front
  of it).

fetched each way):

| Way | Let's Encrypt's directory | The private CA |
|---|---|---|
| Directly | failed: network is unreachable | failed: connection refused |
| The proxy without its password | failed: Proxy Authentication Required | - |
| The proxy with its password | reached in 417 ms | reached in 10 ms |
| The relay (once turned on) | reached in 419 ms | reached in 13 ms |

| Way | What happened |

## Findings

1. **A DNS provider's API over plain `http://` can't go through the
   relay**: the relay only tunnels (CONNECT), so `httpreq` or `pdns`
   pointed at an `http://` URL fails through it, with the relay's 405 in
   the certificate's status. Expected from the design; the docs now say
   that an API through the relay must be HTTPS. A proxy carries it.
2. **The relay doesn't journal that refusal**: a plain-HTTP request is
   refused before it's recorded, so the tab's recent tunnels don't show
   it - only the node's status does. To record it, in the next release.
3. **The Controller's ordered certificates show "renewal asked" after
   the order**, until its next pass (10 minutes): the list keeps what the
   node said before the order. To refresh it from the installed
   certificate, in the next release.
4. **One log line reads oddly**: choosing "Ordered by the Controller"
   logs `the CA is reached not at all: the Controller orders the
   certificates from now on`. To reword, in the next release.
