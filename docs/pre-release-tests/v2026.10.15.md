# v2026.10.15 pre-release tests

Tested on 2026-10-15, right after it was cut: the CI run that built it,
then the lab. The figures to compare with are
[v2026.10.14-6's campaign](v2026.10.14-6.md), measured the same morning
with the same clients and the same scripts.
The scenarios: [Lab test scenarios](lab-scenarios.md).

## Verdict

**Ready to promote.** The fix this pre-release brings held, and nothing
that worked before moved.

**An image with every extension fits the update slots again** (the
fix it brings, [#102](https://github.com/swenske/Janus/pull/102): 1 MiB
squashfs blocks).
- The image factory built it for v2026.10.15. For v2026.10.14-6 it
  couldn't: 64.26 MiB, over the 64 MiB slots.
- The lab's Controller created a machine from it, which booted and
  served: the seven extensions installed, the services without a
  configuration waiting, no denial.
- The nodes on v2026.10.14-6 read the new image like any other, before
  installing it and as their other slot.
- Boot time didn't move.

| Image | v2026.10.14-6 | v2026.10.15 |
|---|---|---|
| `rootfs.squashfs`, the default image | 15.69 MB | 14.78 MB |
| `janus.qcow2` | 53.50 MB | 51.67 MB |
| `janus.iso` | 113.84 MB | 112.00 MB |
| Every extension at once (CI's new check) | 64.26 MiB, refused | 60.09 MiB of the 64 MiB slot |

Everything else matched v2026.10.14-6:
- the Controller's update;
- the rolling update under load (no request lost on the VIP);
- failovers, reboots and rollbacks;
- throughput;
- SELinux enforcing with no denial, CIS 33/33.

What the pre-release brings: v2026.10.14-6 with smaller images -
[its notes](https://github.com/swenske/Janus/releases/tag/v2026.10.15).

## The lab

The same as [v2026.10.14-3's](v2026.10.14-3.md#the-lab): no client of
its own. The fourth machine (not a runner) runs the probes, the
single-client `wrk` runs and the rolling update's load. The four clients
together run the multi-client benchmark.

### The Controller and the image factory

| Step | Result |
|---|---|
| v2026.10.14-6 → v2026.10.15, confirmed, by its updater | updated in 14 s; no answer for **0.30 s** (a probe every 0.1 s from the lab's host), none slower than 0.5 s |
| The bundle of v2026.10.15 for the lab's schematic | ready **54 s** after a node's Update page asked for it |

### A machine with every extension

The lab's Controller was asked for a machine of v2026.10.15 with the
seven extensions: bird, consul, keepalived, letsencrypt, nftables,
prometheus-node-exporter and qemu-guest-agent. That is the schematic
the factory couldn't build for v2026.10.14-6.

| Step | Result |
|---|---|
| The image factory built it | 63 s |
| The machine, from the request to its node answering the Controller | 76 s |
| What the node says | v2026.10.15, the schematic with the seven extensions, the same in its other slot |
| Its services | janusd, HAProxy, the node exporter and the guest agent running and healthy; bird, consul and keepalived waiting for a configuration, as designed |
| SELinux | no denial reported |

The machine was then destroyed.

The auto-scaled machine was updated to v2026.10.15 through the
Controller: 12 s, the version read back from the node.

### The nodes' health, on v2026.10.15

Both nodes:

- v2026.10.15, kernel 7.2.10 (stable track), HAProxy 3.4.6, BIRD 2.20.0,
  the lab's schematic; the other slot v2026.10.14-6.
- Services: janusd, haproxy, bird, keepalived, prometheus-node-exporter,
  qemu-guest-agent - all running and healthy.
- SELinux enforcing, **0** AVC denials; **0** OOM kills.
- CIS Debian Linux 13 Benchmark v1.0.0 (Level 2 - Server): **33/33**
  controls compliant.
