# v2026.10.16 pre-release tests

Tested on the morning of 2026-10-16, right after it was cut: the CI runs
that built it, then the lab. The figures to compare with are v2026.10.15-2's,
measured the same morning on the lab's nodes before they were updated -
the same clients and the same scripts as [its campaign](v2026.10.15-2.md).
What log forwarding costs was measured the evening before on a node of the
branch: [the guide's "What it costs"](../guide/log-forwarding.md#what-it-costs).
The scenarios: [Lab test scenarios](lab-scenarios.md).

## Verdict

**Not ready to promote: v2026.10.16-2 instead.** Everything that worked
before still does, and what v2026.10.16 brings works - except one thing
the lab found:

- **A node without the LOGS partition sent 9 of a boot's ~700 kernel
  messages**, and one boot sent 243 of them under its DHCP address
  instead of its hostname. That is every node updated from an older
  release. janusd followed the kernel's log before it read its saved
  forwarding configuration - the firewall and the extensions start in
  between on such a node - and the shipper dropped what came before it
  had targets; it also applied the configuration before the hostname was
  set. Nothing was lost on a node with LOGS (its targets read the
  partition back).
- **Fixed in [#121](https://github.com/swenske/Janus/pull/121)**: what's
  offered before the first configuration waits for it (8,192 records),
  and janusd reads the configuration once the network and hostname are
  the node's. Proven on the lab: node 02 on that build sent **707 kernel
  messages a boot, twice, all under its name**. CI gets a regression test
  and a run of the forwarding test on a node without LOGS.

What held, on real nodes:

- **Log forwarding from the Controller**: a fleet profile (the bench's
  Elasticsearch and its Logstash over TLS) applied to both nodes in
  seconds, kept applied, `managed by` shown on each node; the older nodes
  said *unsupported - update it*. The Controller's own log and audit, the
  nodes' events, audit and janusd's log reached Elasticsearch.
- **The LOGS partition on a new machine**: the Controller created one from
  v2026.10.16's image - ready in 9 s - with its 512 MiB partition, picked
  by the profile at admission; after a reboot it listed both boots and
  sent its boot's 605 kernel messages. An updated node says it keeps its
  logs in memory.
- Everything else matched v2026.10.15-2: the Controller's update, the
  rolling update under load, failovers, reboots and rollbacks,
  throughput with forwarding on, SELinux enforcing with no denial, CIS
  33/33.

What the pre-release brings: log forwarding (syslog and Elasticsearch,
the audit included), the LOGS partition, the node's audit, fleet
profiles, and HAProxy's `log stdout` lines no longer lost -
[its notes](https://github.com/swenske/Janus/releases/tag/v2026.10.16).

## CI: image-build

The first run, [38853681301](https://github.com/swenske/Janus/actions/runs/38853681301),
failed in *The LOGS partition keeps the logs across reboots*: the job's
earlier tests boot the shared disk image itself, so its LOGS partition
already held their boots when the test expected a first one. A test
problem, fixed by [#120](https://github.com/swenske/Janus/pull/120) (the
test blanks the partition in its copy); every other test job had passed.

## The lab

The same as [v2026.10.15-2's](v2026.10.15-2.md#the-lab). The log servers:
a single-node Elasticsearch 9.5 (2 CPUs) and a Logstash (1 CPU) on a
Docker host of the home network, behind its reverse proxy (an internal
CA) - the nodes reach them through the lab's routers.

### The Controller and the image factory

| Step | v2026.10.15-2 | v2026.10.16 |
|---|---|---|
| The Controller's update by its updater | 14 s, no answer for 0.30 s | 14 s, no answer for **0.41 s** (a probe every 0.1 s), none slower than 0.5 s |
| The bundle for the lab's schematic | ready 48 s after a node's Update page asked | ready **47 s** after |
| A machine created by the Controller from the release's image | - | **ready in 9 s** (the image downloaded, sent to the host, the node registered and admitted) |

### Rolling update under load

| | v2026.10.15 → -2 | v2026.10.15-2 → v2026.10.16 |
|---|---|---|
| VIP | 1 lost (0.05 s) / 2,759 | 1 lost (0.05 s) / 1,664 |
| Anycast | 0 lost / 2,759 | 3 lost, one at a time (0.05 s each) / 1,664 |
| Each node, from Upgrade to back in service | 13.2 s and 13.3 s | 13.3 s and 14.2 s |
| `wrk` | 13,028 req/s, 99th percentile 5.61 ms (2.5 min) | 12,483 req/s, 99th percentile 31.51 ms (1.5 min) |

The anycast's three single requests: two as its route moved from one
node to the other, one 30 s after the second node came back - the lab's
router as the route switches, what v2026.10.15-2's campaign measured
run after run (0 to 3).
