# v2026.10.14-5 pre-release tests

Tested on the night of 2026-10-14, right after it was cut: the CI run
that built it, then the lab. The figures to compare with are
[v2026.10.14-4's campaign](v2026.10.14-4.md), measured a few hours
before with the same clients and the same scripts.
The scenarios: [Lab test scenarios](lab-scenarios.md).

## Verdict

**Not promoted.** The fix this pre-release brings held, and nothing that
worked before moved, but the campaign found an auto-scaling defect worth
a v2026.10.14-6.

**An OOM kill counted once** (the fix it brings,
[#95](https://github.com/swenske/Janus/pull/95)). Tested on the
auto-scaled machine:

1. Auto-scaling on, an OOM kill: memory up.
2. Paused: back to the machine's size.
3. On again: 2 minutes without a step.

v2026.10.14-4 added memory again at once, for the kill it had already
answered.

Everything else matched v2026.10.14-4:
- the Controller's update;
- the rolling update under load (no request lost on the VIP);
- failovers, reboots and rollbacks;
- throughput;
- SELinux enforcing with no denial, CIS 33/33.

Found on the way:

1. **The kernel parameters stayed raised when HAProxy couldn't run at
   the machine's size.** A configuration needing the memory auto-scaling
   gave it ran there, until auto-scaling was paused and its policy
   removed. Back at 1 GiB, HAProxy couldn't run. Auto-scaling confirmed
   the parameters going back only once HAProxy answered, which never
   happened. The node took them back, and `tcp_mem` stayed sized for
   2 GiB on 1 GiB. The policy's removal also forgot what they had been:
   the next policy took the raised values for the machine's own. Fixed
   in [#98](https://github.com/swenske/Janus/pull/98), for
   v2026.10.14-6.
2. **The node kept answering while janusd had no HAProxy running.** In
   the same run, janusd started HAProxy again after each OOM kill
   ([#89](https://github.com/swenske/Janus/pull/89)), and each new
   process was killed within a second. For three stretches of 16 to 60
   seconds, no HAProxy janusd knew of was alive, yet the probes on the
   node's HTTP port were answered. The process that served before the
   first reload of that boot never reported its exit. Most likely it
   kept serving, unknown to janusd, until the machine restarted.
   **Not reproduced**: the configuration was refused at its start in
   every later try, and the faster path in a container didn't reach it
   either. To investigate.
3. **janusd was killed by the kernel once**, at 1 GiB with that
   configuration, while the OOM killer was also taking HAProxy. init
   started it again at once. Nothing protects janusd from the OOM killer
   today: to look at.

What the pre-release brings: v2026.10.14-4, plus an OOM kill counted once
across a new mode -
[its notes](https://github.com/swenske/Janus/releases/tag/v2026.10.14-5).

### Auto-scaling: an OOM kill counted once

The setup:
- the machine v2026.10.14-4's campaign created: 2 vCPU and 1 GiB, room
  for 4 vCPU and 2 GiB, HAProxy answering by itself;
- updated to v2026.10.14-5 through the Controller first: 13 s, the
  version read back from the node afterwards;
- probes on its HTTP port throughout.

Two runs, the second one built to isolate the fix.

**The clean run**, the three-cache configuration refused at its start
(the OOM kill answered, nothing more):

| Step | What happened |
|---|---|
| A policy (on, up to 4 vCPU and 2 GiB, the kernel parameters following) | the one restart: HTTP unanswered 7.0 s |
| An OOM kill (the three-cache configuration, refused) | 1024 → 1280 MiB, *the kernel killed a process for lack of memory (1 since boot)*; the parameters set for 1280 MiB |
| The usual configuration applied again | no kill after it |
| **Paused** | back to 1024 MiB in 16 s, the parameters going back with it - to what the policy had found (below) |
| **On again** | **2 minutes at 1024 MiB, no step**: the kill had been answered before the pause |
| The policy removed | the restart: HTTP unanswered 6.9 s |

The pause put the parameters back to what the policy had found when it
was set: the values the first run (below) had left raised. The policy
took them for the machine's own. They were reset by hand afterwards.

**The first run** - the same steps, but the three-cache configuration was
accepted this time:
- janusd started HAProxy again after each OOM kill
  ([#89](https://github.com/swenske/Janus/pull/89)), and the kernel killed
  it again and again - eight kills before it fit;
- auto-scaling followed, each step for a new kill: 1024 → 1280 → 1664 MiB;
- paused, then on again: 1024 → 1280 → 1664 → 2048 MiB, for kills 6, 7
  and 8, each after the previous step. Kill 6 came while it was paused,
  and counts once it resumes, as designed;
- at 2048 MiB the configuration fit, and HAProxy ran.

Then the defect:
- **Paused**: back to 1024 MiB, where that configuration can't run.
- The parameters going back were put on trial: *on trial, but the node or
  HAProxy stopped answering*. The node took them back 2 minutes later.
- **Policy removed**: the same, then the restart. `tcp_mem` 23052 30739
  46105 and `fs.file-max` 188700 at 1 GiB, against 11649 15532 23298 and
  95654 at its boot.

[#98](https://github.com/swenske/Janus/pull/98) confirms the values going
back once the node answers, whether HAProxy does or not. The values
it doesn't manage to put back stay recorded after the policy's
removal, for a later policy.

During that run, between the policy's restart and its removal, the
probes were answered throughout: 10,408 of 10,416. Yet janusd's events
show no HAProxy of its own alive for three stretches of 16 to 60 s. This is the open
question in the verdict. After the removal's restart, the configuration
couldn't run at 1 GiB and the node stopped answering until it was
replaced by the usual one. The kernel took janusd once then, and init
started it again.
