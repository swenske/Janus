# v2026.10.18-3 pre-release tests

Tested on the evening of 2026-10-18, right after it was cut. It is
[v2026.10.18-2](v2026.10.18-2.md) with the fix for the defect its lab
campaign found: a connectivity test given a source address couldn't
resolve a name on an enforcing node
([#158](https://github.com/swenske/Janus/pull/158), one SELinux rule).
Two test scripts were also made reliable
([#165](https://github.com/swenske/Janus/pull/165)). Nothing else changed:
the nodes, the Controller and janusctl are v2026.10.18-2's code.

This is a short check, not a full campaign: the update steps, the fix
itself on both nodes, and the nodes' health. The failovers, reboots,
rollbacks and throughput of [v2026.10.18-2's campaign](v2026.10.18-2.md)
stand for this one. The scenarios: [Lab test scenarios](lab-scenarios.md).

## Verdict

**Ready to promote.**

- **The fix works on the lab's nodes**: from each node's own address and
  from the VIP, `dns`, `http` and `tls` to a name pass. AVC denials: **0**
  on both nodes before and after, against 8 on node 01 for the same tests
  on v2026.10.18-2.
- **Nothing else moved**: the Controller's update, the image factory, the
  rolling update under load and the longterm machine match
  v2026.10.18-2.
- It carries v2026.10.18-2's 🔒 JANUS-2026-006 (medium).

### The fix

The tests of v2026.10.18-2's campaign that failed, and those around
them, from the VIP's node and the other:

| Test | Source | Result |
|---|---|---|
| `dns` to the project's site, then `http` to it over HTTPS | each node's own address | ✅ both nodes: the name resolved, HTTP/2 200, the chain verified |
| `dns`, `http`, `tls` to the project's site; `tcp` to a public resolver | the VIP, on the node holding it | ✅ all four |
| `dns`, through the Controller (the node page's route) | the VIP's node's own address | ✅ the steps streamed, then `done` |
| `dns` | the VIP, on the node that doesn't hold it | refused, **InvalidArgument** |
| `ping` | an address the node doesn't have | refused, **InvalidArgument** |
| AVC denials | - | **0** on both nodes, before and after |

**The anycast address**: answers to it come back to the node the router
sends it to, as the connectivity test's page now says:
- from node 01, which carried the route: `tcp` and `dns` to a public
  resolver passed;
- from node 02: both timed out.

One lab detail went the other way: a DNS query to the lab's resolver,
which is the router itself, timed out from node 01 and was answered on
node 02. The router's own answers to the anycast address took another
path than the traffic it forwards. The nodes' reverse-path filter
dropped nothing: its counter stayed at 0 through these tests.
