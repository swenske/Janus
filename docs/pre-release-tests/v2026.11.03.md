# v2026.11.03 pre-release tests

Tested on 2026-11-03, the hour it came out, on the lab where
v2026.11.02-2 was measured the day before
([#481](https://github.com/swenske/Janus/pull/481)). What this
pre-release changes:

- **an update is checked block by block as it is written**
  ([#492](https://github.com/swenske/Janus/pull/492),
  [#506](https://github.com/swenske/Janus/pull/506), 🔒 JANUS-2026-007):
  `rootfs.verity` against the root hash the signed kernel image pins,
  then each block of `rootfs.squashfs` before it goes into the slot,
  streamed - the squashfs is no longer held in memory; `Rollback` checks
  the slot it goes to; one operation on the slots at a time;
- **128 MiB slots for new disks** (#506) - older disks keep their 64 MiB
  ones, `janusctl version` says `Slot size`, a release too big for a
  slot is refused before anything is written;
- **an upload goes straight into the inactive slot** (`upload-release`
  and the Controller pushing a bundle), with a `size` that refuses a
  file too big for the slot first;
- **the release catalog weighs each part of an image** and the public
  builder shows a meter ([#507](https://github.com/swenske/Janus/pull/507));
- node_exporter without its debug information
  ([#505](https://github.com/swenske/Janus/pull/505)).

The campaign: the usual steps (the Controller's update, the image
factory, the cluster updated in place under load and once with the
handoff, failovers, firmware and kexec reboots, rollbacks, HAProxy's
throughput and CPU cost against v2026.11.02-2, the nodes' health, the
pages), then this release's own: the update path on the 64 MiB nodes
written by each release (A), damaged and mixed bundles (B), a recycle
onto 128 MiB slots (C), a new machine (D), the catalog and the builder
(E).

## Verdict

**Everything this pre-release brings works on the lab, and the
baseline holds. My opinion: ready to promote** - with the release
notes' disk size corrected (finding 1), which is text, not the build.
The decision is yours.

- **The update path** (A): the update that brings v2026.11.03 is written
  by v2026.11.02-2, as the notes say - janusd's memory grew by 58 MiB
  for it. Once on v2026.11.03, an update by URL grew janusd by **7 MiB**
  (+6.7 MiB of anonymous memory against +62 before), in the same time:
  0.91 s from the call to the reboot (1.02 s before). The Controller's
  relay says "checking the rootfs.squashfs uploaded into slot B ...
  against the hash tree" and takes the same time. Both 64 MiB nodes say
  `Slot size: 64 MiB`.
- **A damaged bundle** (B): one byte changed at 2 MiB, its `.sha256`
  made to match - refused at "block 512 (byte 2097152)", the node
  serving throughout, `version` saying the other slot "holds part of an
  update that was refused", **Rollback refused** ("would leave the node
  unable to boot"), a sound bundle repairing it. **A mixed bundle**
  (v2026.11.03's kernel images, v2026.11.02-2's root filesystem):
  refused, "nothing was written", the other slot intact, **Rollback
  accepted**. A 70 MiB file refused before anything was written; two
  uploads at once, the second refused.
- **The recycle onto 128 MiB slots** (C): a member of a cluster of the
  Controller's machines on v2026.11.02-2 recycled with the pre-release,
  under load: 12.5 s, the newcomer **`Slot size: 128 MiB`**, its stick
  table equal to the other member's (every request counted), the VIP
  moved once. A **new machine** (D): ready in 16 s, 128 MiB slots, zero
  AVC denials, CIS 33/33.
- **The catalog and the builder** (E): base + HAProxy 3.4 = **exactly**
  the release's `rootfs.squashfs`; for the image with every extension
  the catalog's sum is within 0.06 % of the image the factory built
  (57.8 MiB, as the notes say); the builder shows each extension's
  weight and "about 57.8 MiB of the 128 MiB slot", no console error.
- The cluster updated in place onto the pre-release in **35.3 s, no
  probe lost**; the handoff kept **419 long connections out of 419**;
  failovers, reboots under load, rollbacks and boot stages as before;
  zero AVC denials, no OOM kill, no oops, enforcing, CIS 33/33 on five
  nodes; the pages axe-clean.

Two things to know, neither a reason to wait in my view: new disks are
**970 MiB, not 1.2 GiB** (finding 1); and node 01's CPU per new
connection came out 2.4 % higher on v2026.11.03 in three runs of three,
although the kernel, HAProxy, BIRD, keepalived and nftables are the
same bytes in both releases ([HAProxy's CPU cost](#the-baseline)).

## Findings

1. **The release notes give new disks the wrong size.** "New images make
   bigger disks: 1.2 GiB instead of 842 MiB" and "`Install` needs 384
   MiB more disk": the release's `janus-kvm.qcow2` is **970 MiB**
   (v2026.11.02-2's: 842 MiB), and so are the recycled and new
   machines' disks - two slots of 64 MiB more each, **+128 MiB**, as
   `internal/diskimage` and `image/disk/README.md` say (ESP 64, two data
   slots of 128, two hash partitions of 4, STATE 128, LOGS 512 MiB).
   Text only: the release body (and its promotion's) should say 970 MiB
   and 128 MiB.
2. **A staged update's refusal miscounts what it wrote.** When the root
   filesystem came by `upload-release` (or the Controller's push), the
   refusal says "(0 MiB written)" for a damaged file and "nothing was
   written" for a mixed one - but the upload had already written the
   whole file into the slot, which no longer holds its release. What
   `version`, Rollback and the page say is right ("holds part of an
   update that was refused", "holds an uploaded root filesystem");
   only the message is misleading. Cosmetic.

Also, not defects as far as I can tell: the 2.4 % CPU per new
connection (above); the Controller's update still slowed by
`ha/previous/` (#482, not in this release).

- A bundle damaged on the wire over HTTPS: the node fetched the damaged
