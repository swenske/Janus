# v2026.10.14-3 pre-release tests

Tested on 2026-10-14, the day it was cut: the CI run that built it, then
the lab, with v2026.10.14-2 measured the same way just before. For the
first time the lab had no client of its own: the load and the probes
came from machines outside the lab's host - the three CI runners, and a
fourth machine that isn't a runner, always free, where the probes ran.
The scenarios: [Lab test scenarios](lab-scenarios.md).

## Verdict

**What this pre-release fixes held in the lab, and nothing that worked
before moved.**

- **HAProxy started again after the kernel killed it.** Seven times, a
  configuration the kernel's OOM killer kills HAProxy for. Six times it
  killed only the new process, and the previous one kept serving. Once
  it killed the serving process too: janusd started it again after 1 s,
  and the node served again after 1.3 s. Before this pre-release, that
  node stayed down.
- **Auto-scaling added memory at once after the OOM kill**: 1024 →
  1280 MiB 17 s later, `tcp_mem` and `fs.file-max` following.
- Everything else matched v2026.10.14-2, measured the same way just
  before:
  - the Controller's update;
  - the rolling update under load (no request lost during it);
  - failovers, reboots and rollbacks;
  - throughput;
  - SELinux enforcing with no denial, CIS 33/33.

Found on the way:

1. **Paused, auto-scaling forgot the kernel parameters it had raised.**
   The machine went back to 1024 MiB with `tcp_mem` and `fs.file-max`
   still sized for 1280 MiB. Fixed in
   [#92](https://github.com/swenske/Janus/pull/92), for v2026.10.14-4.
2. **CI waited an hour on the Go module proxy.** The Controller's
   self-update test took 60 minutes. The first attempt to publish
   failed on a download from the module proxy that timed out. From here,
   the IPv4 path to Google's servers is slow and stalls now and then -
   see [CI](#ci-image-build). The Controller image keeps its modules
   between builds since
   [#91](https://github.com/swenske/Janus/pull/91).
3. **One firmware reboot took 43 s instead of 9**: 34 s in the firmware,
   before the kernel. The three reboots after it took 9.4 s each.

What the pre-release brings: v2026.10.14-2, plus HAProxy started again
after it dies -
[its notes](https://github.com/swenske/Janus/releases/tag/v2026.10.14-3).

## The lab

[v2026.10.14's lab](v2026.10.14.md#the-lab), with its own client VM
removed - it took the host's CPUs from the nodes. One client from
outside the lab's host, the fourth machine, runs the probes, the
single-client `wrk` runs and the rolling update's load. All four
clients run the multi-client runs. Probed for 2 minutes with nothing
changing, the VIP and the anycast address lost no request from it: 0 in
4,385.

v2026.10.14-2 was measured with these clients just before the update.
These figures aren't comparable with earlier reports': other clients,
another path.

After the update, eight reboots and two rollbacks, node 02's event log
ran from 1 to 216 without a gap.

### HAProxy killed by the kernel

On the auto-scaled node (2 vCPU, 1 GiB, auto-scaling paused, HAProxy
answering by itself on its front address), seven times: a configuration
with three 400 MB caches, which HAProxy writes through when it starts -
more than the node's memory together. Probes on the front address
throughout.

| | What the kernel killed | Back to serving | Lost |
|---|---|---|---|
| 6 tries | the new process only (`kernel.oom_kill`); the configuration refused, the previous one put back | the previous process never stopped | 0 to 3 requests (0.16 s at most) |
| 1 try | the new process, **then the serving one** | `haproxy.exited` "exited on its own", `haproxy.restarted` 1 s later; serving again 1.3 s after the apply | 24 requests (1.3 s) |

Each time, the node said what happened: `kernel.oom_kill` naming the
process, `haproxy.exited` with its reason. In the second case it also
said when it would start HAProxy again. Before v2026.10.14-3, that last
case left the node down until someone started HAProxy.

### Auto-scaling after an OOM kill

The same configuration once more, auto-scaling **on** (up to 4 vCPU and
2 GiB, the kernel parameters following):

- the memory step came **17 s** later, without the usual 2-minute
  window: *the kernel killed a process for lack of memory (9 since
  boot)*. 1024 → 1280 MiB.
- `tcp_mem` and `fs.file-max` were raised for 1280 MiB, on trial, then
  confirmed.
- **Paused**, the machine went back to 1024 MiB at once, but `tcp_mem`
  and `fs.file-max` stayed sized for 1280 MiB. Changing the mode
  restarted auto-scaling's state and dropped its record of what it had
  changed. Fixed in [#92](https://github.com/swenske/Janus/pull/92): the
  record is kept, and auto-scaling puts back what followed the memory
  when paused, when observing, and before the restart that removes its
  policy.

The machine was also updated to v2026.10.14-3 through the Controller
(its version changed in its record): back in 13 s.

### The nodes' health, on v2026.10.14-3

Both nodes:

- v2026.10.14-3, kernel 7.2.10 (stable track), HAProxy 3.4.6, BIRD 2.20.0,
  the lab's schematic; the other slot v2026.10.14-2.
- Services: janusd, haproxy, bird, keepalived, prometheus-node-exporter,
  qemu-guest-agent - all running and healthy.
- SELinux enforcing, **0** AVC denials; **0** OOM kills.
- CIS Debian Linux 13 Benchmark v1.0.0 (Level 2 - Server): **33/33**
