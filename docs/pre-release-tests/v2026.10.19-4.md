# v2026.10.19-4 pre-release tests

Tested on the evening of 2026-10-19, right after it was cut. It is
[v2026.10.19-3](https://github.com/swenske/Janus/releases/tag/v2026.10.19-3)
with:

- the node's neighbour table, `NetworkService.NeighborList`
  ([#174](https://github.com/swenske/Janus/pull/174), for
  [#161](https://github.com/swenske/Janus/issues/161));
- haproxy.cfg's history - who applied what, a diff, going back
  ([#175](https://github.com/swenske/Janus/pull/175), for
  [#163](https://github.com/swenske/Janus/issues/163));
- Go 1.27.2 for every binary
  ([#173](https://github.com/swenske/Janus/pull/173));
- `gofmt` checked by the linter
  ([#176](https://github.com/swenske/Janus/pull/176)), and the
  Neighbours card on a node not yet updated
  ([#177](https://github.com/swenske/Janus/pull/177)).

HAProxy, the kernels and the extensions are the versions of
v2026.10.19-3. The lab ran v2026.10.19-2 - v2026.10.19-3, a direct
release, changed only the Controller's pages; its nodes are the same -,
measured again that evening before the update. This run repeats every
step of the last full campaign
([v2026.10.18-2](v2026.10.18-2.md#the-lab)) and adds the two new
features on the lab's nodes.
The scenarios: [Lab test scenarios](lab-scenarios.md).

## Verdict

**Ready to promote** - with the image's room to decide on before it
grows again (below).

- **The neighbour table** reads the lab's real tables: the backends, the
  router, the Controller, each with its MAC. From the backup node, the
  VIP answers with the MAC of the node holding it, and the MAC changes
  as soon as the VIP moves.
- **The history** keeps each configuration applied through the
  Controller, with who applied it. Going back to the first version
  through the Controller, on the node holding the VIP and the anycast
  route, lost **no request**. The history went through two firmware
  reboots, three kexec reboots and a rollback to v2026.10.19-2, whose
  janusd doesn't know it, and back: it was intact each time.
- **Nothing else moved**: the Controller's update, the image factory, the
  rolling update, failovers, firmware and kexec reboots, rollbacks and
  HAProxy's throughput match the earlier campaigns. Throughput is within
  -2.6 % and +2.3 % run by run, against the release measured the same
  evening.
- **The image's room**: with every extension, the root filesystem takes
  **62.19 MiB of its 64 MiB** boot slot, against 60.65 MiB in
  v2026.10.19-3. CI warned that less than 2 MiB is left. Go 1.27.2 makes
  each Go binary about 3 % larger (below). The image still fits, but the
  slots never grow: what to do about it is a decision to take before the
  next release that adds anything.

## CI: image-build

[Run 39294089958](https://github.com/swenske/Janus/actions/runs/39294089958),
from `main` at `2ddbbfa`, with `release_version=v2026.10.19-4` and
`prerelease`, dispatched at 19:26 Paris.

- **One test job failed** at its first attempt: `controller-libvirt-test`
  expected auto-scaling to add a vCPU under load, and the engine refused.
  The runner's host was busy with the run's other test jobs, so the
  machine's vCPUs waited for the host 22 % of the time (steal), above the
  10 % beyond which another vCPU would wait as well. That refusal is
  [#85](https://github.com/swenske/Janus/pull/85)'s, by design, and
  auto-scaling is untouched here. Run again alone, it passed.
- **The publish job published everything but one step**: the GitHub
  pre-release (44 assets, the signed bundle), the Controller image on
  Docker Hub, the SD card images. Its apt step failed, though: aptly's
  database was held by a cleanup of other repositories' old snapshots
  ("unable to reopen the DB"). janusctl 2026.10.19-4 isn't in apt's
  `testing` suite, a choice: the promotion publishes the release's own
  packages to `stable`, and re-running the job would have built and
  uploaded the pre-release's images again.

Its `security.json` says *none* against v2026.10.19-3: Go goes from
1.26.9 to 1.27.2 with no known vulnerability fixed. No 🔒 in its name, no
badge.

### The neighbour table

`janusctl network neighbors` on both nodes, then the VIP's entry as the
backup sees it. The backup reached the VIP first with a connectivity
test, so that it had an entry for it:

| When | Seen from | The VIP's MAC |
|---|---|---|
| The VIP on node 01 | node 02 | node 01's front MAC, `reachable` |
| Node 01 drained (VRRP priority 50): the VIP on node 02 | node 01 | **node 02's** front MAC, `reachable` |
| Node 01 back: the VIP on node 01 again | node 02 | node 01's front MAC again |

- **Each node's table**: 13 entries on three interfaces.
  - Five neighbours that answer: both backends, the router on the front
    and management networks, the Controller - four `reachable`, the
    router's management address in `delay` at that moment. Each has its
    MAC and was confirmed within seconds by the traffic to it.
  - Eight `noarp`: the multicast groups each interface listens to -
    VRRP's 224.0.0.18, IGMP's 224.0.0.22, IPv6's. The kernel lists them
    as `ip neigh` does.
- **Through the Controller** (its node page's
  `/api/network/neighbors`): the same 13 entries.
- **SELinux**: no denial on either node - janusd's existing netlink
  rules cover it, as `qemu-probe-test` measured.

## Follow-ups

1. **The image's room** (above): 1.81 MiB left with every extension.
   Where it could come from is a decision to take before anything else
   is added:
   - the Go binaries are separate programs, each with its own copy of
     the runtime and the shared packages (janusd, init, janus-acme and
     the Go extensions);
   - init alone is 15.7 MB for PID 1.
2. **The neighbour table's multicast entries** (8 of 13 on each node)
   crowd the card: folding the `noarp` ones away by default would leave
   the neighbours that answer.
3. **Promotion**: release-promote (dry run first); no security fix, so no
   🔒 badge. The landing page's figures become 16 MB for the root
   filesystem and 54 MB for the VM disk.
