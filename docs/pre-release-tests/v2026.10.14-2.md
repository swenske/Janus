# v2026.10.14-2 pre-release tests

Tested on 2026-10-14, the day it was cut, after
[v2026.10.14's](v2026.10.14.md) campaign found three defects in
auto-scaling: the CI run that built it, then the lab, with v2026.10.14
measured the same way just before. For the first time the load and the
probes came from the three CI runners, outside the lab's host: the
host's CPUs went to the nodes. The scenarios:
[Lab test scenarios](lab-scenarios.md).

## Verdict

**The three auto-scaling defects are fixed, and nothing else moved.** In the lab, auto-scaling did what v2026.10.14 got wrong:

- it refused a vCPU to a machine on a host out of CPU, saying why;
- it added two vCPUs to the same machine once the host had CPUs to
  give;
- it added memory on a host whose free memory was mostly page cache;
- it journaled what the machine got.

The rest matched v2026.10.14, measured the same way just before:

- the Controller's update;
- the rolling update under load (no request lost during it);
- failovers, firmware and kexec reboots, rollbacks;
- throughput (from one client 4 % lower at 256 connections, the
  same otherwise);
- SELinux enforcing with no denial, CIS 33/33.

Found on the way:

- **janusd doesn't start HAProxy again when it dies**: CI's first
  attempt failed because the kernel's OOM killer took the serving
  HAProxy after the new one - see [CI](#ci-image-build) and
  [follow-ups](#follow-ups). Not new in this pre-release.
- The runners' paths to the lab lose a request now and then (one every
  1 to 2 minutes, with nothing changing): this report counts them
  apart.

What the pre-release brings: v2026.10.14, plus the three auto-scaling
fixes of [#85](https://github.com/swenske/Janus/pull/85) - steal time is
the host's, not a reason for a vCPU (the node reports it); the host's
room is its available memory on libvirt; a refused step is journaled
once; a step is journaled with what the machine got -
[its notes](https://github.com/swenske/Janus/releases/tag/v2026.10.14-2).

## Follow-ups

1. **janusd should start HAProxy again when it dies.** An HAProxy that
   exits on its own - killed by the kernel's OOM killer as in CI's first
   attempt, or crashing - is counted (`janus_haproxy_unexpected_exits_total`,
   an `haproxy.exited` event) and left stopped: the node serves nothing
   until someone starts it through the API or reboots the node. With
   VRRP or BGP, the other node takes the traffic; alone, the node stays
   down. Proposed: janusd restarts it with the configuration it was
   running, after a growing delay (1 s, doubling, 30 s at most), and
   says so (an event, a counter). With auto-scaling, the OOM kill also
   adds memory at once. Not new in this pre-release: to decide.
2. The hot-plug test's OOM step asserts that the previous HAProxy keeps
   serving, which the kernel doesn't promise - it may pick it as its
   second victim. Once janusd restarts HAProxy, the test can wait for it
   to serve again instead.
3. At v2026.10.14-2's promotion: the landing page's root filesystem,
   15 MB → 16 MB (15.68 MB, as in v2026.10.14).
