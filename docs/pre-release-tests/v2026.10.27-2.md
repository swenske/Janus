# v2026.10.27-2 pre-release tests

Tested on the afternoon of 2026-10-27. It is
[v2026.10.27](https://github.com/swenske/Janus/releases/tag/v2026.10.27)
with one change, [#359](https://github.com/swenske/Janus/pull/359): the
**janusctl skill for Claude Code** (this repository as a plugin
marketplace), **`janusctl haproxy server-state`** and **`janusctl
haproxy reload`**. The nodes and the Controller are unchanged but for
the version.

The same lab as the campaigns before; its HAProxy and kernel unchanged.
The nodes came from v2026.10.26-3: v2026.10.27 itself changed nothing
they run (only the cluster engine the Controller and janusctl use), so
v2026.10.26-3 is the baseline, measured again in this session.

## Verdict

**Ready to promote.** What this pre-release brings works on the lab's
real nodes, under load:

- **A server drained, in maintenance and back** with `janusctl haproxy
  server-state` on the node holding the VIP: **0 lost** of 1,483 VIP
  and 1,473 anycast probes; while drained or in maintenance the server
  got **no** request, and its share came back with `ready`.
- **HAProxy reloaded** with `janusctl haproxy reload` on each node in
  turn: **0 lost** of 1,194 and 1,184; a server drained before the
  reload took traffic again after it, as documented.
- **Claude Code with the skill**, installed from this repository on
  GitHub: with a reader certificate it read the lab and stopped where
  the role stopped it - a drain it was asked for, refused by the node,
  was reported, no other credential tried; with an operator certificate
  it drained a server and put it back under load - **0 lost** of 5,765
  and 5,755.
- **The baseline**: the rolling update under load lost **nothing** on
  the VIP and one anycast probe (the lab router's known noise, below);
  HAProxy's throughput at v2026.10.26-3's level; zero AVC denials, the
  CIS audit 33/33.

## What this pre-release changes

### A server drained, in maintenance and back (#359)

On the node holding the VIP, under probes of the VIP and the anycast
address (50 ms, from a runner) and `wrk` on the VIP (8 keep-alive
connections, another runner): `janusctl haproxy server-state app
back-01` drain for 20 s, ready for 10 s, maint for 20 s, ready. Each
probe records which backend server answered.

| Phase | VIP probes served by back-01 / back-02 |
|---|---|
| Before | 61 / 48 |
| Drained | **0** / 389 |
| Ready | 107 / 88 |
| Maintenance | **0** / 388 |
| Ready again | 222 / 179 |

**0 lost** of 1,483 VIP and 1,473 anycast probes; `wrk` 14,280 req/s,
no socket error. janusctl printed the state HAProxy reports at each
step - `drain`, `up`, `maint`, then `up 1/2` after the maintenance (its
health checks counting again; `up` seconds later) - and the node logged
each change in its events.

### HAProxy reloaded alone (#359)

Same load and probes: back-01 drained on the node holding the VIP, that
node reloaded 10 s later with `janusctl haproxy reload`, the other node
15 s after.

| Phase | VIP probes served by back-01 / back-02 |
|---|---|
| Drained | **0** / 196 |
| After node 01's reload | 80 / 214 - back-01 back in service |
| After node 02's reload | 165 / 430 |

**0 lost** of 1,194 VIP and 1,184 anycast probes; `wrk` 14,044 req/s,
no socket error. The configuration's history kept the same newest
version: a reload isn't a version. Right after a reload `haproxy
backends` shows HAProxy's transitional check states (`up 0/2`, `up
-1/2`) for a second or two.

### The plugin installed from GitHub (#359)

In an empty Claude Code configuration (Claude Code 2.1.311): `claude
plugin marketplace add swenske/Janus` then `claude plugin install
janusctl@janus` installed and enabled the plugin at version
`069bbced1955` - the pre-release's commit; the one-step `claude plugin
install janusctl --marketplace swenske/Janus` did the same.

### Claude Code driving the lab (#359)

Headless Claude Code with the plugin as installed from GitHub, the ask
rules of [its page](../guide/claude-code.md#the-critical-commands-always-asked),
`janusctl *` allowed, **no janusctl context** - the prompt named the
node and the certificate to use with `-endpoint`. The certificates: a
reader's and an operator's, issued for two hours by the node holding
the VIP (`janusctl pki generate-client-config -role ... -ttl 2h`), their
files deleted after.

| Asked | With | What Claude did |
|---|---|---|
| Is the lab's load balancer healthy? | the reader's | read only (versions, services, HAProxy, backends, VRRP, BGP, events under `timeout`, `tui -once`...); said what the role kept from it (the keepalived configuration, HAProxy's errors, a probe from the node) and where its answer stopped (the peer it had no endpoint for); noticed the drains and reload of the scenarios above in the node's events |

Under probes: **0 lost** of 5,765 VIP and 5,755 anycast, `wrk` 15,213 req/s without a socket error; back-02 out 41 s |

## Findings

1. **One anycast probe lost during the rolling update** - at node 01's
   reboot, while it was drained and its anycast route withdrawn for
   8.5 s: node 02 was the only path. One request without an answer in
   1 s, the lab router's known noise around route changes (0 to 3
   probes in earlier campaigns); the node side is unchanged since
   v2026.10.26-3, whose campaign lost none. Nothing to fix in this
   release.
2. **The lab's syslog target is still blocked on the network's side**
   (seen since v2026.10.26's campaign: the router in front of the log
   server answers "unreachable" for its syslog port only) - not Janus.
   The skill's reader run reported it from the node's log forwarding
   status.
