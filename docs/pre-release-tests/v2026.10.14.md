# v2026.10.14 pre-release tests

Tested on 2026-10-14, the day it was cut: the CI run that built it, then
the lab, with v2026.10.13-4 (the newest release) measured the same way
just before.

## Verdict

**No regression found in what v2026.10.13-4 already did; three defects
found in auto-scaling, the pre-release's new feature - fixed in
[#85](https://github.com/swenske/Janus/pull/85), for a
v2026.10.14-2.** Every CI test passed. In the lab, the pre-release
updated the Controller and both nodes without losing a request on the
VIP, failed over, rebooted (firmware and kexec) and rolled back as fast
as v2026.10.13-4, served the same throughput, and ran SELinux enforcing
with no denial and the CIS benchmark at 33/33. v2026.10.13-5's other
slot and kept event log worked on real nodes - through a power cut,
reboots and a rollback.

Auto-scaling, on a machine the lab's Controller created: observing,
growing and shrinking vCPUs under load, memory under pressure, the
kernel parameters following the memory, all without a lost request
(one in 13,836 at a reload). What it got wrong:

1. **Steal time counted as busy.** On a host already out of CPU, a
   machine went from 2 to 4 vCPUs: half of its vCPUs' time was stolen
   by the host, and with the load coming from outside the host, each
   vCPU added made it worse: 13 % of the time stolen at 2 vCPUs, 37 % at
   3, 43 % at 4. See [auto-scaling](#auto-scaling).
2. **libvirt: the host's room read from its free memory only** - 173
   MiB on a host with 6.1 GiB available in its page cache: every memory
   step refused, and the refusal journaled 16 times in 6 minutes.
3. **A step journaled with a late reading** - "1152 MiB" for a step to
   1280 MiB the node already had.

Found on the way, outside the pre-release:

- The Controller's slow requests that v2026.10.12's report left open
  were the network path from the workstation that probed it, not the
  Controller - see [the Controller](#the-controller).
- The landing page's root filesystem figure needs updating at the
  promotion - see [what CI measured](#what-ci-measured).

What the pre-release brings: auto-scaling of the nodes the Controller
creates on libvirt and Proxmox VE, the hot-plug of vCPUs and memory on
the nodes, OOM kills as events, `tcp_mem` among the kernel parameters,
Terraform's `autoscaling` block - and v2026.10.13-5's updates naming what
they install, the other slot, the event log kept across reboots and
updates, BIRD 2.20.0 -
[its notes](https://github.com/swenske/Janus/releases/tag/v2026.10.14).

### Auto-scaling

A machine created by the lab's Controller for this campaign
(the auto-scaled node): 2 vCPU and 1 GiB from the release's default image,
HAProxy in front of the lab's two backends, probes every 50 ms on its
front address throughout. Its policy: up to 4 vCPU and 2 GiB, the
kernel parameters following, every threshold at its default but the
return delay - 10 minutes instead of 30, to fit the campaign.

| Step | What happened |
|---|---|
| Created | from the release's image in **15 s**: downloaded (4 s), the VM started, the node registered and answered the Controller |
| A policy set (observe, room for 4 vCPU and 2 GiB) | the one restart it takes: the Controller's PATCH to ready in 12.7 s, HTTP unanswered for **7.1 s** |
| Observing, loaded 7 min (`wrk -c256` from the load client) | HAProxy 19 to 26 % idle; after 5 minutes, journaled *would grow to 3 vCPU - the CPUs 75 % busy on average over 5m0s*, its status *observing - its size would be 3 vCPU*; nothing resized |
| Turned on, the same load for 14 min | 2 → 3 vCPU 6 s later (the 5-minute window still held the observed load); `net.core.somaxconn` 60000 → 4096 (the node's `somaxconn.memory` suggestion) on trial and confirmed; 3 → 4 vCPU 5 minutes later; each vCPU onlined, `system.cpus_changed` with HAProxy reloaded; **1** probe lost in 13,836 (0.07 s, at the second reload); `wrk`: 31,042 req/s, 89 read errors - its keep-alive connections closed by the reloads |
| The load gone | 4 → 3 vCPU after 10 min, 3 → 2 after 10 more, each *HAProxy would stay idle 50 % of the time or more with N vCPUs*; **0** lost in 17,242 |
| A 700 MB HAProxy cache (7 % of the memory available) | refused, see below - then, with the host's page cache dropped: 1024 → 1280 MiB after 2 minutes (the node's MemTotal 913 → 1169 MiB, 26 % available), `tcp_mem` and `fs.file-max` raised in proportion on trial and confirmed; the cache removed, back to 1024 MiB 10 minutes later and both parameters back to the boot's values; **0** lost in 18,080 |
| Paused | back to its size at once: 4 vCPU to 2 in 14 s |
| Its card and journal | the Hypervisors tab shows *2 vCPU · 1024 MiB - now 4 vCPU*, the status and the journal; both themes, no console error |

What went wrong:

- **Steal time counted as busy.** The second step up, 3 → 4 vCPU, said
  *the CPUs 82 % busy* while HAProxy was 45 % idle. At 4 vCPUs, the
  node's `/proc/stat` over 10 s: 10 % user, 9 % system, 11 % softirq,
  20 % idle, **50 % steal** - the host (4 cores) was 3.8 % idle with a
  load average of 8.4: the load client, the node and the backends all
  ran on it.
  Loaded from the three CI runners instead (outside the host, `wrk -c128`
  each), the same machine at 2 vCPUs was really busy - 82 % busy, 13 %
  steal, HAProxy 7 to 16 % idle - but the host was still out of CPU
  (3 % idle): the steps to 3 then 4 vCPUs took the steal to 37 % then
  43 %, HAProxy still 23 to 31 % idle. A vCPU more doesn't help a host
  that has none to give. Fixed in #85: the node reports its steal time
  (`SystemStat`'s `cpu_steal_ticks`, `janusctl system systemstat`), it
  isn't counted as busy, and no vCPU is added while the vCPUs wait for
  the host more than 10 % of the time. The runners' run would have
  stayed at 2 vCPUs (13 % steal), saying why; the load client's would
  not have gone past 3 - its steal was measured at 4 vCPUs only.
- **The host's room, on libvirt.** The memory step was refused, *the
  host has 173 MiB free: 256 more would leave less than the 797 MiB it
  keeps free*: the driver read the host's free memory (`MemFree`),
  while 6.1 GiB were available - the rest in its page cache, which the
  kernel gives back. Every memory step on a host that has run a while
  would be refused. The refusal was also journaled 16 times in 6
  minutes: its figure changed with each decision, and the "same refusal"
  check compared whole messages. Fixed in #85 (free + buffers + cached,
  refusals told apart by their words). For the rest of this campaign
  the host's page cache was dropped, so the step could go through.
- **A late reading journaled.** The memory step was journaled *to
  1152 MiB*: libvirt's virtio-mem `current` was read before QEMU had
  told it the whole 256 MiB. The minute's sync put 1280 MiB on the
  machine a moment later. Fixed in #85: the hypervisor is read again
  until it agrees with the node, 15 s at most.

Not a defect, but worth knowing: the `somaxconn` suggestion applied at
3 vCPUs stayed at 4096 once the machine was back at its size - only what
follows the memory goes back, as the documentation says.
v2026.10.14's release notes said every parameter went back; the notes of
the next pre-release say it as it is.
