# v2026.11.19-2 pre-release tests

Tested on 2026-11-19, the afternoon it came out, on the lab where
v2026.11.18 - the newest release - was measured first, the same
afternoon, with the same clients ([v2026.11.18's
report](v2026.11.18.md)). What the pre-release changes:

- **janusd's memory on nodes with BIRD or keepalived** (#682): the
  health gates that withdraw a node's routes (BIRD, every second) or
  give up its virtual IPs (keepalived, every two) left a waiting
  goroutine behind at each check, so janusd grew for as long as the
  node ran - since v2026.10.24;
- **node_exporter 1.13.0** (#681, 🔒): Go's HTTP/2 fixes in the
  modules it's built with; the notes say Janus runs it over plain HTTP,
  where Go serves no HTTP/2;
- **cluster members' certificates renewed at half their life** (#683,
  the Controller and `janusctl cluster check`): 15 days left instead of
  10, a day before the example alert.

The campaign was planned for v2026.11.19 (#682 and #681). v2026.11.19-2
- the same plus #683 - came out 31 minutes later, while the release's
baseline was running; the Controller offers a node only the newest
pre-release, so everything after that point ran on v2026.11.19-2, the
build that would be promoted. The Controller's own update and the
image factory were also run once on v2026.11.19 (below); the node
changes are the same in both.

The leak is the point: janusd's memory on both nodes - BIRD and
keepalived on each - and on two of the Controller's machines with
neither, sampled every minute from a fresh boot for 45 to 52 minutes on
the release, then for 61 minutes on the pre-release with a HAProxy
stop on node 01 in the middle. And the workaround the notes give for
nodes not yet updated - `janusctl system restart` - measured on the
release under probes. Then a lighter core campaign: the Controller's
update through its updater, the image factory, the cluster of both
nodes updated in place under load, a VRRP and a BGP failover, a
rollback and back, a firmware and a kexec boot, HAProxy's cost per
request with the release and the pre-release alternated, the pages and
the nodes' health.

## Verdict

**The leak is gone. On the release, janusd grew 20.4 and 21.1 MiB an
hour on the two nodes with BIRD and keepalived - 17 MiB in 45 minutes
on node 01 - while the two machines without them stayed flat; on the
pre-release, over 61 minutes and a HAProxy stop, both nodes moved by
less than a MiB, like the machines without. The gates still react at
once: with HAProxy stopped on node 01, the router lost its route and
the VIP moved within the stop's drain, both back a second or two after
HAProxy restarted, no probe lost. node_exporter says 1.13.0 and, as the
notes say, answers no HTTP/2 on its plain-HTTP port - on the release
nor the pre-release. The restart the notes advise gave node 01's
memory back (50.9 → 30.3 MiB) without HAProxy missing a request on the
node's own address; the VIP was back on it after 7 s, its BGP route
after 11 s. The rest is as before: the cluster updated in place in
41.1 s without a lost probe, the same failovers, boots and cost per
request, zero AVC denials, CIS 33/33, the pages with the release's
buttons. My opinion: ready to promote** - nothing found is the
pre-release's; the decision is yours.

## janusd's memory (#682)

janusd's resident memory read from each node's process list (through
the Controller's node page, every 60 s), and on nodes 01 and 02 its
`/proc/<pid>/status` too - `RssAnon` leaves the binary's mapped pages
out, the clearest signal for goroutine stacks. Every node had just
booted: the lab was switched on for the release's series; for the
pre-release's, nodes 01 and 02 came from the cluster update (and node
01 from the node-loss test), the machines from their update. Slopes by
least squares.

| Node | Extensions | v2026.11.18 | v2026.11.19-2 |
|---|---|---|---|
| 01 | BIRD, keepalived, node_exporter | **+20.4 MiB/h** over 45 min (33.8 → 50.9 MiB; `RssAnon` 15.9 → 31.6, +20.4 MiB/h) | **−0.5 MiB/h** over 61 min (33.9 → 33.0 MiB; `RssAnon` 13.0 → 13.6) |
| 02 | the same | **+21.1 MiB/h** over 52 min (35.1 → 53.9 MiB; `RssAnon` +20.6 MiB/h) | **−0.7 MiB/h** over 61 min (33.1 → 32.9 MiB; `RssAnon` 13.7 → 13.7) |
| The longterm machine | none | −0.3 MiB/h | −0.1 MiB/h |
| The Let's Encrypt machine | Let's Encrypt only | +0.3 MiB/h | −0.5 MiB/h |

The thread count stayed constant (13 and 14) in both versions: the
leaked goroutines were parked, not running. The lab's rate is about
twice what production saw (10 MiB/h with BIRD, 5 with keepalived, so
about 15 for both): one and a half checks a second here make some
5,400 goroutines an hour, about 3.9 KiB each in this measurement. On
the pre-release, node 01's 35 minutes after the HAProxy stop below
were flat too (−1.3 MiB/h, `RssAnon` −0.7): a change - the case where
the new code starts a goroutine - leaves nothing behind.

## The workaround on the release: `janusctl system restart`

What the notes advise for a node not yet updated, on node 01 running
v2026.11.18 after 45 minutes of growth, under the VIP and anycast
probes (50 ms, from the build box), the router watched; done twice, the
second time with a third probe on node 01's own front address, since
the VIP and the anycast route both leave the node during the restart
and their probes can't see its HAProxy.

| From the call | First restart | Second restart |
|---|---|---|
| Node 01's anycast route withdrawn (janusd's leave, then BIRD stopped) | +2.1 s | +2.2 s |
| VIP on node 02 | +2.8 s | +2.65 s |
| Node 01's BGP session and BFD down | +4.2 s | +4.1 s |
| The new janusd logging | +6 s | +6 s |
| **VIP back on node 01** | **+7.05 s** | **+7.1 s** |
| **BGP + BFD up, the route back** | **+11.2 s** | **+10.6 s** |
| Probes lost: VIP / anycast / node 01's front | 0 of 821 / 1 of 818 / - | **0 of 845 / 0 of 842 / 0 of 840** |
| janusd's memory | **50.9 → 30.3 MiB** | 33.2 → 31.5 MiB |

HAProxy went on serving on the node's own address throughout; its
process changed (the new janusd takes it over with a seamless reload,
as the code says), so its uptime starts again. The one anycast probe
lost in the first restart fell when node 01's BGP session dropped,
1.9 s after its route had been withdrawn - a connection the router had
already sent there. All services came back healthy, no AVC denial.

Worth knowing for the notes' "a few seconds": janusd answers the API
for about a second after the call - the old process, leaving - then
nothing until the new one listens at about +6 s; a client that sees the
API answer right after the call hasn't seen the new janusd yet.

## Findings

None in the pre-release. Worth knowing:

1. **The leak ran faster on the lab than in production** - about
   20 MiB an hour on a node with both BIRD and keepalived, against the
   notes' 10 + 5: the notes' figures are production's; the lab's are
   within the same order and the fix removes both.
2. **The restart's API answers right away from the leaving process**:
   the new janusd listens about 6 s after the call. A script waiting
   for the API after a restart should wait for the new process (its
   PID, or the services coming back), not the first answer.
3. **One slower firmware restart** of node 02 in a rollback (16.0 s
   instead of about 11), as on the previous campaign; the boot right
   after was on time.
4. **v2026.11.19 superseded mid-campaign**: v2026.11.19-2 came out
   while the release's baseline ran, so this report is v2026.11.19-2's;
   v2026.11.19 was only installed on the Controller and the longterm
   machine on the way.

## Not tested

  production saw the two rates apart.
- Longer than an hour on the pre-release: production's 1.68 GiB took
  six days; a slope over an hour is flat to within a MiB.
