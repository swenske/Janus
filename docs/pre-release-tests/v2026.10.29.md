# v2026.10.29 pre-release tests

Tested in the night of 2026-10-28 to 29. It is
[v2026.10.28-2](https://github.com/swenske/Janus/releases/tag/v2026.10.28-2),
the release, with
[#396](https://github.com/swenske/Janus/pull/396) (DHCP is janusd's own
client: no `ip=dhcp` on the kernel's command line),
[#395](https://github.com/swenske/Janus/pull/395) (a cluster's members
updated in place, one at a time, in one action),
[#391](https://github.com/swenske/Janus/pull/391) (a drained member stays
drained across a reboot),
[#390](https://github.com/swenske/Janus/pull/390) and
[#397](https://github.com/swenske/Janus/pull/397) (keepalived's and
BIRD's own counters in the Janus exporter),
[#392](https://github.com/swenske/Janus/pull/392) (Proxmox's guest agent
option, and the settings an earlier Controller didn't give a machine,
applied on demand),
[#394](https://github.com/swenske/Janus/pull/394) (the janusctl plugin's
hook, janusctl through a proxy),
[#389](https://github.com/swenske/Janus/pull/389) (an extension may
require another) and
[#388](https://github.com/swenske/Janus/pull/388) (the security badge
names the release with the fixes).

## Verdict

**Ready to promote.** On the lab's real nodes:

- **The baseline holds**: failovers, firmware and kexec reboots and the
  rollback at the level of v2026.10.28-2's campaign; zero AVC denials
  and the CIS audit 33/33 on both nodes.
- **A cluster updated in place** - the lab's two nodes, under load -
  in 35 s, without losing a request on the VIP or the anycast address.
- **A drained member rebooted stays drained**: out of the VIP, its
  anycast route never back at the router until it is undrained.
- **A node on networks without DHCP** answers 1.5 s after its kernel
  started, against 169.1 s on v2026.10.28-2.
- **The guest agent's machine, the new metrics and the Claude Code
  hook** work as their PRs say.

HAProxy's throughput with a new connection per request read lower again;
the CPU time each request costs, alternating both versions on the same
node, is the same ([finding 3](#findings)).

## What this pre-release changes

### Booting without DHCP (#396)

Two machines the Controller created with only the front and backend
networks - neither has a DHCP server - and static addresses; each one's
console read through the Controller while the machine was reset:

| | v2026.10.28-2 | v2026.10.29 |
|---|---|---|
| The kernel's console | `Sending DHCP requests ...... timed out!` twice, `IP-Config: Auto-configuration of network failed` | no DHCP at all |
| init started | 168.80 s after the kernel | 1.24 s |
| `boot: api listening` | **169.1 s** (kernel 168.8 s) | **1.5 s** (kernel 1.2 s) |

(Neither could register: the Controller has no route back to the front
network - the test only needed their boot.)

A third machine, from the pre-release with its management network in
DHCP mode: registered from the address the lab router's DHCP gave it 4
s after it started; its network status shows the lease (server, DNS and
NTP from the lease, 24 hours) and the loopback interface up with
`127.0.0.1` and `::1`. Its renewal at half the lease wasn't waited for;
the `qemu-dhcp-test` of #396 renews a 2-minute lease (run by the PR, not
yet in image-build).

### Updating a cluster in place (#395, #375)

A cluster made by the Controller of nodes 01 and 02 on v2026.10.28-2
(a stick table replicated over the peers, VRRP managed with each
member's priority), then `POST /api/clusters/{id}/upgrade` to
v2026.10.29 under load - `wrk` on the VIP from one runner, the VIP and
the anycast address probed every 50 ms from another:

| | v2026.10.28-2's rolling update (by script) | v2026.10.29's update in place (one call) |
|---|---|---|
| Order | node 02, then node 01 | node 02 (backup), then node 01 (master), by the engine |
| VIP | 0 lost / 3,488 | **0** lost / 7,996 |
| Anycast | 1 lost / 3,478 | **0** lost / 7,986 |
| Each node, drained to back in service | 19.0 s and 17.5 s | 12.9 s and 15.4 s |
| The update call to the node back | 15.9 s and 14.4 s | 12.6 s and 15.2 s |
| `wrk` | 14,564 req/s, 16 read errors (3 min) | 14,638 req/s, 32 read errors (7 min), p99 9.0 ms |
| In all | | 34.5 s, from the call to "lab runs Janus v2026.10.29: 2 member(s) updated" |

The journal has every step: drained, updating from slot B to A (then A
to B), rebooting, back, tables learnt, undrained, "announces its routes
to its BGP peers again" before the next member. Both members ended on
v2026.10.29 with their stick tables, peers connected, no drift.

Coming from v2026.10.28-2, which kept no drain across a reboot, each
member came back in service on its own after its reboot and the engine
drained it again at once until its tables were learnt
([finding 4](#findings)).

### A drained member across a reboot (#391, #356)

On v2026.10.29, under the same load and probes: node 02 drained through
the Controller, rebooted through the firmware, its state read every few
seconds and the lab router's routes to the anycast address every 0.75 s
until it was undrained 3.5 minutes later:

| Check | Result |
|---|---|
| janusd at boot | `cluster: drained before this start, still drained` |
| VRRP | BACKUP since it booted, never master |
| BIRD | `haproxy_anycast` held down since the boot ("HAProxy doesn't answer") |
| The router | node 01's route alone on all 244 reads during the reboot and after |
| Anycast probes | none served by node 02 between the drain and the undrain |
| The Controller | the member drained, the cluster's problem "out of service" |
| Undrained | both routes back, `haproxy_anycast` up |

Anycast 0 lost / 4,331; VIP 1 lost / 4,341 ([finding 1](#findings)). The
second or so a BGP member's routes may be heard after a reboot, before
janusd closes its gate (the notes say so), didn't show here.

### keepalived's and BIRD's counters (#390, #397)

Both nodes' exporters, read after the update:
`janus_vrrp_instance_adverts_sent_total` 3,551 on the master,
`_received_total` 1,310 on the backup (and 21 on node 01, heard while
node 02 held the VIP during its drain), `became_master` 2 and
`left_master` 1 on node 01, the five `advert_errors` kinds at 0;
`janus_bgp_protocol_state` up for the BGP session, BFD and
`haproxy_anycast`, their `since` timestamps at the boots and node 02's
undrain, one route exported to the router, the route change statistics.
`janusctl network bgp status` shows each protocol's since as a full date
and time.

### The guest agent and the machines' settings (#392)

A machine from the pre-release with `qemu-guest-agent` (the image
factory built that schematic in 61 s): ready 72 s after the call, its
agent's service running, `guest-ping` answered from the hypervisor, no
hardware drift on its record, **Apply settings** answering 200 with
nothing to do. The Proxmox side isn't testable in the lab.

### Claude Code's hook (#394)

Headless Claude Code with the plugin from `main`, `Bash(janusctl *)`
allowed, the pre-release's janusctl and a two-hour reader certificate:
`sh -c 'janusctl … system reboot'` was refused before it ran, with the
reason janusctl gave ("janusctl system reboot on … is critical -
soft-stop HAProxy, then reboot"); `janusctl … version` ran under the
rule.

### Extensions that require another (#389)

No extension requires another yet: the Controller's machine creations
above, with and without extensions, went as before.

## Findings

1. **One VIP probe lost** (0.05 s) about 2.5 s after node 02's reboot
   call, while node 02 was drained and node 01 held the VIP - no route
   or VRRP change at that moment. Once in 4,341; not seen in the other
   runs.
2. **One firmware reboot of node 02 took 41.8 s** (gone after 6.5 s, as
   the others). Not reproduced: two more right after took 9.6 and 9.7 s,
   the kernel stage 1.5 s. Node 02 has no LOGS partition and its serial
   console wasn't recorded, so the boot can't be read back; it matches
   OVMF compacting a full variable store (found in v2026.10.25's
   campaigns), unverified.
3. **New connections per request read a quarter lower, the CPU per
   request is the same.** Node 01 alternated between both versions by
   rollbacks, its CPU time by mode read around each run:

   | | v2026.10.28-2 (3 runs) | v2026.10.29 (3 runs) |
   |---|---|---|
   | A new connection per request | 2,937 to 3,292 req/s, 3,091 on average | 2,687 to 2,946, 2,845 |
   | Same, CPU per request | 169.8 µs | 170.9 µs |
   | Keep-alive, 256 connections | 50,943 to 55,337 req/s, 52,421 on average | 51,547 to 55,237, 52,972 |
   | Same, CPU per request | 37.8 µs | 37.3 µs |

   The node stays three quarters idle on new connections: that run is
   bound by each connection's latency through the lab and swings from
   one round to the next, as v2026.10.28-2's campaign found.
4. **The first update in place from v2026.10.28-2** puts each member
   back in service for about two seconds after its reboot, before the
   engine drains it again: that release keeps no drain across a reboot.
   No request was lost; the VIP went back to node 01 and away again
   meanwhile. The release notes say so; from v2026.10.29 on, the drain
   holds.
5. **The build depends on MikroTik's download server** for the RouterOS
   image of `routeros-hook-test`, fetched at each run: unreachable over
   IPv4 for about an hour, it failed the first attempt.
