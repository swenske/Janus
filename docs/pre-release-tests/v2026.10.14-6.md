# v2026.10.14-6 pre-release tests

Tested on the morning of 2026-10-15, right after it was cut: the CI run
that built it, then the lab. The figures to compare with are
[v2026.10.14-5's campaign](v2026.10.14-5.md), measured the night before
with the same clients and the same scripts.
The scenarios: [Lab test scenarios](lab-scenarios.md).

## Verdict

**Ready to promote.** The fix this pre-release brings held, and nothing
that worked before moved.

**The kernel parameters went back with HAProxy unable to run** (the
fix it brings, [#98](https://github.com/swenske/Janus/pull/98)). On a
machine created for the test, a configuration needing more than its
1 GiB grew it to 2 GiB, with `tcp_mem` and `fs.file-max` following.

| Step | v2026.10.14-5 | v2026.10.14-6 |
|---|---|---|
| Paused, back to 1 GiB, where the configuration can't run | the values going back left on trial, taken back by the node 2 minutes later | confirmed; still there 3 minutes later |
| Its policy removed at 2 GiB | - | put back before the restart; the node's own values after it |

Everything else matched v2026.10.14-5:
- the Controller's update;
- the rolling update under load (no request lost on the VIP);
- failovers, reboots and rollbacks;
- throughput;
- SELinux enforcing with no denial, CIS 33/33.

Found on the way:

1. **GitHub's archive of an action failed for hours.** The first two
   attempts of the run failed within seconds, in every job, on
   `actions/setup-go`'s archive. The runners now keep the archives of
   the actions this repository pins:
   [#100](https://github.com/swenske/Janus/pull/100).
2. **No HAProxy process unknown to janusd this time.** v2026.10.14-5's
   campaign left an open question: a node answering while janusd had no
   HAProxy running. The processes were listed every 3 seconds through
   two runs of the same kind of test: never more than one, except for
   the moment of a reload. It is still not reproduced, and stays open.

What the pre-release brings: v2026.10.14-5, plus the kernel parameters
put back when HAProxy can't run at the machine's size -
[its notes](https://github.com/swenske/Janus/releases/tag/v2026.10.14-6).

### Auto-scaling: the kernel parameters put back with HAProxy down

The machine: created by the lab's Controller from the pre-release's
image for this test - 2 vCPU and 1 GiB, room for 4 vCPU and 2 GiB,
HAProxy answering by itself, probes on its HTTP port throughout. Created
and serving in 9 s.

| Step | What happened |
|---|---|
| A policy (on, up to 4 vCPU and 2 GiB, the kernel parameters following) | the one restart: HTTP unanswered 7.1 s |
| The three-cache configuration, applied until it runs | refused twice, then accepted; OOM kills and memory pressure grew the machine 1024 → 1280 → 1664 → 2048 MiB in 2 minutes; `tcp_mem` 10869 14493 21738 → 23052 30739 46105 and `fs.file-max` 88969 → 188700 by the same steps |
| **Paused** | back to 1024 MiB in 16 s. HAProxy can't run there: the kernel kills each start. Then *fs.file-max 188700 → 88969 (back at its size); net.ipv4.tcp_mem 23052 30739 46105 → 10869 14493 21738* - **confirmed**, no error, and the same values 3 minutes later, past the trial's 2 minutes |
| On again | grown back to 2048 MiB (OOM kills, then memory pressure), the parameters following again |
| **The policy removed at 2048 MiB** | *auto-scaling: kernel parameters applied: fs.file-max 188700 → 88969 (back at its size); net.ipv4.tcp_mem … → 10869 14493 21738* before the restart; after it, the node's own values for 1 GiB (11649 15532 23298, 95654) |

The outages were the configuration's own doing and the restarts:
- the policy's restart: 7.1 s;
- paused at 1 GiB, the configuration can't run until the machine grew
  back: 228 s;
- the removal's restart, then the configuration at 1 GiB until it was
  replaced: 23.4 s.

A first run, on the machine of the earlier campaigns, changed no
parameter. As designed: their values had been reset by hand the night
before, and auto-scaling never touches a parameter someone else
confirmed. Hence the fresh machine.

The record of what auto-scaling changed survives the policy's removal,
as #98 intends. After a put-back that succeeded, it still shows the
raised values. It puts nothing back from them: a value goes back only
while the node still has the raised one.

HAProxy's processes were listed every 3 seconds through both runs:
never two processes at once, except for the moment of a reload.
