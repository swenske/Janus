# v2026.11.18 pre-release tests

Tested on 2026-11-18, the morning it came out, on the lab where
v2026.11.17-2 - the newest release - was measured first, the same
morning, with the same clients ([v2026.11.17-2's
report](v2026.11.17-2.md)). What the pre-release changes:

- **`option idle-close-on-response`** in a new node's bootstrap
  configuration and the examples (#675): at a reload the previous
  HAProxy no longer closes the idle keep-alive connections at once, so
  a proxy or a balancer in front reusing its connections stops meeting
  resets;
- **a stop for good doesn't wait for idle clients** (#675): before a
  reboot, a shutdown or an update's reboot, janusd waits only for the
  requests HAProxy is serving, not up to 5 s for every open client
  connection;
- **Linux 7.3.5** (the default track) and **6.18.64** (longterm),
  **AWS-LC 5.15.0** for HAProxy, **Docker Compose v5.8.0** in the
  Controller's updater (#676).

The lab's configuration doesn't have the option (an applied
configuration replaces the bootstrap), which is what made the first
two measurable: HAProxy reloads on node 01 under a keep-alive load,
without and with the line added to its `defaults`, from the build box
straight to the VIP and through an HAProxy in front of the VIP reusing
its connections; and a reboot of node 02 with an idle keep-alive client
open on it and a slow request, janusd's own stop timing read off its
serial console - each on the release first, then on the pre-release.
Then the core campaign: the Controller's update through its updater,
the image factory, the cluster of both nodes updated in place under
load, a VRRP and a BGP failover, firmware and kexec boots on both
kernel tracks with their stages, a rollback and back, HAProxy's cost
per request with the release and the pre-release alternated on node 01
by rollbacks, the pages and the nodes' health.

The lab's nodes ran v2026.11.17, not the release, at the start: both
were first updated in place to v2026.11.17-2 by a cluster (37.0 s, no
load), and the Controller's longterm machine through its record, so
that every baseline figure below is v2026.11.17-2's.

## Verdict

**What the pre-release changes works on the lab. Over 24 reloads of
node 01 under load with the option, no client request failed - neither
`wrk` straight on the VIP nor the HAProxy in front reusing its
connections - against 18 read errors and 30 failed relayed requests
over 24 reloads without it, on the same pre-release the same morning.
With an idle keep-alive client open on node 02, its reboot's HAProxy
stop took 2.12 s - the 2 s drain alone - instead of 7.02 s on the
release, the node back 4.8 s sooner; a request in flight at the
soft-stop got its 200 with `Connection: close`. Compose in the updater
says v5.8.0. The kernels, AWS-LC and the rest are as before: the
cluster updated in place in 36.8 s without a lost probe, the same
failovers, boot times and cost per request, zero AVC denials, CIS
33/33 on every node, the pages with the release's buttons. My opinion:
ready to promote** - nothing found is the pre-release's; the decision
is yours.

## HAProxy reloads under keep-alive (#675)

Four reloads of node 01, 8 s apart (each a configuration applied with
a changing comment), under two loads at once from the build box: `wrk
-t1 -c8` straight on the VIP, reusing its connections, and `wrk -t1
-c8` through an HAProxy 3.4.7 on the box in front of the VIP with
`http-reuse always` - a balancer reusing its keep-alive connections, the
way #675 measured it; the relay's backend counters tell its failed
requests (`eresp`, `srv_abrt`). VIP and anycast probes every 50 ms
throughout. "With" = the line added to the lab configuration's
`defaults` and applied before the first reload (the previous process's
configuration is the one that decides).

| | Direct `wrk`: read errors | Through the relay: failed requests | Probes lost (VIP / anycast) |
|---|---|---|---|
| v2026.11.17-2, without | 7 (13,707 req/s) | 6 (12,310 req/s) | 0 / 0 |
| v2026.11.17-2, with | **0** (13,397 req/s) | **0** (12,296 req/s) | 0 / 0 |
| v2026.11.18, without | 2 (13,647 req/s) | 10 (12,650 req/s) | 0 / 0 |
| v2026.11.18, with | **0** (13,588 req/s) | **0** (12,456 req/s) | 0 / 0 |
| v2026.11.18, 20 reloads, without | 16 (13,203 req/s) | 20 of 2,145,602 (11,788 req/s) | 1 of 3,299 / 0 |
| v2026.11.18, 20 reloads, with | **0** (13,605 req/s) | **0** of 2,237,795 (12,294 req/s) | 0 / 0 |

Each failed relayed request was a server abort on a reused connection
(`eresp` = `srv_abrt`), handed to the relay's client as a closed
connection. The option is HAProxy's own, so the release with the line
added behaves the same: what the pre-release changes is that a new
node starts with it, and the docs say to add it. The one probe lost
without the option opened a new connection during the 13th reload -
the case #675 leaves aside (a fresh connection lost in the previous
listener's accept queue). Throughput is the same with and without.

**The option stays in the lab's configuration** (both nodes'
`defaults`): nothing broke with it.

## HAProxy's stop at a reboot (#675)

Node 02 with the option and a `/slow` path HAProxy holds 4 s (`timeout
tarpit 4s`, `http-request tarpit deny_status 200`); a Python client
sends one keep-alive request to node 02's front address and keeps the
connection idle; then node 02 rebooted through its firmware, the API
polled every 0.1 s, and janusd's "rebooting now - haproxy stopped …"
line read off the node's serial console. Node 02 holds BGP and
keepalived, so its stop always starts with HAProxy's 2 s drain.

| | v2026.11.17-2 | v2026.11.18 |
|---|---|---|
| No client (the boot-stage reboots) | haproxy stopped 2.12 s | 2.11 s |
| **An idle keep-alive client** | **haproxy stopped 7.02 s**; the API back 15.5 s after the call | **2.12 s**; the API back **10.7 s** after the call |
| The idle client and `/slow` sent 1 s before the call | 7.02 s; `/slow` answered 200 after 4.00 s; the API back 15.6 s | 2.12 s; `/slow` answered 200 after 4.00 s (both answered during the drain, before the soft-stop); the API back 42.7 s (below) |
| The idle client and `/slow` sent 3.5 s after the call (in flight at the soft-stop) | - | **5.52 s** (the drain, then the request); `/slow` answered **200 with `Connection: close`** after 4.00 s and closed; the idle client closed 0.05 s later |

The 42.7 s are not the stop's: janusd logged "rebooting now" on time,
and about 36 s passed between the kernel's "machine restart" and the
next kernel starting - the firmware or the host. The six other
firmware reboots of node 02 on the pre-release (two boot-stage
reboots, the other two stop tests, two rollbacks) took 10.0 to
13.4 s; the lab has seen such an occasional slow restart before.

## Findings

None in the pre-release. Worth knowing:

1. **One slow firmware restart** of node 02 (42.7 s instead of about
   10 s): the stop was on time, the time went between the kernel's
   restart and the next kernel. Not seen in the six other firmware
   reboots of node 02 that morning; the lab has had such restarts
   before.
2. **Without the option, a fresh connection can still meet a reload**:
   one VIP probe out of 3,299 over 20 reloads - #675 leaves it aside;
   with the option, none out of 3,324.
3. My first two throughput runs of the release from the CI runner
   overlapped the schematic builds my own factory requests had just
   started on the runners: discarded and run again.

  (no drain delay).

  measured on the pre-release only.
