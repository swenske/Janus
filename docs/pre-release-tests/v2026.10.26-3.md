# v2026.10.26-3 pre-release tests

Tested late on 2026-10-26. It is [v2026.10.26-2](v2026.10.26-2.md) with
one change: **an IPv6 anycast `/128` is never the source of the node's
own connections** - added deprecated from the start
([#345](https://github.com/swenske/Janus/pull/345)).

The same lab as the campaigns before; its HAProxy and kernel unchanged.

## Verdict

**Ready to promote.** The defect #345 fixes - found before announcing an
IPv6 anycast address on a production cluster - was reproduced on the lab
with v2026.10.26-2 first, and is gone:

- **The nodes' own IPv6 connections**: with v2026.10.26-2, both nodes'
  left from the anycast address - node 01's failed **2 of 3** times, its
  replies going to node 02 by the router's ECMP; with v2026.10.26-3,
  **6 of 6** succeeded, from each node's own address.
- **The anycast address itself**: still answered by both nodes (0 lost
  of 534 with node 01's HAProxy stopped 8 s in the middle).
- **The baseline**: the rolling update under load lost **nothing** on
  the VIP nor on the anycast address; HAProxy's throughput level with
  v2026.10.26-2's; zero AVC denials, the CIS audit 33/33.

## What this pre-release changes

### The nodes' own IPv6 connections with an anycast `/128` (#345)

The [IPv6 anycast setup](v2026.10.26-2.md#the-same-ipv6-anycast-address-on-both-nodes-342)
of v2026.10.26-2's campaign, plus a backend address the source rule ties
on - it shares as few leading bits with the nodes' front `/64` as with
the anycast prefix, as an internet address does -, routed by the lab's
router. Each node opened three TCP connections to it (its SSH port)
through the router; the connecting socket's local address read on the
node. Set on v2026.10.26-2; the rolling update then took both nodes to
v2026.10.26-3 with it in place.

| | v2026.10.26-2 | v2026.10.26-3 |
|---|---|---|
| The `/128` on both nodes (`/proc/net/if_inet6` flags) | permanent, `nodad` | permanent, `nodad`, **deprecated** |
| Node 01's connections | from **the anycast address**; **2 of 3 failed** - the backend's replies went to node 02 | 3 of 3, from its own address |
| Node 02's connections | from the anycast address; 3 of 3 by the hash's luck | 3 of 3, from its own address |
| The anycast address, asked from a backend every 50 ms for 30 s, node 01's HAProxy stopped 8 s | 0 lost of 364 | 0 lost of 534 |

A first try with a backend address in a prefix nearer the nodes' `/64`
picked the `/64` on the longest-prefix rule: the defect shows only where
that rule ties - for most of the internet.
