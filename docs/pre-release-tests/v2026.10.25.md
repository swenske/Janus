# v2026.10.25 pre-release tests

Tested in the evening of 2026-10-25. It is
[v2026.10.24-6](v2026.10.24-6.md) with:

- Terraform's `janus_cluster`: a cluster of new machines on the
  Controller's hypervisors, its members and auto-scaling changed in place
  ([#299](https://github.com/swenske/Janus/pull/299));
- the auto-scaling policy's durations in seconds in the API, the
  nanosecond names v2026.10.24-6 used still read (#299);
- a cluster's machines placed where there is the most memory, never on
  a host without room for them
  ([#300](https://github.com/swenske/Janus/pull/300));
- the journal naming a new machine's hypervisor by its name
  ([#297](https://github.com/swenske/Janus/pull/297)).

The same kernel and HAProxy as v2026.10.24-6. **The lab changed since**:
its virtual machines are spread over its two KVM hosts - the 16 GB one
keeps node 01, one backend and the Controller's two machines; the 32 GB
one runs the Controller, node 02, the other backend and the screen-only
node - and four machines the Controller kept from older campaigns were
destroyed. The 32 GB host's disks are plain SATA drives without a write
cache: a synchronous 4 KiB write takes 29 to 61 ms in its machines,
0.5 ms on the 16 GB host (a RAID controller with its cache). The
baseline compares with [v2026.10.24-6](v2026.10.24-6.md)'s figures,
then what this pre-release changes.

## Verdict

**Not ready as is: one regression in what it changes.** With
anti-affinity *preferred*, recycling a member alone on its host put the
replacement **beside another member** - the cluster then on one host -
where the replaced member's host would have been its own once the
member left ([finding 1](#findings)). #300 brought it; the fix is
[#305](https://github.com/swenske/Janus/pull/305). Anti-affinity
*required* (the default) and *off* place as they should.

Everything else holds:

- **`janus_cluster`** (#299), with OpenTofu against the lab's
  Controller:
  - a cluster of two machines was made with one on each host;
  - a third member with anti-affinity required was refused with the
    reason, nothing made;
  - changing the anti-affinity replaced the cluster;
  - it was scaled 2 → 3 → 2 in place;
  - auto-scaling was set and removed in place;
  - a plan after each step had nothing to change;
  - destroy took the cluster and its machines.
- **Placement by memory** (#300):
  - with anti-affinity off, three machines all went to the 32 GB host,
    though the 16 GB host was listed first;
  - with preferred, one per host first, then the emptier host;
  - a 12 GiB machine went to the only host with room for it;
  - requests no host could take were **refused at once** (400), each
    host's memory named, nothing made.
- **The policy in seconds**: the `*_seconds` names were read and given
  back; the old nanosecond names were still read.

**Nothing regressed in the baseline**:

- **Rolling update under load**: the only request lost on the VIP was
  an isolated one, 110 s after the rolling ended.
- **Firmware reboots**: six, 9.3 to 9.8 s each - the intermittent slow
  reboot wasn't seen.
- The failovers, kexec, the rollback, the factory and the Controller's
  machines are level with v2026.10.24-6.
- Throughput is higher from one client and about 5 % lower from three.
- Zero AVC denials; the CIS audit 33/33.

The Controller's own update left it unanswered for 4.2 s instead of
0.6 s, and node 02's update reboot took 2.8 s more. Both machines moved
to the slower disks today ([finding 4](#findings)).

A pre-release with #305 - and
[#303](https://github.com/swenske/Janus/pull/303), which fixes two
older findings - needs only the recycle checked again.

## Findings

1. **A recycle with anti-affinity preferred shares a host it needn't.**
   A cluster of two members, one on each host; recycling the member
   alone on the 16 GB host put its replacement on the 32 GB host, beside
   the other member. The cluster's page then said "tfc-1 and tfc-3 run
   on the same host: losing it stops them all", and the 16 GB host was
   left empty. #300 tries the hosts other than the replaced member's
   first - that one frees its memory only once the member leaves - and
   falls back to it only when that placement fails. Preferred never
   fails: it shares a host instead. Before #300 the replaced member's
   host counted as free, and v2026.10.24-6's campaign saw the
   replacement go there. **A regression of this pre-release.**
   [#305](https://github.com/swenske/Janus/pull/305) falls back to the
   replaced member's host also when placing elsewhere means sharing one;
   its test reproduces the lab's case.
2. **A refused step out still answers 202**
   ([v2026.10.24-6's finding 2](v2026.10.24-6.md#findings)). Through
   Terraform the apply fails in 4 s with the reason, so nothing is lost.
   But the reason stays the cluster's error, and a problem on its page,
   until its next operation.
   [#303](https://github.com/swenske/Janus/pull/303) refuses it at once
   (400), with the old member's drain journaled once in a recycle -
   still twice here.
3. **Cosmetic:**
   - **A refusal for memory gives the memory left after the request's
     earlier machines without saying so.** Two 12 GiB machines with
     anti-affinity required gave "[the 32 GB host] 10813 MiB free". The
     host had 23,101 MiB; 10,813 is what the first machine of the same
     request would have left.
   - **A bound in a seconds field is written as a Go duration**:
     "out_after_seconds: 1m0s to 1h0m0s".
4. **The lab's second host has slow disks.** The 32 GB host's drives
   are plain 7,200 rpm SATA without a write cache: a synchronous 4 KiB
   write takes 29 ms in the Controller's machine and 61 ms in a backend,
   0.5 ms on the 16 GB host. Since today the Controller and node 02 run
   there, and three figures moved:
   - the Controller's update: the updater's stop, backup and start took
     4 s, where they took under a second;
   - node 02's update reboot: 2.8 s more;
   - janusd's shutdown hooks and disk sync before a reboot: up to
     298 ms and 51 ms on node 02, against 9 ms and 1 ms on node 01.

   Not this pre-release: the same steps on slower storage. Worth
   knowing before comparing node 02's figures with older campaigns.
5. **The virtio-net TX failures don't make a reboot slow alone.**
   v2026.10.24-6's slow reboot (43.7 s) was the only one whose console
   showed `net …: Unexpected TXQ (0) queue failure: -5` before the
   machine restarted. This time, with the console timestamped on the
   host, those lines appeared in two of node 02's four firmware reboots,
   in one of node 01's two and in node 01's kexec reboot - and none of
   them was slow (9.3 to 9.8 s through the firmware, 7.5 s through
   kexec).
   That is a fact for the slow reboot's follow-up
   ([#307](https://github.com/swenske/Janus/pull/307)).
