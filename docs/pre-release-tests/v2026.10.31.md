# v2026.10.31 pre-release tests

Tested in the night of 2026-10-30 to 31 and the morning after. It is
[v2026.10.30](https://github.com/swenske/Janus/releases/tag/v2026.10.30),
the release, with:

- [#437](https://github.com/swenske/Janus/pull/437): the VM images' UKIs
  signed with the release key, checked before publishing, and a Secure
  Boot guide;
- [#439](https://github.com/swenske/Janus/pull/439): a node says what its
  firmware does with Secure Boot (`janusctl version`, the Controller's
  machines);
- [#441](https://github.com/swenske/Janus/pull/441) and
  [#447](https://github.com/swenske/Janus/pull/447): the cluster engine
  tries its idempotent calls once more on a dead connection (fixes
  [#438](https://github.com/swenske/Janus/issues/438)), but not the boot
  time an update watches;
- [#436](https://github.com/swenske/Janus/pull/436): the VMware, bare
  metal and Raspberry Pi targets suspended;
- [#435](https://github.com/swenske/Janus/pull/435): a release published
  only once complete, never changed by a re-run;
- [#442](https://github.com/swenske/Janus/pull/442) and
  [#444](https://github.com/swenske/Janus/pull/444): the dependencies
  (Alpine 3.24.3, Debian, Go 1.27.3, npm), and HAProxy's source from
  distfiles mirrors when haproxy.org doesn't answer;
- [#445](https://github.com/swenske/Janus/pull/445): tight BGP timers in
  the BGP cluster update test.

## Verdict

**Ready to promote**, in my opinion. On the lab's real nodes:

- **The baseline holds**: failovers, firmware and kexec reboots, the
  rollback, at the level of the release measured the same night.
  HAProxy's throughput is the release's: an alternating A/B on one node
  gives the same requests per second and the same CPU per request.
  Zero AVC denials and the CIS audit 33/33 on every node.
- **#438 is fixed**: an undrain sent the moment a rebooted member
  answers failed **5 times out of 6** with the release's Controller
  (`connection reset by peer`), and went through **6 times out of 6**
  with the pre-release's.
- **A member that comes back on its old slot is seen** (#447): its
  update made to fail on the lab, the Controller reported the revert
  24 s after the reboot and left the other member alone.
- **Secure Boot**: the published qcow2s carry three signed UKIs each. A
  machine booted from one with Secure Boot enforced (the release
  certificate as PK, KEK and db, the flash locked to SMM) runs, says
  `Secure Boot: on`, reboots and rolls back with it on. The release's
  image, unsigned, is refused by the same firmware. The lab's nodes say
  `Secure Boot: off`, and the Controller shows the crossed-out shield on
  its machines.
- **The cluster updated in place** under load: anycast 0 lost, the VIP
  2 probes out of 5,453.

Two minor findings, neither in the way of a promotion, and the lab's own Logstash target ([Findings](#findings)).

## What this pre-release changes

### An undrain right after a reboot (#441, #438)

The bug: the Controller undrains a cluster member the moment the member
answers after a reboot, and the call fails with `connection reset by
peer`; a second call works. The Controller had sent it on its gRPC
connection from before the reboot.

On the lab: node 02 drained through the Controller's API, rebooted, and
undrained through the API as soon as its janusd answered again (its
port polled every 0.1 s, then `janusctl version`), with no load:

| The lab's Controller on | Reboot | First undrain | Sent after the API answered |
|---|---|---|---|
| v2026.10.30 | kexec, 3 times | **failed 3 times**: `read tcp …:9505: read: connection reset by peer` | 0.02 to 0.03 s |
| v2026.10.30 | firmware, 3 times | failed 2 times, went through once (the first) | 0.02 to 0.03 s |
| v2026.10.31 | kexec, 3 times | **went through 3 times** | 0.02 to 0.04 s |
| v2026.10.31 | firmware, 3 times | **went through 3 times** | 0.02 to 0.03 s |

Each failure was in the cluster's journal and its error; the member
stayed drained until a second undrain. On the pre-release, the journal
holds one undrain each time, and no error.

### A member back on its old slot (#447)

[#447](https://github.com/swenske/Janus/pull/447) came from the second build's failure: with #441, the boot time
that an update watches was retried too, and a member that rebooted fast
onto its old slot looked as if it had never rebooted. The update then
waited for its timeout.

On the lab, the cluster was updated in place from v2026.10.31 to
v2026.10.30, node 02 first. The moment node 02's janusd answered on
its new slot, 5 s after it went down, the VM was destroyed and started
again. The new slot had used its only try (`TriesLeft` 1) and never
confirmed healthy, so init switched back: `boot-commit for slot B
never confirmed after its one attempt - reverting to slot A`.

- The Controller's journal: `lab-janus-02 reverted to Janus v2026.10.31
  on slot A`, **24 s after the reboot**; then node 02 undrained and
  announcing its routes again.
- The update stopped there, with its error: "lab-janus-02 reverted to
  Janus v2026.10.31: the new release didn't confirm healthy on it … the
  members after it left alone". Node 01 was not touched.
- Both nodes on v2026.10.31 after: node 02 on slot A, its slot B holding
  v2026.10.30.

### Secure Boot (#437, #439)

**The images.** `hack/uki-verify.sh` with the release certificate, on
the build box:

- the pre-release's `janus.qcow2` and `janus-kvm.qcow2`: the three UKIs
  of each **signed**;
- the release's `janus.qcow2` (v2026.10.30): `BOOTX64.EFI isn't signed`.

**A machine with Secure Boot enforced**, made by hand on the lab's
second hypervisor as the guide's libvirt section says:
`OVMF_CODE_4M.secboot.fd`, the flash locked to SMM (`secure='yes'`,
`smm on`), and a variable store written by
`image/secureboot/enroll-vars.sh` with the release certificate as PK,
KEK and db; one network interface, no Controller:

- from the release's image: the firmware refused it, `failed to load
  Boot0001 … Access Denied`;
- from the pre-release's `janus.qcow2`: it booted. `janusctl version`:
  **`Secure Boot: on`**; the kernel: `Secure boot enabled`; HAProxy
  answering;
- a firmware reboot (API back in 7.8 s) and a rollback to slot B
  (7.2 s): still on, HAProxy answering, zero AVC denials;
- no kexec on it: with the flash locked to SMM under OVMF 2025.02, a
  kexec reboot is the known failure the guide names. The machine was
  destroyed after.

**Where it shows.** `janusctl version` on nodes 01 and 02 (v2026.10.31,
no Secure Boot): `Secure Boot: off`. The Controller's two machines:

- on v2026.10.28-2: no `secure_boot` in `GET /api/machines`, and no
  badge on Hypervisors › Machines;
- updated to the pre-release through the Controller (73.8 s each, side
  by side): `secure_boot: "off"`, and the crossed-out shield on both
  cards.

The page in headless Chromium, light and dark: no console error, no
failed request, axe clean.

### The cluster updated in place

The cluster of the lab's two nodes was made on v2026.10.30 by the lab's
Controller on v2026.10.30 (12.1 s): a stick table replicated between
them, then VRRP from a template. Once the Controller was on the
pre-release, the cluster was updated in place under load (`wrk` on the
VIP and the probes from the build box):

- **81.5 s** from the call to the end. Node 02 (the backup) first:
  drained, updated, rebooted on slot A, undrained 11.5 s after the
  reboot and announcing 2 s later. Then node 01: drained at 06:42:53,
  rebooting at 06:42:54, its janusd up at 06:43:37, undrained at
  06:43:56.
- **VIP: 2 lost out of 5,453**, 0.05 s each: one during node 02's
  reboot, while node 01 held the VIP, one 3.5 minutes after the update
  ended. The path's noise, as in the campaigns before. **Anycast: 0 out of 5,450.**
- `wrk`: 13,418 req/s, p99 6.68 ms, 16 read errors.
- The stick table, the peers and BGP were back on both; no problem in
  the cluster's view.

Node 01's firmware reboot took 43 s, against 11 s for node 02's
([finding 2](#findings)). From janusd's start to the undrain, the
update's wait loop took 19 s: it polls every 2 s, and a call to a node
that is still away can wait 10 s.

### Suspended targets (#436)

The image factory (janus.sw-servers.net), for v2026.10.31:

- its platforms: the VMware VMDK, the bare-metal ISO and both Raspberry
  Pi images marked `suspended`;
- the lab's schematic for arm64: `unavailable`, its extensions are for
  amd64 only; a schematic made for the test (`console: screen`) for
  arm64: `unavailable`, "HAProxy 3.4 isn't available for arm64 (only
  [amd64])". No build was started: v2026.10.31's catalog has no arm64
  inputs at all, so a request is turned down before it reaches the
  suspension's 409;
- the default schematic for arm64 answers `ready` with no file
  ([finding 1](#findings)).

## Findings

1. **The image factory calls the default schematic `ready` for arm64
   with nothing to download.** For the default schematic, the site's
   `status()` answers `ready` and lists the release's own assets for
   that architecture; v2026.10.31 has none for arm64, so the list is
   empty. The builder greys the Raspberry Pi targets out, so a person
   doesn't meet it; an API client does. Minor: it should say
   `unavailable` when no file is there.
2. **Firmware reboots of 42 to 43 s**: node 01's during the cluster's
   update, node 02's first one in the timed reboots, against 9.6 to
   11 s otherwise. The node's own start was fast: the
   time was the firmware's. The lab's machines keep their UEFI variables
   in a file that OVMF compacts every few dozen boots, the slow reboot
   seen in v2026.10.30's campaign (186 s) and root-caused on 2026-10-25
   ([#307](https://github.com/swenske/Janus/pull/307)). Not the
   pre-release.
3. The lab's log profile has a second target, a Logstash outside the
   lab's reach: `failing`, as in the campaigns before. It's how the lab
   is set up.

## Not tested

  Proxmox procedure isn't run here. A machine the Controller creates
  still has Secure Boot off (the notes' upgrade note).
- **kexec under Secure Boot**: not on the lab's Secure Boot machine, by
  design (the known OVMF 2025.02 failure with the flash locked to SMM).

The lab's Controller, nodes 01 and 02 and the Controller's two
machines on v2026.10.31. The cluster was deleted in 1.1 s, and each
node's `haproxy.cfg` was put back as it was before the cluster: its
other files had stayed identical. The Secure Boot machine was
destroyed, and the runners' load kit taken off.
