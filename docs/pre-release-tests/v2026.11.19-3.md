# v2026.11.19-3 pre-release tests

Tested on 2026-11-19, the evening it came out, on the lab where
v2026.11.19-2 - the newest release - was measured first, the same
evening, with the same clients ([v2026.11.19-2's
report](v2026.11.19-2.md)). What the pre-release changes: HAProxy
alone, in every branch it ships (#689) - **3.4.8, 3.2.27 and 3.0.31**,
each fixing four vulnerabilities rated high (two in HTTP/2, one in
buffer moves, one in the cache) and, with them, how `peers` sections
synchronise and how an interrupted `commit ssl cert` ends. The kernels,
janusd, the Controller and its pages are v2026.11.19-2's.

And one upgrade note: HAProxy now refuses `cache-use` and
`cache-store` rules in a `defaults` section. The notes say such rules
never worked there, that a node whose configuration still has them
can't start HAProxy on the new release, and that with the Controller's
"Revert automatically" - on by default - the node goes back to its
previous slot by itself. That was the point of this campaign: a node
given those rules on the release, then updated through its page.

Then the rest of what HAProxy touches: the 3.0 and 3.2 branches built
by the image factory, a Controller machine on 3.0 updated to 3.0.31;
HTTP/2 over TLS through the VIP; the cluster of both nodes updated in
place under load, its stick tables learnt back, a certificate replaced
at runtime on its members; and a short core campaign - the
Controller's update, the factory, a node loss, a HAProxy stop, a
rollback and back, HAProxy's cost per request with the release and the
pre-release alternated, the nodes' health. No firmware or kexec boots
(the kernels didn't change) and no walk through the pages (they didn't
either).

## Verdict

**The upgrade note holds. On the release, the rules in a named
`defaults` section were accepted by `apply-config` - and HAProxy 3.4.7
crashed on the first request through them, then hung on the next. On
the pre-release, HAProxy refused to start with the note's message, the
node's health check gave up after its 60 s and the node was back on the
release by itself, 70 s after the click, nothing lost but the update;
with the rules moved into the backend, the same update went through,
and the pre-release's `apply-config` refuses the old configuration
without touching the node. The 3.0 machine went from 3.0.30 to 3.0.31,
the factory built both pinned branches in well under a minute, HTTP/2
served without an error at the release's rate, and the cluster updated
in place in 40.3 s without a lost probe, its tables carried through
both reboots; a certificate replaced on its members kept HAProxy's
processes. Everything else measured as on the release. One finding,
not a regression: the Update page announces "Back on v2026.11.19-3"
eight seconds after the click and says nothing when the node goes
back a minute later. My opinion: ready to promote** - the decision is
yours.

## `cache-use` in a `defaults` section

On the Controller's longterm machine, outside any cluster, through its
node page (the same `ValidateConfig` and `ApplyConfig` calls as
`janusctl haproxy apply-config`). The configuration added to the
node's own:

```haproxy
defaults web
    mode http
    timeout connect 5s
    timeout client 30s
    timeout server 30s
    http-request cache-use c
    http-response cache-store c

cache c
    total-max-size 4
    max-age 60

frontend cache-test from web
    bind *:8081
    default_backend cache-test-be
```

An **anonymous** `defaults` section with these lines is refused by the
release already - HAProxy 3.4.7 says "'http-request' not allowed in
anonymous 'defaults' section" -, so the note's case is a **named**
section, used by a frontend with `from` (a frontend and a backend can't
both inherit rules from the same one, the release says too).

### On the release

| | v2026.11.19-2 (HAProxy 3.4.7) |
|---|---|
| Validation | `valid` |
| `apply-config` | accepted, applied |
| The first requests through the frontend | **HAProxy crashed** (a segmentation fault), janusd started it again after 1 s; the next request left a thread stuck in the `cache-use` rule until HAProxy's watchdog killed the process ("thread 1 has stopped processing traffic" five times, then "PANIC! Thread 1 is about to kill the process"), started again after 2 s |

What the notes say - "such rules never worked there - HAProxy crashed,
or cached nothing" - is what the lab saw. The 3.0 machine's 3.0.30
validated the same configuration too.

### The update with the rules still there

Through the node page's Update, in headless Chromium, the bundle the
image factory built for the machine's schematic, "Revert automatically
if HAProxy isn't healthy after the reboot" ticked as the page has it,
60 s, a firmware reboot. Done twice, the second time with the page
followed for two more minutes:

| From the click | First | Second |
|---|---|---|
| Bundle written, the node rebooting | +0.4 s | +0.4 s |
| janusd v2026.11.19-3 listening, "bootcommit: confirming health for slot B (revert to A if it never comes up)" | +5 s | +5 s |
| The page: "Back on v2026.11.19-3 (slot B)" (a green toast) | **+8.2 s** | **+8.2 s** |
| HAProxy 3.4.8 refusing to start, tried again after 1, 2, 4, 8, 16 and 30 s | from +5 s | from +5 s |
| The node's event `bootcommit.reverted` (slot B → A) | +66 s (61 s after the boot) | +66 s |
| **The node back on v2026.11.19-2, slot A, HAProxy 3.4.7** | **+69.8 s** | about +71 s (the page's next poll) |

Each attempt on the new slot logged HAProxy's own words:

```text
[ALERT] config : parsing [/etc/haproxy/haproxy.cfg:25] : error detected in defaults 'web' while parsing 'http-request cache-use' rule : 'cache-use' rules are not supported in a defaults section.
```

in janusd's log, in HAProxy's log, and as `haproxy.restart_failed`
events ("refused to start") - the node page's Events and the
diagnostic bundle show them. No AVC denial on the failed boot. The
node came back with its configuration and its other slot holding
v2026.11.19-3; nobody touched it.

**What the page shows**: during the minute on the new slot, its header
has HAProxy in red and "v2026.11.19-3 pre-release"; the green toast
"Back on v2026.11.19-3 (slot B)" has already said the update went
through. When the node goes back, the "This node" card turns to
v2026.11.19-2 on slot A, the other slot v2026.11.19-3 with HAProxy
3.4.8 - **with no word that the update was reverted**: no toast, no
warning. The page's follow ends when janusd answers on the new
version; the health check runs a minute longer.

### Then as the notes say

| Step | Result |
|---|---|
| The rules moved into the backend (`backend cache-test-be`: `http-request cache-use c`, `http-response cache-store c`), applied on the release | accepted; the frontend answers 200, no crash |
| The same update through the page | "Back on v2026.11.19-3 (slot B)" at +8.0 s, "bootcommit: confirmed healthy for slot B" two seconds after the boot; followed 90 s: stays, HAProxy **3.4.8** |
| The configuration with the rules in `defaults web`, on the pre-release: validation | refused, with the note's message |
| The same through `apply-config` | **`rejected`** (`accepted: false`, the same message); the node's configuration unchanged (same SHA-256 before and after), HAProxy not reloaded |

The machine's configuration was then put back as it was.

The cluster of both nodes, made on the release (1.9 s) with a stick
table on the web frontend replicated by its `peers` section (applied in
11.3 s), then updated in place to the pre-release under `wrk` and the
VIP and anycast probes from the build box, the router watched:

| | v2026.11.19-2 (its campaign, from v2026.11.18) | v2026.11.19-3 |
|---|---|---|
| The cluster updated in place | 41.1 s | **40.3 s** |
| Probes lost, VIP / anycast | 0 of 3,299 / 0 of 3,297 | **0 of 3,305 / 0 of 3,302** |
| `wrk` (8 connections, the VIP) | 13,913 req/s, p99 3.95 ms, 16 read errors | 13,414 req/s, p99 8.33 ms, max 422 ms, 16 read errors (the VIP's moves) |

Node 02 was drained and rebooted first (back on slot A at +18.2 s),
then node 01 (drained at +21.5 s, back on slot B at +39.6 s); the router
dropped and took back each node's anycast route (02: +2.4 to +18.3 s,
01: +18.6 to +39.6 s), and the VIP's MAC moved at +19.3 and +40.4 s.
**The tables came through**: after both reboots, the client's key
counted 2,415,789 requests on node 01 and on node 02 alike - the whole
load, nothing lost -, both members with their peer up and their tables
synced, both on HAProxy 3.4.8.

**Certificates at runtime.** A member certificate is renewed by the
Controller at half its life, and nothing renews a new one on demand:
"Check now" ran and had nothing to renew. The same runtime path - the

given again under the same name with a new key and a later end:

| | v2026.11.19-2 | v2026.11.19-3 |
|---|---|---|

| HAProxy's process on each member | **unchanged** | **unchanged** |

The certificate also survived both reboots of the in-place update (the
node's certificate store gives it back to each new HAProxy). The
cluster was then deleted (1.1 s), the certificate removed, and both

## Findings

None in the pre-release. Worth knowing:

1. **The Update page doesn't say a revert happened.** With "Revert
   automatically", the page announces "Back on <new version>" (green)
   as soon as janusd answers on the new slot, about 8 s after the
   click, and stops following; the health check goes on for its 60 s,
   and when the node goes back the page only shows the old version
   again, without a word. Someone following the notes' upgrade note
   sees a success, then an unexplained old version. The node does the
   right thing; the page should wait for the health check's outcome (or
   say it is still pending) and say when the node reverted. Not this
   release's: the page is v2026.11.19-2's, and the release has the same
   behaviour.
2. **The note's case is a named `defaults` section**: an anonymous one
   with `http-request` or `http-response` rules was already refused
   before this release. The note is right as written ("in a `defaults`
   section"); a user checking with `get-config` only needs to look at
   the named ones.
3. **A fresh cluster's member certificate can't be renewed on demand**:
   the renewal itself was measured through the same runtime path with
   another certificate, not with `member.pem`.
