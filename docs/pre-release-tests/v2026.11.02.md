# v2026.11.02 pre-release tests

Tested on 2026-11-02, the morning the pre-release came out. Against
[v2026.10.31-4](v2026.10.31-4.md), the latest release, it brings
(#459-#474):

- **the pairing code**: a new node makes its CA and its server
  certificate only - no admin credential, no key on its console - and
  shows a one-time code; the Controller's **Add node** and `janusctl
  fleet adopt -code` pair it
  ([#465](https://github.com/swenske/Janus/pull/465),
  [#466](https://github.com/swenske/Janus/pull/466),
  [#469](https://github.com/swenske/Janus/pull/469));
- **the rescue volume**: a `JANUSRESCUE` volume opens a 30-minute window
  whatever the node trusts; `janusctl access rescue` gets an hour's admin
  certificate of the node's own CA
  ([#468](https://github.com/swenske/Janus/pull/468));
- **`janusctl login -kit`**: with the Controller down, an hour's
  certificate signed with the fleet's recovery kit; a restore on another
  host follows it ([#463](https://github.com/swenske/Janus/pull/463));
- **one Controller per data directory**
  ([#462](https://github.com/swenske/Janus/pull/462));
- **a warm standby** for the Controller, its epochs, and a **witness**
  in Consul's KV or the backups' bucket
  ([#470](https://github.com/swenske/Janus/pull/470),
  [#471](https://github.com/swenske/Janus/pull/471)), and a restore that
  seals the standby's files again
  ([#474](https://github.com/swenske/Janus/pull/474));
- **cluster updates** that wait for the balancer, pause between members
  and hand the open connections over (`nft dup`, new in the kernels)
  ([#461](https://github.com/swenske/Janus/pull/461));
- **a firewall ruleset confirmed just before a power cut is kept**, and
  the saved VRRP, BGP and Consul configurations
  ([#467](https://github.com/swenske/Janus/pull/467));
- **the LOGS tile** says how far back the logs go
  ([#460](https://github.com/swenske/Janus/pull/460)).

The campaign: the usual one first (the Controller's update, the image
factory, the cluster updated in place under load, boot stages through
the firmware and kexec, the rollback, failovers, a rebooting node seen
from the router, HAProxy's throughput as an A/B against v2026.10.31-4,
the nodes' health, the pages), then each new feature on the lab's real
nodes and Controller, with throwaway machines for what must start blank.

## Verdict

**Ready to promote, in my opinion - with one thing left untested**
(waiting for the balancer, below). On the lab:

- **The baseline holds**: the Controller's update (4.6 s without an
  answer), the cluster updated in place under load with nothing lost,
  the same boot stages through the firmware and kexec, a continuous
  rollback, the failovers and reboots as before, and HAProxy costing the
  same CPU per request as v2026.10.31-4 (an A/B by rollbacks).
- **A new node shows no key**: its whole first-boot console has no
  private key and no admin line; it shows a pairing code, refuses wrong
  ones with the tries left (a mistyped code costs none), and the
  Controller's Add node pairs it - its page relayed, its window closed
  30 s later, every try audited, the code in no log. Nodes updated from
  v2026.10.31-4 and a machine the Controller creates open no window.
- **The rescue volume** gives an hour's admin certificate of the node's
  own CA, every call audited under `rescue:<name>`; detached, no window.
- **`login -kit`** reaches every node with the Controller stopped, and
  the nodes log `kit:admin`; `-role os:reader` can't write.
- **The warm standby works end to end**: pairing, a copy every minute,
  switch-overs both ways in 1.7 s, a forced promotion behind a real
  partition, and the old active stepping down **through the Consul
  witness** 18 s after the promotion wrote it. The nodes saw nothing.
- **A restored Controller starts again** (#474): restored from its first
  page, listening 2.8 s later, signed in with the lab Controller's
  account.
- **The connection handoff keeps long connections**: 0 cut out of 479
  during a cluster update with it, against 77 out of 394 without it.
- **A ruleset confirmed half a second before a power cut is applied at
  the next boot**, twice.

Three findings, none in the way of a promotion: the handoff offered to
members on an older release (**already fixed on main by
[#475](https://github.com/swenske/Janus/pull/475)**), a misleading
"standby too" line for a minute after a switch-over, and a handoff copy
outliving its cluster ([Findings](#findings)). **Waiting for the
balancer** couldn't be tested: the cluster has no balancer hook, and
adding a read-only REST user on the lab's router was refused by the
session's own permission guard - the choice was checked to be greyed out
with its reason, nothing more ([Not tested](#not-tested)).

## What this pre-release changes

### The pairing code

A node made for the purpose from the image factory's v2026.11.02 image
of the lab's schematic (every extension), **with nothing provided**: no
NoCloud volume, one NIC on DHCP.

- Its first boot logged `pki: first boot - generated a new CA in
  /etc/janus/pki` and `pairing: the node trusts nothing yet - a pairing
  window on :9506`, and its console showed the code, in the banner too.
  **The whole serial log holds no `PRIVATE KEY` and no admin
  certificate line.** The API listened 3.5 s after the kernel started.
- Port 9506 answered with a certificate `CN=pairing <host>` issued by
  the node's CA; 9505 stayed mutual TLS.
- Through the Controller's Add node (its API, as the form calls it):
  - a code with one symbol changed: refused, "the pairing code doesn't
    check: a symbol mistyped" - **no try spent**;
  - a code with the right check symbol and a wrong secret: "a wrong
    pairing code - 4 tries left before the window closes", then "3 tries
    left";
  - the right code: added (201), its page relayed by the Controller,
    **port 9506 closed 30.5 s later**.
- The node's audit: the two refusals and `PairingService/Pair  pairing
  code ... OK, 243 ms`; its events: `access.paired` with the fleet's root
  and bundle version. janusd's log has the tries and `paired from ...`,
  **never the code**.
- Nodes 01, 02 and the Controller's two machines, updated from
  v2026.10.31-4: port 9506 closed, no `pairing` line.
- A machine the Controller created on a hypervisor from v2026.11.02's
  image: ready in 15 s, `first boot - generated a new CA`, admitted by
  self-registration, no pairing line, 9506 closed. Destroyed after.

### The rescue volume

On the same node: `janusctl image rescue-volume rescue.iso` (1 MiB,
label `JANUSRESCUE`), attached as a CD-ROM, the node restarted.

- Attached on a SCSI bus, libvirt added an LSI Logic controller the Janus
  kernel has no driver for: the CD wasn't seen. On a **SATA** bus: `init:
  rescue: a rescue volume on /dev/sr0`, `rescue: a rescue window on
  :9506 until 10:29:23Z`, the code in the banner ("rescue"). The docs'
  test uses virtio-scsi; a note in the guide that an LSI Logic bus won't
  do may help (not a defect of the release).
- `janusctl access rescue -endpoint ... -code ... -name campaign-66`:
  an `os:admin` certificate `CN=rescue:campaign-66` issued by the
  node's own CA for an hour; calls with it answered. The window closed
  (`the window on :9506 is closed: rescued`, port closed ~22 s later).
- The audit: `PairingService/Rescue  pairing code  OK`, then every call
  made with it under `rescue:campaign-66 (os:admin)` - reads
  included; the events `access.rescue_issued` and a change made with it
  `by: rescue:campaign-66`. The code is in no log.
- Detached and restarted: no rescue or pairing line, 9506 closed.

### A ruleset confirmed before a power cut

Still on that node (it has nftables): a ruleset applied and confirmed,
then the VM powered off hard **0.66 s** after the confirmation. At the
next boot: `firewall: applied the saved ruleset`, state running, saved,
the rule in place. Again with another ruleset, cut **0.48 s** after the
confirmation: the new one was applied, not the first. The node was
removed from the Controller and destroyed.

### `janusctl login -kit`

A test context (its own `JANUSCONFIG`, signed in with a temporary API
token, revoked after). The lab Controller stopped (outside any
measurement):

- `janusctl login -kit` with the fleet's recovery kit and passphrase:
  "a certificate the fleet's root signs, kit:admin (os:admin) until
  12:03 ... the Controller wasn't asked";
- `janusctl -all version`: the five nodes answered, the v2026.10.21 node
  included (two nodes made and destroyed earlier in the campaign were
  still in the context's list, unreachable);
- a change on two nodes: their log says `api:
  SystemService/ConsoleBudgetSet: kit:admin (os:admin, fleet)`, their
  audit the same;
- `-role os:reader`: reads answer, the change is refused ("requires role
  [os:admin], kit:admin has [os:reader]").

The Controller started again in 2 s; `janusctl login` as before.

### A restore on another host (#474)

A second Controller host (a Debian VM on the other hypervisor, Docker
from Debian), **its way out to every private network cut first**
(nftables), so that a copy of the lab's Controller couldn't reach its
nodes, hypervisors or log targets. A new Controller on a data volume of
its own; a backup downloaded from the lab Controller and the lab's
backup kit given to its first page's restore (the same call the page
makes): "64 files", **listening again 2.8 s later**, its identity renewed
for the new host and the `restore:` lines saying what still names the
old one. Signed in with the lab Controller's account (password and
TOTP): its five nodes listed. Meanwhile it tried the lab: **699
packets refused by the cut**. Stopped, its volume deleted, the cut
removed.

### The warm standby and the witness

The same host, a new data volume, the lab Controller's Compose service
(no updater):

- **Pairing**: a token from Settings › High availability, then
  `docker compose run --rm janus-controller standby -peer
  ACTIVE:8443 -pair TOKEN -address STANDBY:8443`: "Paired with ... as its
  standby, epoch 0 - a first copy of 69574 bytes". Started: its page says
  standby, `/api/ha/active` answers 503 on it and 200 on the active,
  `dashboardd ha status` shows a copy every minute, the active's card
  shows the standby, its last copy and its answer.
- **Switch over** from the active's card: the standby took over in
  **1.7 s** at epoch 1 on a copy the active handed over; the lab
  Controller's account signs in on it, the five node pages are relayed
  through it; the old active stepped down, set its data aside in
  `ha/previous/` and copied the new active a minute later. **Switch over
  back** from the new active's card: 1.7 s, epoch 2.
- **The witness**: a Consul 2.1.0 server on a third VM (neither
  Controller's host), HTTPS, ACLs denying by default, the Controller's
  policy as the guide has it; Settings › Consul pointed at it with a node
  selector that matches no node (Consul's catalog then held its own
  server only). Within seconds: the key `janus/controllers/<id>/witness`,
  the card "Witness - epoch 2, held by this Controller - consul ...", the
  standby copying the settings.
- (A first try of the partition below failed on my nftables syntax, so
  `dashboardd promote` ran with the active reachable: a normal promotion,
  the active handing over, epoch 3 written to the witness first. Switched
  back: epoch 4.)
- **A forced promotion behind a partition**: the link between the two
  Controllers cut both ways on the standby's host, both still reaching
  the witness. `dashboardd promote`: refused - "the active didn't hand
  over (... context deadline exceeded); the active answered 1m22s ago and
  didn't hand over: it may still run - stop it, wait 2m0s, or force the
  promotion" (exit 1). `promote -force`: "the active now, epoch 5 (the
  witness consul ... holds it), on the copy of 10:17:51Z (the last one
  pulled ...)". Two actives answered `/api/ha/active` for 11.9 s, then
  the old one logged **"ha: the witness says the peer ... is the active at
  epoch 5, above this Controller's 4 - stepping down"** - **18 s after the
  promotion wrote the witness** - and answered 503. Each `promote` call
  waited 60 s for the unreachable active before answering.
- **The link back**: the old active, now the standby, copied the new one
  (epoch 5) within a minute; the node pages were relayed by the new
  active.
- **Back to the base**: Switch over to the lab Controller (epoch 6),
  the standby removed, Settings › Consul back as it was (off), both VMs
  destroyed.

Through all of it the nodes saw nothing: their janusd start times
unchanged, their pages relayed by whichever Controller was active.

### Cluster updates: the connection handoff

The lab's cluster (nodes 01 and 02: BIRD, nftables, an anycast address
over BGP with the router's multipath, a VRRP VIP) has no balancer hook,
so **Wait for the balancer** is greyed out: "the cluster has no balancer
hook to ask". The handoff was offered.

A client on the build box kept **40 long connections** to the anycast
address - HTTP keep-alive, a request every 0.5 s, each connection held
40 s then replaced - and counted every connection that broke (a reset,
an early close, a timeout, a non-200). Idle, 25 s: 100 connections, none
cut. Then two updates in place, each changing the members' image so
there was something to update:

| | Without the handoff (HAProxy 3.2) | With the handoff (back to 3.4), a 10 s pause between members |
|---|---|---|
| The update | 101 s, 62 of them the factory's build; each member out ~16 s | 123.5 s: each member served its connections 40 s and 35 s before rebooting, then the pause |
| Long connections | **77 cut out of 394** (reset): 20 when node 02 was drained, 41 when it came back (the router's hash moved them to it), 16 when node 01 came back | **0 cut out of 479** |
| Probes, VIP / anycast | 0 of 6,616 / 2 of 6,612 lost | 2 of 8,654 / 3 of 8,650 lost |

The journal tells the sequence for each member: "node-01 copy
node-02's connections to it while it is out - 24 now", drained,
"node-02 has no connection left after 40s", rebooted, "node-02
copies the others' connections to them for 1h0m0s: node-01's 40",
undrained, "a pause of 10s before node-01 goes". The three anycast
probes lost each fell as a member started refusing new connections: the
dropped SYN is retried a second later, after the probe's 1-second
timeout - by design. `janusctl cluster get` showed the copy in effect
("Handoff: copying node-02's 0 connection(s) to it until ...").
After the handoff: zero AVC denials on both nodes.

## Findings

1. **The handoff offered to a cluster on an older release.** With both
   members on v2026.10.31-4, `GET .../upgrade-options` said the handoff
   was available - a member whose release predates it says nothing
   against it. An update with it stopped at once at the first member:
   "refusing new connections: unknown method ClusterHandoff ... - still
   in service on Janus v2026.10.31-4", nothing drained. Harmless, but
   updating a cluster onto this release is when anyone would first pick
   it. **Fixed on main by
   [#475](https://github.com/swenske/Janus/pull/475)** (`handoff_supported`,
   the choice greyed with "its release has no connection handoff"), after
   this pre-release.
2. **"The peer is a standby too" for a minute after a switch-over.** Right
   after switching back, the new standby's first look at its peer came as
   the peer was restarting as the active: `ha status` and the standby's
   log said "the peer ctl-a is a standby too, epoch 2: promote one of
   the two" until the next copy, a minute later - when nothing was to be
   done. Seen after both switch-overs to the lab Controller.
3. **A handoff copy outlives its cluster.** After the cluster was deleted,
   node 01 still copied node 02's connections - "copying node-02's 0
   connection(s) to it until 12:35:24 ... - last reading: this node is in
   no cluster": the hour's copy back after an update isn't stopped when
   the node leaves. It copies nothing and ends at its deadline.

Also, not this release: the v2026.10.21 node's page asks `/api/cluster`
and gets 501; every boot of a disk image logs `init: mount iso9660 on
/etc/janus/release: invalid argument` (the kernel's `ISOFS: Unable to
identify CD-ROM format`), as v2026.10.31-3's did; the lab's log profile's
Logstash target is out of the lab's reach (`failing`).

## Not tested

- **Waiting for the balancer.** It needs a balancer hook. The lab's
  anycast is BGP, which the RouterOS hook's read-only mode is made for:
  the engine reads the router's routes and writes none. Setting it up
  takes a REST service, a certificate and a read-only user on the lab's
  router (as v2026.10.25-3's campaign did); the session's permission guard
