# v2026.11.27 pre-release tests

Tested on 2026-11-28, the morning after it came out, on the lab where
v2026.11.24 - the newest release - was measured first, the same
morning, with the same clients ([v2026.11.24's
report](v2026.11.24.md)). What the pre-release changes:

- **HAProxy 3.4.9** on the default branch (was 3.4.8, 165 fixes),
  **3.2.28** and **3.0.32** on the pinned ones - among them the
  `peers` fixes (message sizes bounded, over-long string keys trimmed,
  string keys sharded on the stored key), `add ssl crt-list` keeping a
  certificate's settings, HTTP/2 timeouts and buffer allocations, and
  settings HAProxy used to accept now refused (the release notes'
  upgrade note);
- 🔒 **Docker Compose v5.8.1** in the Controller's updater, which the
  updater only gets from a `docker compose up -d` after the update;
- **the kernel with the EFI maintainer's kexec fix** (#716) in place of
  Janus's own, on both tracks, same versions (7.3.6 and 6.18.65).

So HAProxy came first: its version on every node, its throughput over
HTTP/1.1 and HTTP/2 and its cost per request, the reloads under new
connections and behind a keep-alive relay, the refused settings
before and after (and what an update does to a node that has one),
the cluster updated in place with a string-keyed table, a certificate
bound with a server name; then the Controller's update and the
`docker compose up -d` the notes ask for; the kernels' boots with the
EFI tables each boot was given, and an update by kexec; the other
branches on machines made for it; then the core campaign.

## Verdict

**Nothing regressed.** Every node reads **3.4.9-ab5581f** (3.0.32 and
3.2.28 on the pinned machines). Twenty reloads under about 12,000 new
connections a second failed no `wrk` request on either version, every
one handed over; behind a keep-alive relay, 0 and 0. Throughput and
cost per request moved inside the bench's spread over eight alternated
passes (keep-alive 37.5 against 37.3 µs per request, HTTP/2 49,300
against 49,334 requests a second). **The upgrade note holds**: 3.4.8
accepts every setting it names, 3.4.9 refuses every one with a clear
message, a configuration with one is refused before it is applied, and
a node updated with one went back to the release by itself 61 s after
its boot - but its Update page said "Back on v2026.11.27" and never
said the update was undone (as in v2026.11.19-3's campaign). The
cluster updated in place in 41.0 s, no probe lost, both tables -
the string-keyed one too - identical on both members after. The
kexec'd kernels now report the first boot's INITRD and memory
attributes tables `unusable`, the firmware boots list them as before,
with the same boot times, 0 AVC denials and CIS 33/33. The Controller
updated in 27.1 s; `docker compose up -d` recreated the updater alone,
with Compose v5.8.1 inside, without the Controller missing a probe.
**My opinion: ready to promote** - the decision is yours.

## Findings

None in the pre-release. Worth knowing:

1. **The Update page doesn't say an update went back.** A node that
   can't start HAProxy on the new release returns to the old one by
   itself (61 s after its boot here), but the page says "Back on
   v2026.11.27" as soon as janusd answers, then shows the old version
   without a word. Same as v2026.11.19-3's campaign; with this
   release's upgrade note, an operator relying on the page could
   believe a node updated that didn't. Worth an issue if there isn't
   one.
2. **The boot stages count HAProxy as up on that failed boot**
   ("haproxy 1.6s" in janusd's boot line), though the process exited
   at once: the stage is HAProxy's start, not its health.
3. **One firmware boot took about 32 s to reach the kernel** (the
   longterm machine's first boot of the new slot, with the refused
   setting); the same update minutes later and every other boot of the
   campaign were normal. Not the release's - the firmware, before
   Janus runs.
4. **New connections cost 4 % more CPU on the pre-release** over eight
   alternated passes (184.1 against 177.1 µs per request) while its
   rate was 5 % higher - inside the campaigns' spread; to watch.
