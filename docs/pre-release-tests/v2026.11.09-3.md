# v2026.11.09-3 pre-release tests

Tested on 2026-11-09, the evening it came out, on the lab whose
Controller and nodes ran v2026.11.09-2 - the newest release, promoted
that afternoon ([v2026.11.09-2's report](v2026.11.09-2.md)). The nodes'
kernel and janusd are v2026.11.09-2's; what the pre-release changes is
the Controller and the CI:

- **the releases' files kept on the Controller's disk and read
  together** (#610): each release's `security.json`, checksum and
  Controller image in `release-cache.json`, read back at start; those
  not read yet, eight at a time; "Prepare the pre-release" given 40
  seconds instead of 10;
- **the Update page shows the node's messages as they come** (#611),
  when the node downloads the release or takes uploaded files - a
  download asked again after a 504 included;
- **fewer CI reruns** (#612).

The campaign was the light one a Controller-only release takes: the
Controller's update and the image factory, the release cache through
restarts (a slow GitHub simulated), the Update page in the browser in
its three modes, then the core - the cluster updated in place under
load, a VRRP and a BGP failover, firmware reboots and kexec, a rollback
and back, the nodes' health, the Controller's pages in both themes.
The load and the probes came from the build box and one CI runner.

## Verdict

**What the pre-release changes works on the lab. The Update page now
shows each "trying again in 5s (2/5)" about 70 ms after the server's
504, then the writing, the reboot and the node back - in both themes,
without a JavaScript error; the Controller-push mode still works, and a
hardware refusal is a clear message on the page. After a restart the
Controller knows the newest release at its first answer, in 1.8 s
instead of 19.5 s, with one request to GitHub's API and no
`security.json` read again; without the file it reads them eight at a
time (4.3 s) and writes the same file back. The file holds public data
only. The core campaign is as before: the cluster updated in place
without a lost request (VIP 0 of 3,154, anycast 0 of 3,153), zero AVC
denials, CIS 33/33, the same boot times. My opinion: ready to
promote** - finding 1 is the one to read, a corner the cache doesn't
cover yet. The decision is yours.

- **The live progress** (#611): through a server answering 504 to each
  file's first request, the page showed `The node: verifying 10% - GET
  …/flaky/uki-b.efi: unexpected status 504 Gateway Timeout - trying
  again in 5s (2/5)`, then the same for `rootfs.verity` and
  `rootfs.squashfs`, then `writing-data 30% - writing rootfs.squashfs to
  slot B …`, "Rebooting into slot B (Janus v2026.11.09-3)" and "Back on
  v2026.11.09-3 (slot B)" - a message every second of the 15 s it
  worked, where v2026.11.09-2's page showed nothing until the end.
- **The release cache** (#610): restarts timed from `docker compose
  restart` to the first answer of the Controller's update status that
  names the newest release, its outgoing HTTPS captured: 19.5 s on
  v2026.11.09-2; 1.8 s on the pre-release with the file, one TLS
  connection (GitHub's API); 4.3 s without it, eight connections to
  GitHub opened together. With GitHub 1 s further away: 4.4 s with the
  file, 32 s without.
- **A cold start with a slow GitHub can lose the newest releases for
  minutes** (finding 1): with neither the file nor a fast GitHub, the
  30 s one read of the releases has were spent by the ~62
  `security.json`; the pre-release's own files then timed out, the
  pre-release was left out until the next read, and "Prepare the
  pre-release" answered 400 "v2026.11.09-3 isn't a release offered to
  this node - reload the page" until it came back 3 minutes later. With
  GitHub 4 s away and no file, the newest release itself stayed unknown
  for 5 minutes.
- **Upload mode shows nothing while the browser sends** (finding 2):
  the node's messages come once the files are on the node; the browser
  limited to 1 MB/s, the page said "Uploading…" for 27.7 s with no
  progress, then the node's message.

is asked. A fresh Controller machine with the default image (ready in

**No JavaScript error and no page error** in the six runs. The browser

the "This node" card kept "Other slot v2026.11.09-3 · slot A" until the
page was reloaded, then "slot A: holds a release whose kernel can't
drive this machine" - the node said so already.

The lab-built bundle is v2026.11.09-2's campaign's, made again from the
pre-release: its root filesystem rebuilt as a user with the same SELinux

`virtio_net`, the hash tree made again with the release's salt rule,
both UKIs' root hash and salt replaced in place (same length); the
script rebuilds it byte for byte.

### The release cache (#610)

After the Controller's update, `release-cache.json` was in its data
directory (23,791 bytes, mode 0600, the Controller's user):
`{"version": 1, "security": …, "assets": …}` - **62 releases'**
`security.json` contents (19 with fixes, 216 entries: id, target,
extension, severity, component, variant, audience) and **4 assets**
(the checksum and the Controller image of v2026.11.09-2 and of the
pre-release), every URL under the repository's GitHub releases. No key,
token, password, lab address or host name. Pre-releases' `security.json`
aren't read, as designed.

Each restart: `docker compose restart` of the Controller, its outgoing
HTTPS captured for 90 s, and its update status asked every 0.2 s with
an API token (sessions don't survive a restart) until it names the
newest release.

| Restart | The newest release known | GitHub connections |
|---|---|---|
| v2026.11.09-2 (no cache) | at the first answer, **+19.5 s** (the request waits for the read) | 3 (API, github.com, release assets), reused one after the other |
| **The pre-release, the file there** | at the first answer, **+1.8 s** | **1**: the API's release list; no `security.json` read |
| The pre-release, the file removed | +4.3 s | 10: **eight to github.com opened together**, then the assets; the file written again, **the same content** |
| GitHub 1 s further away (netem on the host's packets to GitHub only), the file there | +4.4 s | 1 |
| The same, the file removed | **+32.0 s** | 26: eight and eight in parallel; the pre-release left out - finding 1 |
| The same, the file there but without the pre-release's two files (as right after a publication) | +5.7 s; "Prepare the pre-release" sent at +1.9 s answered **"ready" at +6.9 s** | 4 |
| GitHub **4 s** further away, the file removed | **+302.9 s**; "Prepare" sent at +2.2 s answered 502 "newest release: fetch controller-image.txt: … context deadline exceeded" at +31.4 s | 35 |
| GitHub 4 s further away, the file there | +54.7 s (the release list alone missed the first 30 s: "decode GitHub API response: context deadline exceeded"); "Prepare" 502 with that message at +31.3 s | 1 |
| The file there, GitHub as it is | +4.1 s; "Prepare" sent at +2.2 s, **"ready" at +4.2 s** | 2 |

**"Prepare the pre-release"**, on schematics the factory hadn't built
yet (the longterm and Let's Encrypt machines'): first answers
"building" in 1.6 and 2.5 s, ready in 34 and 55 s, **no
"unavailable"**. The lab's own schematic, asked earlier from
v2026.11.09-2's Controller two minutes after the publication: first
answer in 8.85 s - under the old 10 s, but close - ready in 46 s.

The cold start with a slow GitHub: the Controller's journal said
`releases: pre-release v2026.11.09-3: fetch controller-image.txt: Get
"…/download/v2026.11.09-3/controller-image.txt": context deadline
exceeded - read again in 3m0s`. The first read of the releases list has
30 s for everything (`sharedFetchContext`); the ~62 `security.json`,
eight at a time at 1 s per round trip, took nearly all of it. The newest
release was known at +32 s, but without its pre-release: the node page's
"Prepare" got 400 "v2026.11.09-3 isn't a release offered to this node -
reload the page" (the page would offer nothing to prepare), and the
pre-release came back at the next read, 3 minutes later (Prepare then
"ready" in 7.3 s).

At 4 s, without the file, the newest release's own files - read after
the `security.json` - timed out too: the whole read failed ("newest
release: fetch controller-image.txt: … context deadline exceeded"),
round after round, each keeping the `security.json` it did read, until
the newest release was known **5 minutes after the start**. With the
file the `security.json` aren't read; at 4 s only the release list
itself, a large answer, missed its first 30 s once (known at 54.7 s).
A 4 s round trip slows TCP's start more than a server answering in 8 s
does, so these figures are a bound, not #553's case itself.

During these runs GitHub's API moved to another address range than the
one first delayed: the shaping covered GitHub's published ranges from
then on, and the one run it missed is the "GitHub as it is" row.

## Findings

1. **A cold start with a slow GitHub can lose the newest releases for
   minutes** - not a blocker in my view: without
   `release-cache.json` (the first start after this update, or the file
   lost) and with GitHub at 1 s per round trip, the ~62 `security.json`
   took nearly all of the 30 s one read of the releases has
   (`sharedFetchContext`); the pre-release's `controller-image.txt` then
   timed out, the pre-release was left out until the next read 3
   minutes later (`partialRetry`), and its "Prepare" answered 400 "isn't
   a release offered to this node - reload the page" - wrong words for a
   read that timed out. In #553's own conditions (8-10 s an answer, 8 at
   a time) the security files alone would take over a minute; measured
   with GitHub 4 s further away, the newest release's own files, read
   after them, timed out too and failed the whole read, round after
   round, and the Controller knew the newest release only **5 minutes
   after its start** (each round keeps the files it did read). The file
   makes every later start fast (one request, at 4 s: 54.7 s, the list
   alone). Reading the
   newest releases' own files before the older `security.json`, or
   giving them their own budget, would avoid it.
2. **Upload mode shows no progress while the browser sends**: the
   node's messages start once the files are on the node; a slow link
   leaves "Uploading…" alone for as long as the upload takes (27.7 s at
   1 MB/s for 21 MB). An upload progress bar from the browser's side
   would cover it.
3. After a refused update, the "This node" card shows the other slot's
   old version until the page is reloaded (the node already marks the
   slot). Cosmetic.
