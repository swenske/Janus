# v2026.11.09 pre-release tests

Tested on 2026-11-09, the morning it came out, on the lab where
v2026.11.08-3 - the newest release, promoted that morning - was
measured again first as the baseline
([v2026.11.08-3's report](v2026.11.08-3.md)). What the pre-release
brings:

- **a kernel for KVM/QEMU virtual machines** (#591), on both tracks, at
  the same versions as v2026.11.08-3 (Linux 7.3.3 stable, 6.18.62
  longterm): no physical network cards, no VMware vmxnet3 or pvscsi, no
  NVMe, no RAID/SAS controllers, no USB, no IOMMU, no cpufreq;
  `image.json` says `kernel.flavor: virt` and lists `kernel.drivers`,
  which the update check of v2026.11.08-3 (#590) reads;
- **node_exporter's `nvme` collector retired**;
- **the Controller keeps offering releases while GitHub's downloads
  fail** (#600).

Since the kernel's configuration changes, the core campaign ran in
full, v2026.11.08-3 measured the same way the same morning: the
Controller's update, the image factory, the cluster updated in place
under load, failovers, janusd restarted, HAProxy reloaded under load,
rollbacks, HAProxy's throughput and two A/B series by rollbacks, the
boot stages on both kernel tracks with each boot's console read, the
nodes' health, hot-plug through auto-scaling, every extension, USB
devices, the Controller's pages. Then the update guard on real
machines: machines made by hand on v2026.11.08-3 with devices the new
kernel can't drive, and one with Proxmox's default devices.

The load and the probes came from the build box and one CI runner;
every throughput figure is compared with v2026.11.08-3 measured the
same morning from the same client.

## Verdict

**The kernel holds on every machine the lab has: zero AVC denials, no
oops, no kernel warning trace a boot didn't have before, every node CIS
33/33, the same kernel parameters written by init, the cluster's
in-place update without a lost request (VIP 0 of 3,304, anycast 0 of
3,301), the failovers, boots and rollbacks as before, CPU and memory
hot-plug, every extension running or waiting for its configuration. The
update guard refuses the machines it must refuse, accepts the one it
must accept, and leaves a refused node as it was. My opinion: ready to
promote.** The decision is yours.

- **The guard, on real machines**: a node on v2026.11.08-3 with vmxnet3
  cards **refused** the update in 2 s, with a message naming the cards
  and what would happen; one booting from an NVMe disk **refused** it
  too; the machine with a virtio-SCSI disk and e1000e cards (Proxmox's
  defaults) **updated** and booted. A refused node: same slot, no
  reboot, its other slot marked as holding a release that can't drive
  it.
- **The NVMe refusal holds for the wrong reason** (finding 1):
  v2026.11.08-3's guard looks for the disk `nvme0n1p` (the partitions'
  prefix) instead of `nvme0n1`, can't find it, and refuses with "can't
  tell whether this release's kernel drives this machine: disk
  nvme0n1p: lstat /sys/block/nvme0n1p: no such file or directory" - the
  refusal is right, but it doesn't name the missing driver, and a kernel
  that had NVMe would be refused the same way. The same code is in this
  release.
- **Forcing it** (`-allow-unsupported-hardware`, janusctl only - the
  Controller's pages don't relay it): the vmxnet3 node booted the new
  release without any network interface and confirmed its boot health
  (the check is local), so nothing brought it back; given virtio cards
  instead, it answered again and rolled back. The NVMe node waited for
  its disk forever (`device-mapper: init: waiting for device
  PARTLABEL=BOOT-B-DATA ...`, no timeout): destroyed. As the notes and
  the refusal's message say.
- **A new kernel log line at every boot of the virt kernel**, both
  tracks (finding 2): `Warning: Processor Platform Limit event detected,
  but not handled. Consider compiling CPUfreq support into your
  kernel.` - not a warning trace, cosmetic, a consequence of cpufreq
  gone.
- **HAProxy costs the same per request**: two A/B series of eight
  runs by rollbacks, 37.2 against 36.6 µs per keep-alive request
  (+1.6 %, the first series +4.6 %, the second −1.6 %), new connections
  187.9 against 192.6 µs; the VIP benchmark within noise (−1.1 %).
- **Sizes**: the VM disk image is **9.4 % smaller** (54.66 → 49.55 MB),
  the UKI 23.8 % (7.17 → 5.46 MB).

## Findings

1. **The update guard misnames an NVMe boot disk** - not a blocker in
   my view: the refusal it gives is the right outcome for this
   release. janusd takes the boot disk from `bootslot.Disk()`, which
   returns the partitions' prefix (`/dev/nvme0n1p` - what
   `SlotDataDevice` appends a number to), and `hwsupport.InUse` looks for
   `/sys/block/nvme0n1p`: the boot's `hardware:` line says "disk
   nvme0n1p: lstat /sys/block/nvme0n1p: no such file or directory" and
   Upgrade refuses with "can't tell whether this release's kernel (virt)
   drives this machine" instead of naming `nvme`. The same would happen
   to an `mmcblk0p` disk, and a future kernel with NVMe would be refused
   on such a machine too. `bootslot.WholeDisk()` strips the `p`; the two
   call sites are `internal/api/lifecycle.go` (`bc.disk` given to
   `checkHardware`) and `cmd/janusd/hardware.go`. The unit tests pass
   `/dev/nvme0n1` straight, which is why they didn't see it.
2. **A new kernel log line at every boot of the virt kernel**:
   "Warning: Processor Platform Limit event detected, but not handled.
   Consider compiling CPUfreq support into your kernel." - from the ACPI
   processor driver when the kernel has no cpufreq, on both
   tracks and every machine; absent on v2026.11.08-3. Cosmetic, but a
   new "Warning" anyone reading the kernel log will ask about.
3. **A node page asks `/api/cluster` of a node too old to have it**: the
   v2026.10.21 node's Update tab logs a failed request (501) and a
   console error. Not this release's change.
4. **Forcing an update isn't offered by the Controller**: the node
   page's update relays neither the field nor the refusal's way out;
   only janusctl can pass `-allow-unsupported-hardware`. Probably as
   meant, but the refusal's message ("set allow_unsupported_hardware…")
   reaches the page's users too.
5. node_exporter still offers `cpufreq` and `thermal_zone`, which find
   nothing on this kernel (harmless).
