# v2026.10.17-2 pre-release tests

Tested on the afternoon of 2026-10-17, right after it was cut. It is
[v2026.10.17](https://github.com/swenske/Janus/releases/tag/v2026.10.17)
with HAProxy and the extensions' C daemons linked as static PIEs
([#143](https://github.com/swenske/Janus/pull/143)) and built on Alpine
3.24.2 (gcc 15.2, musl 1.2.6), an update held since 2026-10-03 until
[#141](https://github.com/swenske/Janus/pull/141) found why HAProxy
crashed on it. HAProxy, the kernels and the extensions are the same
versions, and nothing in it fixes a known vulnerability. This run
repeats every step of the previous campaign, with the release measured
again the same afternoon, and adds one: where each binary sits in
memory, start after start.
The scenarios: [Lab test scenarios](lab-scenarios.md).

## Verdict

**Ready to promote.**

- **The binaries move**: on v2026.10.17, HAProxy, keepalived and BIRD
  sat at `0x400000` on both nodes, as on every node. On the
  pre-release, every start put them somewhere else: 10 HAProxy starts
  read (the update, a reload, a stop and start, firmware and kexec
  reboots, a rollback) gave 10 different addresses. SELinux enforcing,
  no denial.
- **Nothing else moved**: the Controller's update, the image factory,
  the rolling update, failovers, firmware and kexec reboots, rollbacks
  and HAProxy's throughput all match the release (throughput within
  -2.4 % and +3.5 % run by run).
- **The longterm track**: the lab's machine on it, updated through the
  Controller, runs 6.18.57 on the pre-release - SELinux enforcing with
  no denial, CIS 33/33.

### Where the binaries sit in memory

The new check: the address where each binary's first mapping starts,
read from `/proc/<pid>/maps` through `janusctl system cat`, on v2026.10.17
before the update and then after each step that starts one of them
again:

| When | Node | HAProxy | keepalived | BIRD |
|---|---|---|---|---|
| v2026.10.17, before the update | 01 and 02 | `0x400000` | `0x400000` | `0x400000` |
| After the rolling update | 01 | `0x7f93016cb000` | `0x7fdd1e7ad000` | `0x7f0ac59da000` |
| | 02 | `0x7fb67ee4f000` | `0x7fc59bc96000` | `0x7fa9a5d9c000` |
| After a reload (its own configuration applied again) | 01 | `0x7fcd03a51000` | not restarted | not restarted |
| | 02 | `0x7f3eef041000` | not restarted | not restarted |
| After the node loss, then HAProxy stopped and started | 01 | `0x7fc487cd5000` | `0x7fce7ac6f000` | `0x7ff9dce05000` |
| After two firmware reboots | 02 | `0x7fd5ac207000` | `0x7fb3bc8da000` | `0x7f0153168000` |
| After two kexec reboots | 02 | `0x7f19035cb000` | `0x7fad73a91000` | `0x7fe5bd8a2000` |
| After three more | 02 | `0x7fd06e178000` | `0x7f365349b000` | `0x7f2ca3e68000` |
| After the rollback and back | 02 | `0x7ff5d1472000` | `0x7fc8e0658000` | `0x7fca6b81e000` |
| After one more firmware reboot | 02 | `0x7f7dffe19000` | `0x7f7a7fc0b000` | `0x7f4237f7f000` |

A static PIE has no loader, so the kernel places it in the mmap area
(`0x7f…`), at a random offset each time. A static executable has a fixed
address. HAProxy took a new address at each reload, as a reload starts a
new process; keepalived and BIRD kept theirs until their next start.
The nodes logged no AVC denial through all of it. The binaries have no
text relocation, so SELinux needs no `execmod`.

### HAProxy's throughput

`wrk` on the VIP, 30 s a run, the release measured first the same
afternoon (requests/s, 99th percentile):

| From one runner | v2026.10.17, run 1 / run 2 | v2026.10.17-2, run 1 / run 2 | v2026.10.17-2, run 3 / run 4 |
|---|---|---|---|
| keep-alive, 8 connections | 13,223 / 13,558 (5.4 / 8.9 ms) | 13,401 / 13,333 (10.5 / 11.1 ms) | 13,440 / 13,394 (3.7 / 23.6 ms) |
| keep-alive, 64 connections | 44,442 / 44,315 (8.9 / 7.4 ms) | 44,599 / 44,101 (13.0 / 13.4 ms) | 44,494 / 44,471 (5.7 / 11.4 ms) |
| keep-alive, 256 connections | 51,873 / 51,053 (14.4 / 12.7 ms) | 51,467 / 52,848 (14.5 / 12.6 ms) | 52,661 / 52,303 (10.9 / 11.4 ms) |
| a new connection per request, 32 connections | 4,815 / 4,844 (10.6 / 9.6 ms) | 4,794 / 4,772 (10.4 / 10.2 ms) | 4,701 / 4,764 (10.7 / 11.0 ms) |
| **The three runners at once**, 256 keep-alive connections each (total) | 50,031 / 49,923 (99th percentile 144-170 ms) | 50,638 / 49,732 (157-164 ms) | - |

- **Requests per second**: the same, within the runs' own spread
  (-2.4 % to +3.5 % run by run, each against the release's run of the
  same rank).
- **The 99th percentile on few connections**: the pre-release's first
  two runs were higher at 8 and 64 connections, so two more were taken
  later that afternoon. They gave 3.7 then 23.6 ms at 8 connections: that
  measure jumps from one run to the next, as in every campaign.
- **`wrk`'s read errors**: the runs from three clients counted some on
  the pre-release (21, 21 and 22 a client, then 75 on one). The
  release's runs that afternoon had none, and those of v2026.10.17's
  own campaign had 8 to 101. HAProxy wasn't restarted during the runs,
  and the nodes logged no event.
- **The nodes' boot on v2026.10.17-2**: the kernel 1.6 s, the API
  listening 1.9 s after the kernel started.
