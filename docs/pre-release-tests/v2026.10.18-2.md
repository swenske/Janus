## Verdict

**Not ready as is: one defect in the new connectivity test, fixed by
[#158](https://github.com/swenske/Janus/pull/158).**

- **The defect**: a connectivity test given a source address (`-source`,
  **Options › Source**) that has to resolve a name - `dns`, or `tls` and
  `http` to a name - fails on every enforcing node with `bind:
  permission denied`, and the node logs AVC denials. The test asks the
  DNS from its source on purpose; SELinux allowed janusd to bind a TCP
  or ICMP socket to an address, not a UDP one. #150's measurement had
  run no DNS test with a source. #158 adds that single rule, from the
  lab's own denial, and a case in `qemu-probe-test`.
- **The security fix and the other tools work as documented**: a
  reader's certificate reads the configuration with its passwords
  masked, line for line; the stick table, sessions, captured errors,
  map lookups and bundles behave on real nodes under load, and the
  bundles hold no secret.
- **Nothing else moved**: the Controller's update, the image factory,
  the rolling update, failovers, firmware and kexec reboots and HAProxy's
  throughput match the release (throughput within -1.4 % and +2.9 % run
  by run). One rollback out of four took 43.5 s, against 9.5 to 9.7 s;
  it didn't happen again (below).
- **The longterm track**: the lab's machine on it, updated through the
  Controller, runs 6.18.57 on the pre-release - SELinux enforcing with
  no denial, CIS 33/33.

- **The 43.5 s rollback** went from the release back to the
  pre-release, a second after node 02 had come up on the release. Where
  the time went:
  - the boot that followed was normal: the API listening 1.8 s after
    the kernel started, as at the boot before;
  - the release's janusd stopped HAProxy at the usual moment (4 s after
    the call, its drain), then nothing until the next kernel, 37 s
    later. Normally that leg - the shutdown, the firmware's restart -
    takes about 2 s;
  - the node has no LOGS partition and its last lines before a reboot
    don't reach Elasticsearch, so the release's shutdown left no trace;
  - two more rollbacks, with the serial console timestamped on the
    host, took 9.5 and 9.7 s: 2 s from the kernel's restart to the
    firmware's boot entry, as usual.

  It didn't happen again, and nothing points at the pre-release, whose
  boot it was. The rollback script now has the console's timestamps
  to say which leg it is, should it come back.
- **`wrk`'s 16 read errors** are its 8 keep-alive connections, closed
  once by each node that reboots, as in every campaign.
- **The binaries still move**: HAProxy, keepalived and BIRD took a new
  address at each start read - the update, the node loss, HAProxy's
  stop and start, the firmware and kexec reboots, the rollback.
- **The reboot script needed its janusctl named**: its first run left
  silently. It now defaults to the lab's.

What the tests from another address also showed, which the network
explains rather than the node:
- **From the VIP or the anycast address to a backend** on a network the
  node is on, a TCP test times out. The node sends from its own interface
  on that network; the backend's answer to the VIP goes to its gateway,
  the router, which drops half a connection it never saw open.
- **From the anycast address on the node not carrying its route**, it
  times out too: the answers go to the node the router sends the anycast
  address to.

The connectivity test's page says both since
[#158](https://github.com/swenske/Janus/pull/158).
