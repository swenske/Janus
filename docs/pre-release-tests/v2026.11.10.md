# v2026.11.10 pre-release tests

Tested on 2026-11-10, the day it came out, on the lab whose Controller
and nodes ran v2026.11.09-3 - the newest release
([v2026.11.09-3's report](v2026.11.09-3.md)). What the pre-release
changes:

- **zlib 1.4 in HAProxy** (#577): the HAProxy binary is another one;
- **the newest release read before the security files** (#615): a
  Controller starting without its `release-cache.json` while GitHub is
  slow should know the newest release and the pre-release at once, the
  `security.json` files following;
- **the Update page reads the slots again after a refusal** (#615);
- **dependencies**: go-jose 4.1.9 and golang.org/x/oauth2 0.38 (single
  sign-on), the Controller's pages and the image factory's site on
  lucide-react 1.70 and Vite 8.3.6.

The campaign: the Controller's update and the image factory, the cold
start of v2026.11.09-3's finding 1 replayed the same way, the Update
page's refusal in the browser, HAProxy's compression on a test frontend,
single sign-on through the lab's Keycloak, the factory's public site,
then the core - the cluster updated in place under load, a VRRP and a
BGP failover, HAProxy reloads, firmware reboots and kexec, a rollback
and back, the nodes' health, the Controller's pages in both themes -
and HAProxy's cost per request, the release and the pre-release
alternated on node 01 by rollbacks. The load and the probes came from
the build box and one CI runner, the release measured from the same
clients the same day.

## Verdict

**What the pre-release changes works on the lab. Node 01's HAProxy is
the release's binary and runs on zlib 1.4; gzip and deflate compress
as before - the same bytes on the wire, every body decompressed
identical to the file, the same CPU per request (905 against 907 µs for
gzip, 918 against 914 µs for deflate, over four runs each, the release
and the pre-release alternated by rollbacks). On a cold start with
GitHub 1 s away the Controller now knows the newest release and the
pre-release at its first answer and "Prepare the pre-release" works at
once - v2026.11.09-3, restarted the same way the same morning, answered
502 and knew neither for 75 s; the `security.json` follow at the next
read. After a refused update the Update page shows the slot's new state
2 ms after the toast, without a reload. Single sign-on, the Controller's
pages and the factory's site work, with no console error. The core
campaign is as before: the cluster updated in place without a lost
request (VIP 0 of 3,302, anycast 0 of 3,299), zero AVC denials, CIS
33/33, the same boot times and the same throughput. My opinion: ready
to promote** - finding 1 is the one to read: with GitHub 4 s away and
no cache file the pre-release stays missing, as in v2026.11.09-3, the
release list itself now being what doesn't fit. The decision is yours.

## What the pre-release brings

### zlib 1.4 and HAProxy's compression (#577)

HAProxy's build options aren't in the API: `haproxy show-info` and the
node page give the version only (`3.4.7-8872a26`, the same string on
both releases). So the binary itself: the release's
`haproxy-3.4-amd64.tar` (checked against its digest) and node 01's
`/usr/local/sbin/haproxy` copied off the node through the file API have
the **same SHA-256**, and its `-vv` says **"Built with zlib version :
1.4 / Running on zlib version : 1.4"** (v2026.11.09-3's: 1.3.2) - the
same size, 9,010,040 bytes, the same build options otherwise (`USE_ZLIB`,
no libslz, AWS-LC 5.12.0).

The compression: both backends serve a 64 KiB JSON file (made from a
seed, `gzip off` in nginx), and node 01 got a test frontend on another
port in front of them with `compression algo gzip deflate` and
`compression type application/json text/plain`.

| Asked as | v2026.11.09-3 | v2026.11.10 |
|---|---|---|
| identity | 65,536 bytes | 65,536 bytes |
| `gzip` | `Content-Encoding: gzip`, 17,625 bytes (26.9 %) | gzip, 17,550 bytes (26.8 %) |
| `deflate` | `deflate`, 17,581 bytes | `deflate`, 17,529 bytes |
| `gzip, deflate` / `deflate, gzip` | gzip / deflate | gzip / deflate |

`Vary: Accept-Encoding` on each compressed answer, and **every body,
decompressed, has the file's SHA-256**. The sizes move by a few dozen
bytes from one request to the next on both releases (HAProxy compresses
as the data comes, level 1 by default).

Under load, from the CI runner, `wrk -t2 -c16` for 30 s on that frontend
for each encoding, node 01's CPU time by mode read off its exporter
around each run and its front interface's bytes sent:

| Per request (node 01) | v2026.11.09-3 | v2026.11.10 |
|---|---|---|
| identity | 1,775 req/s (the link's limit), 256 µs CPU | 1,773 req/s, 257 µs |
| **gzip** | 2,206 req/s, **906.5 µs** (894.6 - 921.2), ~18,420 bytes sent | 2,211 req/s, **905.1 µs** (897.4 - 914.7), ~18,420 bytes |
| **deflate** | 2,193 req/s, **914.1 µs** (909.8 - 918.6), ~18,415 bytes | 2,182 req/s, **918.1 µs** (903.4 - 928.3), ~18,415 bytes |

Means of four runs each, alternated by rollbacks with the throughput's
runs below. Compressing, node 01's two vCPUs are saturated (under 1 s
idle of 60): the rate is the CPU's, about 700 µs of user time per
64 KiB response. The same within the runs' spread.

### The newest release first (#615)

v2026.11.09-3's finding 1 replayed with its method: the Controller
restarted (`docker compose restart`) without `release-cache.json`,
GitHub made slower by `netem` on the Controller's host for GitHub's
addresses only, the outgoing HTTPS captured, an API token polling every
0.2 s, and "Prepare the pre-release" sent from a node page 2 s after the
restart. The Controller being on the pre-release itself, its own update
status offers no pre-release: the newest release and the pre-release
were read on a v2026.11.09-2 node's update check (the Controller's
`/nodes/<id>/api/update-check`, what its Update page shows). The
release, v2026.11.09-3, was restarted the same way first at 1 s.

| Restart | v2026.11.09-3 | v2026.11.10 |
|---|---|---|
| GitHub 1 s further away, no file | first answer +31.6 s **without the newest release**; "Prepare" **502** "newest release: fetch controller-image.txt: … context deadline exceeded" at +31.3 s; the newest release and the pre-release known at **+74.9 s**; 41 `security.json` read in the first 30 s, 62 at +80 s; 8 + 8 connections | **the newest release and the pre-release at the first answer, +31.4 s**; "Prepare" **200 "ready"** at +31.4 s; 16 `security.json` in the first read, 56 at +245 s (the next read, 3 minutes later); one connection to each GitHub host |
| GitHub 4 s further away, no file | (v2026.11.09-3's campaign: the newest release at +302.9 s, the pre-release still missing) | "Prepare" **502** "newest release: decode GitHub API response: context deadline exceeded" at +31.4 s; the release list read once about 3 minutes in, the newest release known from then; **the pre-release still missing at +960 s** - finding 1 |
| GitHub as it is, no file | (v2026.11.09-3's campaign: +4.3 s) | +6.9 s, both; 62 `security.json` at +11 s; the file written again |
| GitHub 1 s further away, the file there | (+4.4 s) | both at the first answer, +13.8 s (the node's answer also asks the image factory); one connection to GitHub, the API |
| GitHub 4 s further away, the file there | (+54.7 s) | "Prepare" 502 "decode GitHub API response" at +31.5 s; **the pre-release at +58.7 s** |

At 1 s a round trip the fix does what it says: the pre-release and the
newest release come with the first answer, "Prepare the pre-release"
works at once, and the `security.json` follow at the next read (16,
then 56 three minutes later). The first answer still waits for the
whole first read - about 30 s, the read's budget, spent to the end on
`security.json` with the time left.

At 4 s a round trip without the file the bottleneck isn't the
`security.json` any more but the release list itself, one large answer
that TCP needs more than 30 s to bring at that delay: the first read
failed on it; a later one got it in about 3 minutes, but then the
pre-release's `controller-image.txt` missed the read's end (`releases:
pre-release v2026.11.10: fetch controller-image.txt: … context deadline
exceeded - read again in 3m0s`) - and every read after it failed on the
list again ("the list read … ago kept, tried again in 2m0s"), so the
pre-release stayed missing 16 minutes, when the test was stopped.
v2026.11.09-3 lost the pre-release the same way there. That log line's
"10m30s ago" counted from a time moved back for the partial list's
retry: the list had been read 3 min 30 s before.

## Findings

1. **With GitHub 4 s away and no cache file, the pre-release stays
   missing** - not a blocker in my view, and not a regression: at that
   delay the release list itself, one large answer, needs more than
   the 30 s a read has. The read that got it spent nearly all of its
   time on it, the pre-release's `controller-image.txt` then missed the
   end, and every later read failed on the list again (kept, tried
   every 2 minutes): the pre-release was still missing 16 minutes after
   the start, as it was on v2026.11.09-3. The newest release was known
   about 3 minutes in. #615 moved the `security.json` out of the way,
   which is what 1 s needed; at 4 s the list's own read would need a
   longer budget, or the pre-release kept from a list read before. The
   log line's "the list read 10m30s ago kept" counts from a time moved
   back for the partial list's retry - it had been read 3 min 30 s
   before (cosmetic).
2. **A cold start's first answer still waits for the whole first read**:
   with GitHub 1 s away, about 31 s - the read's budget, used to its end
   on `security.json` once the releases are known. The answer is now
   right (both releases); answering as soon as they are known would
   make it quick too. Minor.
