# v2026.10.28-2 pre-release tests

Tested on the evening of 2026-10-28. It is
[v2026.10.28](https://github.com/swenske/Janus/releases/tag/v2026.10.28) -
Linux 7.2.13 and 6.18.59, HAProxy on AWS-LC 5.12.0, Consul 2.1.0, the
janusctl plugin's icon - with
[#377](https://github.com/swenske/Janus/pull/377) (the screenshots wait
for each page's first render),
[#378](https://github.com/swenske/Janus/pull/378) and
[#384](https://github.com/swenske/Janus/pull/384) (the libvirt host
preparation's UEFI firmware step),
[#379](https://github.com/swenske/Janus/pull/379) (Proxmox machines get
the `x86-64-v2-AES` CPU model),
[#380](https://github.com/swenske/Janus/pull/380) (the DHCP wait in the
docs) and [#381](https://github.com/swenske/Janus/pull/381) (an HTTP-01
order that fails while HAProxy's configuration changed is retried at
once).

Neither v2026.10.27-4 nor v2026.10.28 had a lab campaign: this one
covers everything since
[v2026.10.27-3](https://github.com/swenske/Janus/releases/tag/v2026.10.27-3),
the release, measured again in this session on the same lab.

## Verdict

**Ready to promote.** On the lab's real nodes:

- **The baseline holds**: the rolling update under load lost **nothing**
  on the VIP and one anycast probe (the lab router's known noise);
  failovers, firmware and kexec reboots and the rollback at the level of
  the campaigns before; zero AVC denials and the CIS audit 33/33 on all
  five nodes.
- **Linux 7.2.13 and 6.18.59** run on the lab's nodes and on the
  longterm machine, with no oops. HAProxy's throughput first looked
  lower on the new kernel; measured again with the CPU time each request
  costs, alternating both versions on the same node, it is the same
  within the lab's variance ([finding 1](#findings)).
- **Consul 2.1.0** joined a Consul 2.1.0 server - the first campaign with
  a real server rather than an agent alone: leader seen, both members
  alive from both sides, a bad configuration refused.
- **HAProxy on AWS-LC 5.12.0** serves TLS 1.3 and 1.2 with the
  certificates the Controller ordered; **Let's Encrypt's** machine kept
  its two certificates across the update.
- **The libvirt preparation's new step** hides nothing on the lab's
  Debian 13 hosts and changes nothing there, as designed; the
  Controller generates it.

## What this pre-release changes

### Linux 7.2.13 and 6.18.59

Nodes 01 and 02 run 7.2.13 since the rolling update; every reboot above
(firmware, kexec, rollback, the node loss) came back without an oops,
and the boot stages are where they were (kernel 1.62 to 1.65 s, init
1.76 to 1.80 s, HAProxy 1.98 to 2.07 s). The lab's longterm machine,
updated through the Controller with the image factory building its
schematic, runs 6.18.59 - the release's high CVE fix for that track -
healthy, CIS 33/33, no denial.

### HAProxy on AWS-LC 5.12.0

On the Let's Encrypt machine (CPU `host-passthrough`, the certificates
the Controller ordered from the lab's private CA): TLS 1.3 negotiated
`TLS_AES_256_GCM_SHA384`, TLS 1.2 `ECDHE-ECDSA-AES128-GCM-SHA256`, and a
client listing ChaCha20 first got ChaCha20. The rolling update and
every failover ran on the new build.

### Consul 2.1.0

A machine the Controller created with the Consul extension (the image
factory built that schematic for the pre-release), and a Consul 2.1.0
server next to the lab's Controller for the test - earlier campaigns
had no server, the agent alone:

| Step | Result |
|---|---|
| A configuration with an unknown key, checked | refused by `consul validate`: `invalid config key bogus_key` |
| The client's configuration (the server to join, its own address and name), applied | the agent restarted with it |
| `janusctl network consul status` | running, client, datacenter `lab`, **Consul 2.1.0**, the leader, both members alive |
| The server's `consul members` | the machine alive, client, build 2.1.0 |
| The machine's health | `consul` running and healthy, no AVC denial, CIS 33/33 |

The machine and the server were removed afterwards.

### Let's Encrypt (#381)

The change is in the node's own ordering: an HTTP-01 order that fails
while HAProxy's configuration changes is retried at once. CI's
`qemu-acme-test`, `-proxy-` and `-ordered-` ran it on enforcing nodes
(the PR's 13 runs, and this build's). In the lab, the machine whose
certificates the Controller orders went to v2026.10.28-2 through the
Controller: both certificates still valid and served after the update,
the path unchanged. The race itself wasn't reproduced here.

### The libvirt preparation's UEFI firmware step (#378, #384)

## Findings

1. **HAProxy's throughput varies more between rounds than between the
   versions.** The first two comparisons put v2026.10.28-2 up to 23 %
   behind on new connections. A third, with node 01's CPU time by mode
   read from its exporter around each run and the versions alternated
   twice more on that node, showed:

   | | v2026.10.27-3 (3 runs) | v2026.10.28-2 (4 runs) |
   |---|---|---|
   | A new connection per request | 2,928 to 3,410 req/s, 3,215 on average | 2,962 to 3,459, 3,221 |
   | Same, CPU per request | 165 µs | 170 µs |
   | Same, the node idle | 74 to 79 % | 74 to 77 % |
   | Keep-alive, 256 connections | 52,489 to 55,225 req/s, 54,173 on average | 51,296 to 55,019, 52,847 |
   | Same, CPU per request | 36.4 µs | 37.2 µs |

   A node three quarters idle can't be what limits new connections: that
   run is bound by the latency of each connection through the lab's
   hosts and router, and swings by a quarter from one round to the next.
   The CPU each request costs is the same within about 3 %. Nothing to
   fix in this release; the lab's reports keep the CPU per request for
   such comparisons. An image with v2026.10.28-2's system and the
   7.2.12 kernel, built to isolate the kernel, wasn't installed: its
   unsigned kernel needs the node's signature check skipped, which the
   test's automation refused.
2. **One anycast probe lost during the rolling update** - 5 s after
   node 01 was back in service and its route announced again: the lab
   router's known noise around route changes (v2026.10.27-3's campaign
   lost one too).
3. **The image factory took 249 s for the lab's bundle** against 61 to
   87 s in the last campaigns, and 7 minutes for the Consul schematic
   (about a minute for the longterm and Let's Encrypt ones the same
   evening). The bundles were right; the time went to the
   `schematic-build` runs on the runners, not investigated further.
4. **The lab's syslog target is still blocked on the network's side**
   (since v2026.10.26's campaign) - not Janus.
