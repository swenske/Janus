[Lab test scenarios](lab-scenarios.md).

## Verdict

**Ready to promote.**

- **The pages in chunks**: through the lab's Controller, its main bundle
  is 355,319 bytes (107,440 gzipped) against 471,542, a node page's
  316,873 (98,736) against 627,352; the chunks fetched when a view opens
  come `immutable` and gzipped like the rest. The pages walked in two
  palettes and both modes, the lazy views among them: no error.
- **The shipping**: both nodes' targets `ok` with 0 records dropped through
  the update, the reboots and the rollbacks; a firmware boot's 707 kernel
  lines in Elasticsearch, as before; the Controller's own forwarding
  unchanged.
- **Nothing else moved**: the Controller's update, the image factory, the
  rolling update under load, failovers, firmware and kexec reboots,
  rollbacks, the longterm machine's update and the nodes' health match
  v2026.10.20's campaign; HAProxy's throughput is within the runs' spread
  against v2026.10.20 measured the same evening.

## CI: image-build

[Run 39420016725](https://github.com/swenske/Janus/actions/runs/39420016725),
from `main` at `0ff48a0`, with `release_version=v2026.10.20-2` and
`prerelease`, dispatched at 14:40 Paris; published at 17:26 after three
reruns.

- **The internet, not the code, failed the run twice.** For about two
  hours, from the three runner machines - not from the build host -
  HTTPS to `docker.elastic.co` and `proxy.golang.org` timed out while
  GitHub and Docker Hub answered: the ISP's. The Elasticsearch test
  couldn't fetch its image, `pebble` couldn't be fetched for the Let's
  Encrypt test, and once both had passed, `publish` couldn't download
  node_exporter's module for its arm64 extension. A loop checked the
  three machines every ten minutes and reran the failed jobs when all
  of them reached both hosts again; each then passed.
- **One real failure**: the `docs-screenshots` job timed out on the
  Traffic flow screenshot. The view is loaded when opened since
  [#195](https://github.com/swenske/Janus/pull/195), and React holds a
  view that resolves after its placeholder showed behind a 300 ms timer -
  which the screenshots' paused clock never fires. Reproduced on the
  build host (the chunk arrives, "Loading…" stays), fixed by
  [#200](https://github.com/swenske/Janus/pull/200): the clock pauses
  400 ms short of the shots' instant and runs them once the splash is
  gone, landing on it exactly - the 20 screenshots compare unchanged.
  The job reports and never blocks; it will pass on the next run from
  `main`.
- **The eight test jobs**, the new `test-logs` among them: the longest
  13 min 52 s against 20 min 25 s before the split.

### init's CPU, asked about

A production node just updated to v2026.10.20-2 - one vCPU on a Xeon of
2012 - showed init busier than a node of the previous release with more
traffic - two vCPUs on an i9 of 2023: 0.78 % against 0.42 % of a CPU
over a minute, both logging every HAProxy request to stdout. On the
lab's node 02 (a Xeon of 2013), init's CPU over 60 s, on each slot:

| | v2026.10.20 | v2026.10.20-2 |
|---|---|---|
| idle, HAProxy not logging | 0.02 % | 0.02 % |
| under `wrk` (40,000 req/s), HAProxy not logging | - | 0.03 % |
| under `wrk` (33,000 req/s), HAProxy logging every request to stdout | **2.13 %** (janusd 19.7 %) | **2.25 %** (janusd 19.5 %) |

init's CPU follows HAProxy's logging, not the version: what janusd lets
through to the console (2 KiB/s, the console budget) goes through init
to `/dev/console` - the serial port, whose kernel driver waits for the
transmitter in a loop. The same work on an older core costs more of it.
init's code didn't change since v2026.10.19-4; init runs on every CPU
like any Go program, but has nothing to spread. janusd's cost per logged
line - the ring, the LOGS partition, the shipping - is the same on both
versions.
