# v2026.11.08-2 pre-release tests

Tested on 2026-11-08, the afternoon it came out, on the lab where
v2026.11.08 - the newest release, promoted that morning - was measured
again first as the baseline ([v2026.11.08's report](v2026.11.08.md)).
What the pre-release brings:

- **a kernel minor version on the stable track**, Linux 7.3.3 (7.2.15
  before), and 6.18.62 on the longterm track (6.18.60, a critical
  netfilter fix);
- **io_uring left out of both kernels**;
- **a hardware guard** (#590): an update whose kernel couldn't drive the
  boot disk or a network interface is refused, and janusd logs once a
  boot what those devices are bound to - the lists are empty in this
  release, so nothing is refused yet;
- **Consul services named after the node's cluster** (#588),
  `haproxy-<cluster>-…` (`haproxy-<node>-…` for a node alone), each
  node's token allowed its own scope's only.

Since the kernel changes minor version, the core campaign ran in full
with v2026.11.08 measured the same way the same afternoon: the
Controller's update, the image factory, the cluster updated in place
under load, failovers, janusd restarted, HAProxy reloaded under load,
rollbacks, HAProxy's throughput with an A/B by rollbacks, the boot
stages on both kernel tracks with each boot's console read, the nodes'
health, hot-plug through auto-scaling, USB devices, the Controller's
pages. Then the Consul scenarios replayed across the update, and the
hardware line read on every kind of machine the lab has.

The load and the probes came from the build box and one CI runner, as
for v2026.11.08; every throughput figure is compared with v2026.11.08
measured the same afternoon from the same client.

## Verdict

**The kernels hold: zero AVC denials, no oops, no warning a boot
didn't have before, every node CIS 33/33, the init's kernel parameters
all written, every daemon running without io_uring, the cluster's
in-place update without a lost request (VIP 0 of 3,303, anycast 0 of
3,300), the failovers as before. The Consul renaming works on the
nodes. But one defect keeps #588's restriction from reaching the
nodes it was written for, so my opinion: not ready to promote as is -
ready once the defect below is fixed.** The decision is yours.

- **#588's token restriction never reaches a node updated after the
  Controller** (finding 1): the documented order - the Controller first,
  then the nodes - leaves every updated node's Consul token with
  `janus-nodes-legacy`, the older right to register any `haproxy-…`
  service. A node of the cluster, on the pre-release, registered
  another scope's `haproxy-<other>-x` and got **200**. A node made on
  the pre-release gets the restricted token and is refused (**403**) -
  the restriction works where it is applied. Nothing is worse than on
  v2026.11.08 (every node could write any `haproxy-…` there), and the
  services themselves take their new names.
- **Linux 7.3.3 costs about 4 % more CPU per keep-alive request** than
  7.2.15 with the same HAProxy bytes (finding 2): 40.2 against 38.7 µs
  over eight alternated runs, keep-alive throughput 3.1 % lower; new
  connections cost the same. Beyond the noise of earlier A/Bs; not a
  blocker in my view.
- **The hardware line**: every kind of machine in the lab binds its boot
  disk and its interfaces to drivers in #591's `KERNEL_DRIVERS` -
  `virtio_blk`, `virtio-pci`, `virtio_net`, and, on a machine made with
  a virtio-SCSI disk and e1000e interfaces, `sd`, `virtio_scsi`,
  `e1000e`. **No driver missing from #591's list.**
- No update refused; `lifecycle upgrade -help` shows
  `-allow-unsupported-hardware`.

### Hot-plug through auto-scaling

A fresh Controller machine on the pre-release, 2 vCPU and 1 GiB, a
policy on with maxima 4 vCPU and 2 GiB (the one restart it takes:
9.5 s), the durations shortened to the minimum the policy accepts.

| Step | What happened |
|---|---|
| Memory (its threshold set to 90 % available, to see it move) | **1024 → 1280 → 1664 MiB** live within a minute (virtio-mem); that threshold then held the CPU step ("too little memory is available for HAProxy's reload") - put back to its default, without a restart |
| Under `wrk` from the CI runner | **2 → 3 → 4 vCPU**, a minute apart; the node counts 3, then 4 ("ACPI: CPU2 has been hot-added") |
| The load stopped | **4 → 3 vCPU** after 3 minutes, **3 → 2** three minutes later ("CPU 3 is now offline") |

## Findings

1. **An updated node's Consul token keeps `janus-nodes-legacy`
   (#588)** - blocking in my view. After the Controller's update, its
   pass pushed the new layer, `scope` included, to the nodes still on
   v2026.11.08; their janusd dropped the unknown field but kept the
   layer's `managed_by`, whose hash covers the scope. Once updated, each
   node reports `scope: ""` with that same `managed_by`, so the
   Controller sees the layer as applied and never sends it again
   (`dashboard/backend/consul.go`: `have == want.ManagedBy`), and keeps
   computing `Legacy` from the empty scope - the passes 7 and 11 minutes
   after the update, **Run now**, and the one a new machine brought, left the three updated nodes' tokens
   with `janus-nodes-legacy`; an updated member registered another
   scope's `haproxy-<other>-x` (200). Their services are named right
   (the node falls back on its cluster or its own name). Anything that
   changes the layer clears it: a label added to one node sent its
   layer again (`scope: kc`), its token lost `janus-nodes-legacy` and
   another scope's name was refused (403). The fix belongs in the
   Controller - send the layer again when the node's scope differs from
   the one it should have - with a test on this path: a layer pushed to
   a node of the release before, then the node updated.
2. **About 4 % more CPU per keep-alive request with Linux 7.3.3**, see
   HAProxy's throughput. Not investigated further.
3. **`janusctl network consul managed` doesn't print the scope**: the
   field is in the API (`ConsulManaged.scope`, the node page shows it)
   but not among the command's lines (Managed by, Datacenter, Node
   name, Join, Advertise, Gossip key, ACL token, RPC CA, Node meta,
   Registers, Services). The Consul tab's node table doesn't show a
   node still on the legacy right either (the API's `legacy`).
4. **A kernel warning when the first vCPU is hot-added**:
   `cpuid-deps.c:127 do_clear_cpu_cap` from `init_ia32_feat_ctl`, on
   7.2.15 as on 7.3.3 - older than this release; the CPU comes up and
   is used.
5. While cleaning up, five Consul machines destroyed at once: the
   Controller's next passes failed on `GET /v1/operator/keyring: 500`
   ("1/2 nodes reported success" - the departed members), so their
   tokens weren't deleted before the integration was turned off. Not
   followed further; the Consul server was removed with them.
