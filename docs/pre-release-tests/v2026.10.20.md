# v2026.10.20 pre-release tests

Tested on the morning of 2026-10-20, right after it was cut. It is
[v2026.10.19-4](https://github.com/swenske/Janus/releases/tag/v2026.10.19-4)
with lot A of the optimisation review of the same day:

- six of the node's hot paths doing less work - HAProxy's log lines,
  `/proc/stat`, the exporter's labels, the console budget, the
  Controller's audit log and the configuration masking
  ([#185](https://github.com/swenske/Janus/pull/185));
- the Controller's page and each node's page served with an ETag,
  compressed and cached
  ([#187](https://github.com/swenske/Janus/pull/187));
- the Controller's tests making their recovery kits at a cheap scrypt
  work factor under `go test` only
  ([#186](https://github.com/swenske/Janus/pull/186)), and CI's own
  caches, pinned tools and parallel docs walk
  ([#188](https://github.com/swenske/Janus/pull/188)).

HAProxy, the kernels and the extensions are v2026.10.19-4's. The lab ran
v2026.10.19-4, measured again that morning before the update. This run
repeats every step of the last full campaign
([v2026.10.19-4](v2026.10.19-4.md#the-lab)) and adds the Controller's
serving to the checks. The scenarios:
[Lab test scenarios](lab-scenarios.md).

## Verdict

**Ready to promote.**

- **The Controller's serving**: through the lab's Controller, its page
  and a node's page come with a strong ETag (a 304 on `If-None-Match`),
  gzipped (the main bundle 471,542 → 135,782 bytes on the wire, a node
  page's 627,352 → 182,203), the hashed assets `immutable` for a year,
  `index.html` and the rest `no-cache`, `/assets/` no longer listed.
  The pages walked in two palettes and both modes: no error.
- **Nothing else moved**: the Controller's update, the image factory, the
  rolling update under load - **0 lost** on the VIP and on the anycast
  address this time -, failovers, firmware and kexec reboots, rollbacks,
  the longterm machine's update and the nodes' health match the earlier
  campaigns. HAProxy's throughput is within the runs' spread against the
  release measured the same morning; a new connection per request came
  out 9 to 13 % higher in both runs.
- **The image's room** is as before: 62.18 MiB of the 64 MiB slot with
  every extension (62.19 in v2026.10.19-4). The faster paths add no
  code worth a kilobyte; the decision noted in the last report stands.

## CI: image-build

[Run 39392456979](https://github.com/swenske/Janus/actions/runs/39392456979),
from `main` at `ceb6808`, with `release_version=v2026.10.20` and
`prerelease`, dispatched at 09:53 Paris.

- **Three test jobs failed at the first attempt, on the same runner
  machine, for the same reason: its disk was full.** 124 per-commit
  Controller image tags - one per `publish`, never removed - and 161
  orphaned volumes filled a 64 GB disk, and BuildKit, with no cache
  policy, had evicted the kernel's layers as the disk filled: two jobs
  then rebuilt the kernel and the musl toolchain until "No space left on
  device" stopped the runner's own log, and the third saw Elasticsearch
  refuse to start. GitHub balances nothing between machines: this run
  put five of its eight jobs on that one. The machine was cleaned, the
  three jobs run again, and all passed; the fix is
  [#191](https://github.com/swenske/Janus/pull/191) (the `publish` job
  tidies its runner, a cache budget on each machine, documented in
  [CI runners](https://janus.sw-servers.net/docs/ci-runners.md)).
- **The publish job** published everything: the GitHub pre-release (44
  assets, the signed bundle), the Controller image on Docker Hub, the SD
  card images, janusctl on apt's `testing`. It took 24 minutes: on the
  cleaned machine, its Docker cache held no kernel any more, so it built
  one.

Its `security.json` says *none* against v2026.10.19-4: no dependency
changed. No 🔒 in its name, no badge.
