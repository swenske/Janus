# v2026.10.23 pre-release tests

Tested on 2026-10-23, in the afternoon. It is
[v2026.10.22-2](v2026.10.22-2.md) with:

- **more on a node's page**
  ([#239](https://github.com/swenske/Janus/pull/239)): the clients' IP
  versions, errors and refusals, traffic by frontend, each backend's
  throughput in a sortable table, the LOGS partition beside STATE,
  backends as a list, stick tables drawn as tables on the Traffic flow,
  the sockets by IP version;

  ([#240](https://github.com/swenske/Janus/pull/240));
- **the exporters on the node's main interface by default**, nodes set

  [#246](https://github.com/swenske/Janus/pull/246));

  ([#234](https://github.com/swenske/Janus/pull/234)), single sign-on's
  linking made findable
  ([#237](https://github.com/swenske/Janus/pull/237)), and docs
  ([#236](https://github.com/swenske/Janus/pull/236),

The same kernel, HAProxy and extensions as v2026.10.22-2. The campaign
of [v2026.10.22-2](v2026.10.22-2.md) - the update path, the throughput,
the failovers, the reboots, the longterm machine - plus what this one
changes on real nodes: where the exporters listen after the update, the
per-connection counters under load, the reboot lines, and the pages it
changed in the browser. The scenarios:
[Lab test scenarios](lab-scenarios.md).

## Verdict

**Ready to promote.** The Controller and the nodes update as before -
no request lost on the VIP in the rolling update under load, both nodes
back in service 16 s after their drain. The nodes set up before keep
their exporters on every address, as the release says, and a node set to
the main interface listens where its default route goes. The
per-connection counters match the load generator's own figures. No
regression in the throughput: an A/B run at the same hour puts the
pre-release level with or above the release. Two findings, neither
blocking: a reboot's timing line doesn't always reach the log server
from a node without a LOGS partition, and Monitoring › Network's sockets
table isn't reachable with the keyboard (already the case in
v2026.10.22-2).

### Where the exporters listen

Right after the update, on both nodes and on the longterm machine:

- `janusctl system metrics` says `http://<node>:10056/metrics` and the
  node exporter `http://<node>:9100/metrics` - every address, saved as
  the node's setting at its first boot on v2026.10.23 (the
  `listen-default` marker is there);
- Netstat shows both listening on `[::]`: the scrapes the lab already
  had (the throughput script reads the boot stages through the
  management network) went on working.

Then node 02 was set to the main interface (`-address auto`). The lab's
nodes have the layout the documentation warns about: the management
network has no gateway, the default route goes out through the front
network. The exporter moved to the front network's address, the
management address stopped answering and the front one answered - as
documented. Set back to every address (`-address '*'`), the management
address answered again. The lab's nodes keep every address.

### Each connection's bytes

On node 01, with `wrk` loading the VIP (8 connections), Netstat read
twice, 5 s apart, through the node's page on the Controller:

- 22 TCP connections established, every one with its byte counters;
  none on the UDP sockets nor the listeners;
- each of `wrk`'s 8 connections received about 64 KiB/s and sent about
  278 KiB/s - eight times that is the 2.07 MB a second `wrk` read
  (12,833 requests a second).

### A reboot's step times

janusd now logs a line with each step's time before the machine goes
down, and the nodes send janusd's log to the lab's log server. Of the
five reboots v2026.10.23 made (a rollback on node 01, two firmware and
two kexec reboots on node 02), three lines arrived there, for example
`lifecycle: rebooting now - haproxy stopped 2.018s, shutdown hooks 2ms,
sync 0s`. HAProxy's 2 s is the drain delay of a node with VRRP and BGP.

The two firmware reboots' lines never arrived: the line is logged after
the shutdown hooks, which flush the log shipper, and these nodes have no
LOGS partition to keep it for the next boot - it goes only if the
shipper sends it during the 2 s the console is given to drain. To fix in
the next release: flush the shipper again after that line. The line is
on the console every time (CI checks it there).
