# v2026.11.05 pre-release tests

Tested on 2026-11-05, the hour it came out, on the lab where
v2026.11.04-2 was measured the same afternoon
([v2026.11.04-2's report](v2026.11.04-2.md)). A security-review
release: two high and nine medium findings in Janus's own code,
JANUS-2026-008 to -018, all fixed. What the lab can show of them:

- **HAProxy in a mount namespace without STATE's secrets**
  ([JANUS-2026-008](https://github.com/swenske/Janus/blob/v2026.11.05/security/fixes/JANUS-2026-008.json)):
  a configuration naming the node CA key is refused;
- **the Controller's ACME ordering policy**, fail-closed
  ([JANUS-2026-009](https://github.com/swenske/Janus/blob/v2026.11.05/security/fixes/JANUS-2026-009.json));
- **the global-section check tokenized as HAProxy does**
  ([JANUS-2026-010](https://github.com/swenske/Janus/blob/v2026.11.05/security/fixes/JANUS-2026-010.json));
- **a DHCP server's host name and domain validated**
  ([JANUS-2026-011](https://github.com/swenske/Janus/blob/v2026.11.05/security/fixes/JANUS-2026-011.json));
- **readers kept from secrets**: a cluster's versions
  ([JANUS-2026-013](https://github.com/swenske/Janus/blob/v2026.11.05/security/fixes/JANUS-2026-013.json))
  and stick-table keys
  ([JANUS-2026-016](https://github.com/swenske/Janus/blob/v2026.11.05/security/fixes/JANUS-2026-016.json));
- **the audit trail** quoted, capped and rate-limited for anonymous
  callers ([JANUS-2026-015](https://github.com/swenske/Janus/blob/v2026.11.05/security/fixes/JANUS-2026-015.json));
- **a removed cluster member refused**
  ([JANUS-2026-017](https://github.com/swenske/Janus/blob/v2026.11.05/security/fixes/JANUS-2026-017.json)).

Each fix was tried on the lab's real nodes and Controller - where it
made sense, on the release first, to see the hole, then on the
pre-release - and the baseline went through as usual: the Controller's
update, the cluster updated in place under load, failovers, janusd
restarted, HAProxy reloaded under load, rollbacks, HAProxy's
throughput against v2026.11.04-2 (an A/B by rollbacks on one node),
the boot stages, the nodes' health.

## Verdict

**Every fix the lab can reach works on real enforcing nodes and on the
lab's Controller, and the baseline holds: no request lost in the
cluster's update, the failovers as before, zero AVC denials. My
opinion: ready to promote.** The decision is yours. One thing to know
before it ([finding 1](#findings)): a Controller that starts while
GitHub is slow can't name the newest release for a while - it reads
every release's `security.json` one after the other - which held the
lab's Controller update 26 minutes this afternoon. Not this release's
doing (v2026.11.04-2 does the same), and nothing on the nodes depends
on it.

- **#008**: on the release, a configuration answering with
  `/etc/janus/pki/ca.key` through `http-request return ... file` was
  **valid**. On the pre-release the same is refused - validation and
  `ApplyConfig` both say HAProxy's `error opening file
  '/etc/janus/pki/ca.key'` -, as is `/etc/.state/pki/ca.key`, the
  server key, the ACME account key, the Controller's and the network's
  files. The node's own configuration still applies, HAProxy serves,
  reloads under load lost nothing, the cluster's peers still connect,
  the boot is as fast. Zero AVC denials.
- **#009**: right after the update nothing was ordered - the node's
  page said why: "the Controller's ordering policy doesn't allow the CA
  directory". With the lab's CA allowed but no rule, "doesn't allow
  the name". A rule for one name ordered that one and refused the
  other; a rule whose labels didn't match the node refused, until the
  node got the label - then ordered. The page's **Policy** in both
  themes, no axe finding.
- **#010, #011**: `"daemon"` in quotes and an `.if` block refused with a
  clear message, the node's own configuration applied; a domain with a
  newline and a `nameserver` line sent by the lab router's DHCP server
  was ignored ("label ... may only contain letters, digits and '-'"),
  a legitimate one used as the search domain.
- **#013, #016, #015**: a reader of the Controller - and a node's
  `os:reader` certificate - sees a cluster version's haproxy.cfg with
  `password <redacted>`, no keepalived.conf, no member variables
  (all visible on the release); a string-keyed stick table's keys as
  `(hidden)`, counters kept, an address-keyed table as before. A forged
  audit line stays one quoted line, a 3,000-character path is recorded
  at 512, an anonymous flood of 200 requests left 58 entries, an
  admin's 120 all.
- **#017**: a member removed by force while the Controller couldn't
  reach it - so never told, still holding its membership and its
  certificate - tried to pull the cluster's secrets from the remaining
  member: **refused at the TLS handshake**. The probes lost nothing.

## The security fixes

### HAProxy without STATE's secrets (#008)

A configuration made of the node's own plus one frontend on the
loopback answering with a file - `http-request return status 200
content-type text/plain file <path>` -, sent to the node's
`ValidateConfig` (the node page's validate), then to `ApplyConfig`
(`janusctl haproxy apply-config`):

| The file | v2026.11.04-2 | v2026.11.05 |
|---|---|---|
| `/etc/haproxy/haproxy.cfg` | valid | valid |
| `/etc/janus/pki/ca.key` (the node CA key) | **valid** | **refused**: `error opening file '/etc/janus/pki/ca.key'`, validation and apply |
| `/etc/.state/pki/ca.key` | **valid** | **refused**, the same |
| `/etc/janus/pki/server.key`, `/etc/janus/config/acme/account.key`, `/etc/janus/controller/ca.crt`, `/etc/janus/network/config.json`, `/etc/.state/config/console.json` | - | refused |

### The Controller's ordering policy (#009)

The Let's Encrypt machine orders through the Controller
(`CONTROLLER_ORDERED`), its CA the lab's private Pebble, reachable only
from the Controller; two certificates - two names over HTTP-01, a
wildcard over DNS-01. Both were valid until January, so each step asked
for their renewal on the node's page and kicked the Controller's pass:

| The policy | What happened | What the node's page said |
|---|---|---|
| None (as after the update) | nothing ordered | "the Controller's ordering policy doesn't allow the CA directory "…" - add it under "Ordering for the nodes" on the Let's Encrypt tab" |
| The lab CA's directory allowed, no name rule | nothing ordered | "… doesn't allow the name "site.lab.test" for this node …", and "*.wild.lab.test" |
| Rules: every node for `site.lab.test`; label `site=lab71` for `wild.lab.test` - the node has no label | **the first ordered** - new serial, served, verified against the CA's root; the wildcard refused | the wildcard's error as above |
| The label put on the node | **the wildcard ordered** within seconds, served and verified | none |

The rules are checked when saved: `*.lab.test` ("isn't a domain suffix
(e.g. example.com)"), a rule with no suffix, and an `http://` directory
are 400s. The tab's **Policy** in the pinned Chromium, light and dark,
with the lab's policy and with none - "No name rule yet: nothing is
ordered until you allow at least one name suffix." -: no console
error, no failed request, no axe finding. The lab keeps a rule for the
two names and its CA's directory.

### The global section (#010)

On a node, `janusctl haproxy apply-config` of the node's configuration
with, in `global`:

- `"daemon"` in quotes: rejected - `global: "daemon" isn't allowed on a
  node: janusd supervises HAProxy in the foreground`;
- `.if defined(HAPROXY_LOCALPEER)` / `insecure-fork-wanted` / `.endif`:
  rejected - `".if" isn't allowed on a node: HAProxy's configuration
  conditionals (.if/.elif/.else/.endif) could hide what a node
  requires`;
- the node's own with a comment more: applied.

## Findings

1. **A Controller can't name the newest release while GitHub is slow
   - not new.** To know the 🔒 fixes, the Controller reads the
   `security.json` of every release - 58 now - one after the other,
   cached in memory only, within one 30 s fetch; any one that fails
   fails the whole list (`readSecurity` returns the error). This
   afternoon GitHub served each file in 8 to 10 s and answered 504 to
   some of them for minutes: the lab's Controller (v2026.11.04-2) said
   "the newest release is unknown" and refused its update (502) for
   26 minutes, each refresh caching a few more; the pre-release's
   Controller, fresh from its start, needed 2 more minutes. The same
   code runs on every Controller, so a restart on a bad GitHub day
   leaves the update and the 🔒 badge unknown until it has read them
   all. The nodes' own update checks went through (the image factory,
   then its mirror). Worth a cache on disk - a published release's
   `security.json` doesn't change - or reading them in parallel and
   leaving out one that fails.
2. **`qemu-lifecycle-slots-test` can fail on the line it expects.**
   `"$CTL" … version | grep -q "^Other slot: B - .*refused"` under
   `pipefail`: `grep -q` exits at the match and janusctl's next write
   gets SIGPIPE, so the pipeline fails - the first attempt's failure,
   the line printed right after it matching. A here-string, as the
   repository's own shell traps say, or `grep` without `-q`.
3. **The cluster update's first refusal named the mirror.** The image
   factory took more than the Controller's 10 s once; the Controller
   asked the mirror, which holds releases only, and the call failed
   with "this mirror has no build of this schematic for v2026.11.05" -
   true, but it reads as if the factory had none. The factory had it.
   A pre-release could say the factory didn't answer, or not ask the
   mirror at all.
4. Smaller, for the record:
   - #017's refusal leaves no line on the member that refused (a TLS
     handshake, before any call); the departed member's peers show
     `UNKN` until it's told to leave.
   - A cluster member's own peers certificate and key
     (`/etc/haproxy/cluster/member.pem`) stay readable by a
     configuration, by design: HAProxy uses them. A member's HAProxy
     domain is locked to the Controller, so an operator can't apply
     such a configuration there.
   - The Ordering card's badge says "ready" while no name rule allows
     anything; the text under the Policy says so plainly.
   - A member re-added after a removal needs its template variables in
     the request; the Controller's refusal names the missing one.
