# v2026.10.14-4 pre-release tests

Tested on 2026-10-14, the evening it was cut: the CI run that built it,
then the lab. The figures to compare with are
[v2026.10.14-3's campaign](v2026.10.14-3.md), measured a few hours
before with the same clients and the same scripts.
The scenarios: [Lab test scenarios](lab-scenarios.md).

## Verdict

**The fix this pre-release brings held, and nothing that worked before
moved.**

**The kernel parameters went back** - `tcp_mem` and `fs.file-max`,
which follow the memory. Tested on a machine created for it:
- paused, the machine went back to its size, and both parameters went
  back with it;
- with its policy removed, both parameters went back before the restart.
v2026.10.14-3 left both still sized for the memory the machine no longer
had.

Everything else matched v2026.10.14-3:
- the Controller's update;
- the rolling update under load (no request lost on the VIP);
- failovers, reboots and rollbacks;
- throughput;
- SELinux enforcing with no denial, CIS 33/33.

Found on the way:

1. **An OOM kill counted twice.** On, paused, on again: auto-scaling took
   the OOM kill it had already answered for a new one, and added memory
   again at once. Fixed in
   [#95](https://github.com/swenske/Janus/pull/95), for v2026.10.14-5.
2. **A CI test's false negative.** The arm64 network test's first attempt
   failed on a kernel line printed in the middle of init's on the serial
   console. Fixed in [#94](https://github.com/swenske/Janus/pull/94).

What the pre-release brings: v2026.10.14-3, plus the kernel parameters
that followed the memory put back when auto-scaling stops resizing -
[its notes](https://github.com/swenske/Janus/releases/tag/v2026.10.14-4).

## CI: image-build

[Run 38633566155](https://github.com/swenske/Janus/actions/runs/38633566155),
from `main` at `3a0767f`, with `release_version=v2026.10.14-4` and
`prerelease`. The pre-release was published 26 minutes after the
dispatch, the second attempt included.

The first attempt failed in one test, the arm64 network boot test, on
`init: sysctl /proc/sys/net/ipv4/conf/eth0/send_redirects=0ext4:
Unknown parameter 'context'`. The kernel printed its line in the middle
of init's on the serial console. arm64 has no SELinux, so STATE's
`context=` mount option is unknown there. The test took the merged line
for a failed sysctl write. The job, run again, passed.
[#94](https://github.com/swenske/Janus/pull/94) makes the check look for
what a failed write logs.

The Controller's self-update test took 2 minutes, against 60 in
v2026.10.14-3's run: the first one with
[#91](https://github.com/swenske/Janus/pull/91)'s module cache, and a
network path that didn't stall.

### The kernel parameters put back

On a machine the lab's Controller created for this campaign from the
pre-release's image:
- 2 vCPU and 1 GiB;
- HAProxy answering by itself;
- probes on its front address throughout.

Created and serving in 12 s.

| Step | What happened |
|---|---|
| A policy (on, up to 4 vCPU and 2 GiB, the kernel parameters following) | the one restart: HTTP unanswered 5.7 s |
| An OOM kill (the three-cache configuration) | 1024 → 1280 MiB 11 s later; `tcp_mem` 10869 14493 21738 → 13914 18554 27829, `fs.file-max` 88969 → 113901, and `somaxconn` 60000 → 4096 (another suggestion) |
| **Paused** | back to 1024 MiB in about 10 s, **and `tcp_mem` and `fs.file-max` back to 10869 14493 21738 and 88969** - journaled *back at its size*. `somaxconn` stays, as the documentation says |
| On again | **1024 → 1280 MiB at once**, *the kernel killed a process for lack of memory (1 since boot)* - the kill of the first time, already answered: fixed in [#95](https://github.com/swenske/Janus/pull/95) |
| A second OOM kill | 1280 → 1664 MiB, the parameters following again |
| **The policy removed** | before the restart, *auto-scaling: kernel parameters applied: fs.file-max 151301 → 88969 (back at its size); net.ipv4.tcp_mem 18483 24646 36967 → 10869 14493 21738*; then the restart without room to grow (HTTP unanswered 6.9 s); the node's parameters at their boot values afterwards |

No request was lost at the OOM kills' reloads; the two outages were the
two restarts a policy set and removed take, as documented.

The machine of v2026.10.14-3's campaign, left with its parameters raised
by that release's defect, was destroyed.
