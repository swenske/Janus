# v2026.11.07 pre-release tests

Tested on 2026-11-07, the morning it came out, on the lab where
v2026.11.05-2 - the newest release - was measured again the same
morning as the baseline ([v2026.11.05-2's report](v2026.11.05-2.md)).
The release that closes the 2026-11-05 security review: its last two
findings, the two that needed a decision, plus a dependency fix:

- **A node's identity only for a root's certificate**
  ([JANUS-2026-031](https://github.com/swenske/Janus/blob/v2026.11.07/security/fixes/JANUS-2026-031.json)):
  `StateExport` and `StateExportGrant` with the identity are refused to a
  Controller sign-in's 12-hour certificate; `janusctl -kit` signs an
  hour's certificate with the fleet's root for that call;
- **rescue and pairing codes hidden in the Controller's machine
  consoles**
  ([JANUS-2026-032](https://github.com/swenske/Janus/blob/v2026.11.07/security/fixes/JANUS-2026-032.json));
- **klauspost/compress 1.20.2** (GO-2026-6865), the zstd decoder that
  reads a node's LOGS partition.

Both fixes were tried on the lab's Controller and on fresh machines it
made - #032 on the release first, where the code shows. The baseline
went through as usual: the Controller's update, the cluster updated in
place under load, failovers, janusd restarted, HAProxy reloaded under
load, rollbacks, HAProxy's throughput against v2026.11.05-2 with an A/B
by rollbacks, the boot stages, the nodes' health, the Controller's pages.

**Fewer load clients than usual.** The production hypervisors that host
two of the three CI runners were to be updated during the campaign (the
update was postponed in the end), so those two runners were left alone:
the load and the probes came from
the build box and the third runner only. Every throughput figure below
is compared with v2026.11.05-2 measured this morning from the same
client, not with the previous reports' figures (taken from another
runner).

## Verdict

**Both fixes work on the lab's real Controller and enforcing nodes, the
LOGS partition reads as before, and the baseline holds: the cluster's
in-place update lost nothing on the VIP (0 of 3,308), the failovers are
as before, zero AVC denials, every node CIS 33/33. My opinion: ready to
promote.** The decision is yours. No regression found.

- **#031**: with the Controller sign-in's certificate, `system state
  export -identity` is refused - "the node's identity - its CA's key -
  goes only to a certificate this node's own CA or the fleet's root
  itself signs, and admin's comes from an issuing CA: add -kit KIT" -
  and leaves no file; without `-identity` the export goes through and
  carries no `pki/ca.key`; with `-kit` it carries the CA key and the
  node logs `kit:admin`. Node to node, `-identity` without `-kit` is
  refused at the grant and nothing is staged; with `-kit` the new
  machine takes the old one's CA; without `-identity` the replacement is
  unchanged.
- **#032**: on v2026.11.05-2's Controller an operator and an admin
  watching a machine's console both saw its rescue code, in the
  `rescue: code` line and in the banner. On v2026.11.07's both see
  `[hidden by the Controller - read it on the hypervisor's console]`
  in both places, and nothing code-shaped is left in the stream; the
  hypervisor's own console still shows the code, and `janusctl access
  rescue` works with it.
- **klauspost/compress**: a fresh machine with a LOGS partition reads
  its previous boot's logs through `janusctl system logs -boot -1` and
  through its node page's Service logs, the same line counts both ways.

## The security fixes

### A node's identity, only for a root's certificate (#031)

Three fresh Controller machines on the pre-release's default image, made
by the lab's Controller in 12 to 15 s each. The first - the old node -
given a state of its own: a marker in its `haproxy.cfg` (its health
frontend answering "st-old 73 state"), a file in HAProxy's files,
`net.ipv4.tcp_fin_timeout` 33 confirmed. Every call with the janusctl
context of a Controller sign-in (an admin certificate of the fleet's
issuing CA); `-kit` with the Controller's recovery kit, its passphrase
through `JANUS_KIT_PASSPHRASE`.

| Step | What happened |
|---|---|
| `system state export -identity FILE`, no `-kit` | **PermissionDenied**: "the node's identity - its CA's key - goes only to a certificate this node's own CA or the fleet's root itself signs, and admin's comes from an issuing CA: add -kit KIT (the fleet's recovery kit) or use the node's own credential (janusctl access rescue)"; **no file left** |
| `system state export FILE` (no `-identity`) | written, 17 files; under `pki/` only the fleet's root and bundle - **no `pki/ca.key`** |
| `system state export -identity -kit KIT FILE` | written, 22 files, **`pki/ca.key`** among them with the CA and server certificates; the old node's log: "state: exported (21 files, identity true) - by **kit:admin** (os:admin, fleet)" |
| A third machine: `system state import -from OLD -identity`, no `-kit` | refused **at `StateExportGrant`** with the same message; the machine untouched - its own health answer and CA, only "a signing request made" in its log |
| A second machine: `system state import -from OLD` (no `-identity`) | "Identity: this node's own"; back in the old node's state - the marker, the file (same SHA-256), the kernel parameter; its API certificate still issued by its own CA. The old node's log: the grant "(identity false) - granted by admin", the export by the transfer certificate |
| The third machine: `-from OLD -identity -kit KIT` | "Identity: <the old node>'s"; after its restart its API certificate is issued by the old node's CA (the same key identifier), its health answer the old node's. The old node's log: "… may pull this node's state once, until … **(identity true) - granted by kit:admin** (os:admin, fleet)", then the export by the third machine's transfer certificate |

The old node's audit holds both refusals (`StateExport`,
`StateExportGrant`, PermissionDenied, by `admin`) and the calls that
went through by `kit:admin`. Zero AVC denials on the three machines.
The export files were deleted at once, and the machines destroyed - the
third carried the old one's CA.

### Rescue codes hidden by the Controller (#032)

A Controller machine (the release's default image) on the second KVM
host; a rescue volume from `janusctl image rescue-volume` attached on
the host as a SATA CD-ROM, the machine cold-booted. Its console opened
from the Controller during the boot by a throwaway **operator** account
and by the **admin** at once (the Controller's console hub fans one
libvirt console out to both). Each stream decoded with every code-shaped
string counted, then masked in the saved copy.

| | v2026.11.05-2's Controller | v2026.11.07's Controller |
|---|---|---|
| The operator's stream | **the code**, in `rescue: code … on :9506 until …` and in the banner's `rescue` row | `rescue: code [hidden by the Controller - read it on the hypervisor's console] on :9506 until …`, the banner the same; **no code-shaped string** |
| The admin's stream | the code, the same two places | the same notice, twice; no code-shaped string |
| The rest of the console | - | as on the hypervisor's: 706 against 711 lines, the same 13 janusd and 85 init lines |

The node ran v2026.11.05-2 throughout: the hiding is the Controller's
doing. Then the Controller's consoles closed, the next cold boot was
read on the hypervisor's own serial console (`virsh console`): the
`rescue: code` line carries the code there. `janusctl access rescue`
with it got an `os:admin` certificate, CN `rescue:<name>`, an hour; one
call with it, and janusd logged "an admin certificate for rescue:…, an
hour, issued to … - the rescue window is closed". The volume detached
and the machine cold-booted again: no rescue line, :9506 shut, the node
`trusted` in the fleet, zero AVC denials.

### klauspost/compress: the LOGS partition (GO-2026-6865)

| Read | Result |

| The node page's Service logs in the browser | below, no problem |

## The baseline

### The Controller's update

The lab's Controller updated itself from v2026.11.05-2 to v2026.11.07
through its updater: the pre-release offered apart (`update_available`
false); refused without `"prerelease": true` (409); the job "Updated to
v2026.11.07" in 25 s; **7.76 s** without an answer (76 probes of 612,
every 0.1 s, none slower than 0.5 s). The session, in memory, was lost
and signed in again; `docker compose up -d` gave the updater the
pre-release's image too (Compose v5.7.0 in both). The `ha/` directory as
before, no stale socket.

### The image factory

The node page's pre-release request for the lab's schematic first
answered "unavailable" although the factory was up - it logged the
build request that second and built it: the Controller's request ran
out of time on its side (finding 1); a minute later the same request
answered "building", **ready in 87 s**. The two other
schematics the lab uses (the longterm kernel, Let's Encrypt) were ready
in 34 and 38 s.

## Findings

None of this release's doing.

1. **The first pre-release request after a release blames the factory
   for the Controller's own timeout** (pre-existing - the v2026.11.05
   campaign saw the same message). The Controller prepares a
   pre-release within one 10-second budget: the node's version, the
   newest releases from GitHub - cold right after a release, the slow
   path of [#553](https://github.com/swenske/Janus/issues/553) - then the
   image factory. The budget ran out, the mirror was then asked with the
   same expired context, and the answer read "unavailable", "context
   deadline exceeded" for the factory and its mirror, while the factory
   had the request and built it. A minute later, the caches warm, the
   same request answered "building". Added to #553: its own budget for
   the preparation, no mirror with an expired context, "timed out"
   rather than "unavailable".

## Not tested

- The hiding of a **pairing** code in the Controller's console: a
  Controller machine trusts the fleet from its first boot and never
  opens a pairing window; the rescue window's line and banner were
  tested, and both kinds of code go through the same redactor.
- The zstd decoder's crash itself (two-block frames) can't be produced
  from the lab without writing the LOGS partition by hand; the fix is
  proven by govulncheck and its tests, the lab shows the reading
  unchanged.
- The rolling update through the Controller's node pages wasn't run:
  the cluster's in-place update covers the same nodes under load.
