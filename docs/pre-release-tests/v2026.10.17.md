# v2026.10.17 pre-release tests

Tested on the morning of 2026-10-17, right after it was cut. It is
[v2026.10.16-5](https://github.com/swenske/Janus/releases/tag/v2026.10.16-5)
with its dependencies brought up to date - the round merged in
[#136](https://github.com/swenske/Janus/pull/136): the Go modules the
nodes, janusctl and the Controller are built with (`x/crypto` v0.58.0,
`x/net` v0.61.0, `x/text`, `x/term`, `go-pkcs12` v0.7.4), Vite and
lucide-react in the Controller's pages, the docs site, the Debian images
the build starts from, and CI's own tools. None of them fixes a known
vulnerability, and HAProxy, the kernels and the extensions are the same
versions. This run repeats every update step of the previous campaign,
with the release measured again the same morning.
The scenarios: [Lab test scenarios](lab-scenarios.md).

## Verdict

**Ready to promote.**

- **Nothing moved**: the Controller's update, the image factory, the
  rolling update, failovers, firmware and kexec reboots, rollbacks and
  HAProxy's throughput all match the release, measured the same morning
  (throughput within -4 % and +6 % run by run, both ways).
- **The longterm track**: the lab's machine on it, updated through the
  Controller, runs 6.18.57 on the new release - SELinux enforcing with
  no denial, CIS 33/33.
- **The Controller's pages**: the lab's Controller serves the rebuilt
  pages, and CI's screenshots of every page match the committed ones.

## CI: image-build

[Run 39002420971](https://github.com/swenske/Janus/actions/runs/39002420971),
from `main` at `1b17dab`, with `release_version=v2026.10.17` and
`prerelease`. Its first attempt failed in `qemu-system-info-test`:
"couldn't extract pki/admin.crt from disk.img's STATE partition". The
test reads the node's first credentials off its disk the moment HAProxy
answers - 4 s after QEMU started, under KVM - and HAProxy starts before
the PKI, by design: the credentials weren't written yet, or were still
only in ext4's journal. [#127](https://github.com/swenske/Janus/pull/127)
made five tests wait for them; this one and about twenty others still
read them once. Nothing to do with this release's changes: the re-run of
that job passed. Published at 07:49 Paris, 85 minutes after the
dispatch - the images job took 39 minutes, the new Debian base images
having invalidated the build cache (the kernels and every stage were
built again). Its `security.json` says *none* against v2026.10.16-5: no
🔒 in its name, no badge.

v2026.10.16-5, which only added the docs - and was measured again that
morning before the update. The fourth client machine, which also drives
the campaign, has a memory fault found the night before: nothing was
built on it, the janusctl it used came from the pre-release's own
package (checked against the release's digest).

The rolling update's one lost probe on the VIP came 8 s after the VIP
had moved back to node 01: nothing happened on either node then (their
logs, keepalived's included, are quiet from the switch on), and a
single lost probe shows in 4 of the 10 previous campaigns' rolling
updates. The node-loss failover of the VIP has taken 0.54 to 0.70 s
in the previous seventeen runs; `wrk`'s 99th percentile during the
rolling update was 17.82 ms in v2026.10.16-3's campaign, 3.55 ms in
-4's. `wrk`'s 16 read errors are its 8
keep-alive connections, closed once by each node that reboots, as in
every campaign. The path check before the campaign (the probes for 2
minutes, nothing changed): 0 lost of 2,196 on the VIP and of 2,194 on
the anycast address.

### HAProxy's throughput

`wrk` on the VIP, 30 s a run, the release measured first, the same
morning (requests/s, 99th percentile):

| keep-alive, 64 connections | 42,336 / 42,322 (7.6 / 45.9 ms) | 44,026 / 42,827 (10.2 / 20.2 ms) |
| keep-alive, 256 connections | 51,247 / 52,061 (12.6 / 17.6 ms) | 50,492 / 50,593 (15.3 / 13.5 ms) |
| a new connection per request, 32 connections | 2,562 / 2,428 (40.8 / 43.2 ms) | 2,621 / 2,580 (42.6 / 38.4 ms) |
| **The four clients at once**, 256 keep-alive connections each (total) | 48,857 / 48,966 (99th percentile 169-181 ms) | 48,269 / 49,076 (166-192 ms) |

Within the runs' own spread both ways (-4 % to +6 %): HAProxy and the
kernel are the same builds of the same versions. A run's 99th
percentile on few connections jumps from one run to the next (46 ms in

the kernel 1.8 s, the API listening 2.1 s after the kernel started.
