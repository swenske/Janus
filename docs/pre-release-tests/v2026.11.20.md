# v2026.11.20 pre-release tests

Tested on 2026-11-20, the evening it came out, on the lab where
v2026.11.19-3 - the newest release - was measured first, the same
evening, with the same clients ([v2026.11.19-3's
report](v2026.11.19-3.md)). What the pre-release changes:

- **HAProxy's reloads hand the listeners over** (#680, #697): the
  previous process passes its listening sockets to the new one through
  a socket of janusd's (`expose-fd listeners`, `-x`) instead of closing
  them, so connections waiting in their queue are no longer reset;
- **`net.ipv4.tcp_migrate_req` on at boot** (#696), for the reloads
  that still open new listeners (a changed `bind`, backlog, threads...,
  and the first one after janusd restarts);
- **removing a Let's Encrypt certificate no longer deadlocks the
  node's ACME manager** (#694, #695), and a boot puts back - or deletes
  - a certificate file a hung removal had set aside;
- **node_exporter 1.13.1** (#693).

The kernels, the Controller's pages and HAProxy (3.4.8, 3.2.27, 3.0.31)
are v2026.11.19-3's. So the campaign measured the reloads first - a
new connection per request straight on the VIP, which the build box
alone can't do at a useful rate through its own QEMU -, then the other
two HAProxy branches, the certificate removal on the release and on
the pre-release, the cluster (its `peers` listener is handed over too)
updated in place under load and reloaded, and a short core campaign.
No firmware or kexec boots and no walk through the pages: neither the
kernels nor the pages changed.

## Verdict

**The hand-over does what the notes say. Forty reloads under about
12,000 new connections a second failed 571 requests on the release and
none on the pre-release, every reload handed over, one HAProxy left;
the same on the 3.0 and 3.2 branches, and inside a cluster. The reloads
that must open new listeners - a changed backlog, janusd's own restart
- lost nothing either, `tcp_migrate_req` on. The certificate removal
that hung the release's ACME manager (reproduced: every ACME call and
even a HAProxy apply timed out) is now refused in 0.03 s while
`haproxy.cfg` uses the file and accepted in 0.06 s once it doesn't; the
node left hung on the release came back whole from the update. The
cluster updated in place in 40.9 s with its tables carried, node_exporter
is 1.13.1, and everything else measured as on the release. Two things
worth knowing, neither a regression: a janusd restart reloads HAProxy
itself (so "the first reload after a restart" is janusd's own, at its
start), and a cluster member's stick-table counters can dip, once even
restart, when it reloads under load - on the release as well. My
opinion: ready to promote** - the decision is yours.

## Reloads under new connections

Node 01 (the VRRP master), its configuration as the lab runs it - one
HTTP frontend balanced over the two backends, `option
idle-close-on-response` in `defaults`. The load straight on the VIP,
`Connection: close` so that every request is a new TCP connection:
`wrk -t4 -c32` from the build box and `wrk -t2 -c8` from an idle CI
runner at the same time, plus the VIP and anycast probes every 50 ms.
Meanwhile 40 reloads of node 01, one every 3 s (`apply-config` with a
comment that changes each time; each apply took 0.26 to 0.41 s).
Counted: every `wrk` error (connect, read, write, timeout, non-2xx),
the probes lost, then node 01's `haproxy.started` events and its
processes.

The build box first reached only 1,100 new connections a second after
half a minute: its ephemeral ports were full of `TIME_WAIT` (it closes
first, and its kernel reuses such ports only towards itself). For the
campaign the box - a load client, nothing else - had
`net.ipv4.tcp_tw_reuse=1` and a wider port range, put back afterwards:
9,000 to 10,000 new connections a second steadily from it alone,
12,900 at 64 connections.

| `tcp_migrate_req` on node 01 (read from `/proc` through the API) | 0 | **1** |
| Build box: requests, rate | 1,347,944, 9,838 req/s | 1,322,449, 9,649 req/s |
| Build box: errors | **466 read errors** (connections reset) | **0** |

| HAProxy processes after | 1 | 1 |

571 failed requests out of 1.65 million on the release - what #680
describes, a little under the build box's own figures since the lab's

waited for its retransmission, not a reload's reset.

A last round at a higher rate - `wrk -t8 -c128` from the box with the
runner: about 12,400 new connections a second, node 01 saturated (mean

requests, **0 errors**, every reload handed over, 0 and 1 probes lost

### The reloads that open new listeners

Same load, a plan of reloads 3 s apart on the pre-release:

| Plan | `handover` of each reload | `wrk` errors | Probes lost (VIP / anycast) |
|---|---|---|---|
| The configuration twice, `bind *:80 backlog 2048` three times, the configuration three times | true, true, **false**, true, true, **false**, true, true | **0** of 523,290 | 3 / 5 (see below) |
| The backlog alone, then back | **false**, **false** | **0** of 601,323 | 0 / 0 |

A changed backlog opens new listeners (a socket handed over would keep
its old backlog), and the next reload hands over again. With
`tcp_migrate_req` none of their queued connections was reset - the
notes' "0-2 per 45 reloads" measured as 0 and 0 here. The few probes
lost in the first plan were lost at the same instant on both addresses
- the anycast one served by either node (the router spreads it) - and
two of them before the first reload: the client's, not the reloads'.

### janusd restarted

`janusctl system restart` on node 01 under the same load, then reloads:

| | Result |
|---|---|
| janusd back | about 6 s after the call |
| HAProxy at janusd's start | **reloaded by janusd itself**: `-sf <the previous pid>`, no `-x`, `"handover": false` - the pid changed (802 → 814, 868 → 879) before any reload was asked for |
| The next reload asked for | `"handover": true` |
| `wrk` errors | 69, 29 and 76 in three runs |
| Where they fall (the load cut into one-second runs) | 20 at +2.5 s, when keepalived - a child of janusd - stopped and the VIP went to node 02; 21 at +6.8 s, when it was back and took the VIP back; **0 in the second of HAProxy's reload** at janusd's start |

So the errors of a janusd restart on the VRRP master are the VIP
leaving and coming back - as the release's campaign measured a restart
-, not HAProxy: its reload without hand-over at janusd's start lost
nothing. The notes' "the first reload after janusd restarts also opens
new listeners" is that reload at janusd's start; `janusctl system
restart`'s "HAProxy keeps serving" is true, but HAProxy is reloaded.

## Removing a Let's Encrypt certificate

On the Controller's Let's Encrypt machine, outside any cluster: two
certificates issued by the lab's private CA, `site` (HTTP-01) and
`wild` (DNS-01), ordered for the node by the Controller. Every call
bounded (`timeout 60`), through the Controller's relay like any
`janusctl` call with a Controller context.

### On the release - the incident and the upgrade note

| Step | v2026.11.19-3 |
|---|---|
| `haproxy.cfg` naming only `wild.pem` | applied (0.13 s) |
| `acme check` of the configuration without `site` | **no answer**, cut at 10.0 s (the Controller's relay: `Canceled`) |
| `acme status` | **`DeadlineExceeded`** at 10.0 s |
| `acme apply` without `site`, `acme get` | the same, 10.0 s each |
| `/etc/haproxy/.acme-removing/` | **`site.pem` set aside there** |
| `haproxy apply-config` (the same configuration) | **`DeadlineExceeded`** at 10.0 s - HAProxy kept serving |
| The note: `janusctl system restart` | janusd back in about 6 s, `acme status` answers: `site` **pending** with a stand-in in `acme/` (its configuration still names it: the hung apply saved nothing), **`site.pem` still in `.acme-removing/`** |
| Then updated to the pre-release through its page | back in **7.0 s**; at its boot **`site.pem` put back** (the real certificate, served on :443 again), `.acme-removing/` gone; `acme status` answers, both certificates valid |

The incident is #694's exactly. The boot's recovery took the right
branch: the certificate was still configured, without a real one in
place, so the file came back rather than being deleted. Left in the
status: `site`'s last failed attempts (the stand-in's orders, refused by
the Controller's ordering policy, which doesn't allow the lab CA's
directory) - shown under a certificate that is valid again.

## Findings

None in the pre-release. Worth knowing:

1. **A janusd restart reloads HAProxy.** At its start janusd reloads
   the HAProxy that kept serving (`-sf`, without hand-over: it doesn't
   know what the previous process opened), so the pid changes before
   any reload is asked for - that is the notes' "first reload after
   janusd restarts", and it lost nothing here. `janusctl system
   restart` says "HAProxy keeps serving": true, but a reader expecting
   the same process (or no reload at all) is surprised. On a VRRP or
   BGP node the restart also moves the VIP and the route away and back
   (keepalived and BIRD are janusd's children) - those moves are what
   the clients notice.
2. **A cluster member's stick-table counters under load at a reload.**
   On both releases a reloaded member's counts can dip for a moment and
   the peers lose about 5,000 increments per ten reloads at 12,000
   requests a second; once in six runs (on the pre-release) a key's
   count restarted from zero and stayed so. A rate-limiting table would
   forget a client's history at such a reload. Not this release's (the
   hand-over doesn't change how the tables are learnt), worth an issue.
3. **A load client reaching 10,000 new connections a second** needs
   `tcp_tw_reuse` (or several addresses): with Linux's defaults the
   build box fell to 1,100 a second after half a minute. Worth noting in
   the scenario, done there.
4. **The Let's Encrypt status keeps a stale failure**: after the boot
   put `site.pem` back, `acme status` still showed the stand-in's last
   failed attempts and a next attempt under a certificate valid until
   2027.
