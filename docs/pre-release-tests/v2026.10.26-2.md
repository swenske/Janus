# v2026.10.26-2 pre-release tests

Tested on the evening of 2026-10-26. It is [v2026.10.26](v2026.10.26.md)
with:

- **a network change leaves a VRRP node's virtual IP alone**: a node
  removes only the addresses it added itself, and the boot DHCP lease's
  ([#342](https://github.com/swenske/Janus/pull/342));
- **the same IPv6 anycast address on several nodes**: a `/128` is added
  without duplicate address detection (#342);
- **a refused call relayed as the node answered it**: an `ApplyConfig`
  stream error comes back with the node's words and its code, not a 502
  ([#339](https://github.com/swenske/Janus/pull/339));
- an IPv6 VRRP test, and the docs of BGP multipath behind RouterOS
  ([#332](https://github.com/swenske/Janus/pull/332),
  [#341](https://github.com/swenske/Janus/pull/341),
  [#343](https://github.com/swenske/Janus/pull/343)).

The same lab as the campaigns before; its HAProxy and kernel unchanged.

## Verdict

**Ready to promote.** Both defects #342 fixes were first seen on a
production cluster, then reproduced on the lab with v2026.10.26 before
the update - and are gone with v2026.10.26-2:

- **A network change on the VRRP master**: with v2026.10.26, each apply
  took keepalived's virtual IP off the node holding it - keepalived saw
  it go, left MASTER and took it back - and **3 of 840 requests to the
  VIP were lost**; with v2026.10.26-2, **none**, and keepalived saw
  nothing.
- **The same IPv6 anycast `/128` on both nodes**: with v2026.10.26, node
  02's copy ended **"dadfailed"** - the router still sent it half the
  flows: **389 of 547 requests failed**, and 11 s of total outage while
  node 01's HAProxy was stopped; with v2026.10.26-2, both copies usable,
  **1 of 547** lost - as node 01's HAProxy stopped.
- **The relay** (#339): a stream error through a node's page comes back
  with the node's message and the matching code.
- **The baseline**: the rolling update under load lost **nothing** on the
  VIP nor on the anycast address; HAProxy's throughput level with
  v2026.10.26's; zero AVC denials, the CIS audit 33/33.

The router's half of an IPv6 anycast address - BGP over IPv6 with BFD,
multipath, `l4` - also ran for the first time (RouterOS 7.25).

## What this pre-release changes

### A network change on the VRRP master (#342)

Under probes of the VIP and of the anycast address (every 50 ms, from
the fourth client), a network configuration applied on the node holding
the VIP - an address no one announces added to its front interface,
taken away 12 s later -, keepalived's log read on that node before and
after. The same on v2026.10.26 before the rolling update, then on
v2026.10.26-2.

| | v2026.10.26 | v2026.10.26-2 |
|---|---|---|
| keepalived, at each apply | "Netlink reflector reports IP *the VIP* removed from front", then BACKUP and MASTER again - twice | nothing |
| The VIP | **3 lost** of 840 (0.05 s and 0.11 s) | **0** lost of 840 |
| The anycast address | 0 lost of 837 | 0 lost of 837 |

The production case: the node's network configuration applied through
the Controller - an anycast address added to a cluster member that held
a public VIP - removed it the same way; keepalived took it back within
the second.

### The same IPv6 anycast address on both nodes (#342)

For the campaign only, taken off afterwards (the router's configuration
compared with its export from before): a ULA `/64` on the front network
and another on the backends' network, on the router; the router's BGP
over IPv6 with both nodes (`afi=ipv6`, BFD at 200 ms × 3, the lab's
multipath, IPv6 flows hashed by ports), only `/128`s from the anycast
prefix accepted, IPv6 BGP and BFD let in and the backends let through to
the anycast address (the router's IPv6 firewall drops everything else);
on each node, an address on the front `/64`, **the same `/128` anycast
address**, an IPv6 gateway, an IPv6 session exporting a `haproxy_*`
static route, HAProxy on IPv6 too. A backend VM, through the router,
asked the anycast address every 50 ms for 30 s, node 01's HAProxy
stopped for 8 s in the middle. Set on v2026.10.26; the rolling update
then took both nodes to v2026.10.26-2 with it in place.

| | v2026.10.26 | v2026.10.26-2 |
|---|---|---|
| The `/128` on node 01, node 02 (`/proc/net/if_inet6` flags) | permanent; **dadfailed, tentative** - node 01 answered node 02's duplicate address check | permanent, `nodad` on both |
| The router's routes to it | two, both active (multipath) | two, both active |
| IPv6 BGP and BFD | established, up | established, up |
| The probes | **389 failed** of 547 - every flow hashed to node 02, and **11.2 s of total outage** while node 01's HAProxy was stopped (only node 02's route left) | **1 failed** of 547, as node 01's HAProxy stopped |
| Answered by | node 01 only (158) | node 01 (170), node 02 (374 - alone during the stop) |

### A refused call through the relay (#339)

Through a node's page, `POST /api/haproxy/config` asking to go back to a
version its history doesn't have: **404, "No such version in the
history: 999999"** - the node's status and words; before #339, every
error of the call's stream came back as a 502, as if the node were out
of reach (v2026.10.26's [finding 1](v2026.10.26.md#findings), a
cluster's lock). A configuration HAProxy refuses is still a 200 whose
`stage` is `rejected` with the node's message - the call's answer, not
an error.

## Findings

1. **`qemu-acme-*-test`'s HTTP-01 fetch flakes**: Pebble's request to
   the node's port 80 (QEMU's user network) gets "connection reset" -
   v2026.10.26's first attempt, then both runs of this pre-release
   (`qemu-acme-proxy-test`, then `qemu-acme-ordered-test`). Each passed
   on a rerun, `qemu-acme-proxy-test` on the build box too. Three builds
   in a row: worth finding out why.
2. **The screenshots job timed out** waiting for a page's text (a log
   target's name; an app's name at v2026.10.26's build): it only
   reports, and passed on the rerun.
3. **The lab's Logstash is still out of reach from the lab** - "network
   is unreachable" from the nodes, as at v2026.10.26's campaign: the
   network's, not Janus's.
